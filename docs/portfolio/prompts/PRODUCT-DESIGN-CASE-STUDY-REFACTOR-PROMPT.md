# 产品设计案例页重构：Codex 通用提示词

这份提示词用于把其他产品项目的“设计页 / 案例页”重构为一份能够体现系统产品思维的作品集案例。

这里的“设计页”特指产品案例页、项目复盘页或作品集详情页，不是官网首页、营销落地页，也不是产品后台本身。

默认采用两阶段流程：

1. 先审计项目材料、证据和页面缺口，输出重构方案；
2. 用户确认后，再修改案例页、补充配图并完成验证。

这样可以避免在证据不足时直接编写结论，也能防止 Codex 误改营销页或擅自增加产品功能。

---
## 一、使用前填写

复制后替换以下变量；无法填写的内容可以保留为空，让 Codex 从项目文件中检索。

| 变量 | 填写内容 |
|---|---|
| 项目根目录 | `{项目路径}` |
| 当前设计页路由或文件 | `{例如 /case-study 或 src/pages/case-study.tsx}` |
| 产品 Demo 路由 | `{例如 /dashboard；没有则留空}` |
| 线上地址 | `{没有则留空}` |

## 二、可直接复制给 Codex 的完整提示词

```text
你是一名资深产品经理、UX 研究员和产品作品集设计师。请在当前项目中重构“产品设计案例页”，让读者能够清楚看到我如何发现问题、研究用户、分析需求、定位目标用户、控制产品范围、设计产品模型、产出界面方案并验证迭代。

【项目信息】
- 项目根目录：{项目路径}
- 当前设计页路由或文件：{设计页路由或文件；未知时请自行检索}
- 产品 Demo 路由：{Demo 路由；没有则留空}
- 线上地址：{线上地址；没有则留空}
- 我的真实角色：{个人项目 / 团队项目 / 产品经理 / UX / AI 辅助开发等}
- 项目时间：{项目时间}
- 希望重点体现的能力：{可留空}
- 是否允许联网研究：{是 / 否}
- 是否允许生成概念配图：{是 / 否}
- 本轮模式：{只输出方案 / 方案确认后实施 / 直接审计并实施}

【任务范围】
1. 本次只重构产品设计案例页或项目详情页。
2. 不要重构官网首页、营销落地页、定价页或产品后台，除非它们只是作为案例页中的真实产品截图被引用。
3. 不新增产品功能。发现当前产品能力不足时，将其写入“缺口”或“未来验证计划”，不要为了让案例完整而修改产品功能。
4. 不覆盖与本任务无关的现有修改，不删除用户已有文件，不擅自重写整个视觉系统。
5. 如果项目缺少关键材料，先说明缺失内容、影响和最低成本补齐方式；需要真实用户或业务环境才能完成的工作必须保留为缺口。

【核心目标】
案例页不能只是界面截图合集，也不能只是“我做了用户研究、竞品分析、原型设计”的名词列表。整页需要形成以下推导链：

研究问题
→ 可追溯证据
→ 分析方法
→ 产品判断
→ 需求与范围
→ 方案模型
→ 界面产出
→ 走查与迭代
→ 已证明结果
→ 尚未证明与未来计划

每一个重要结论尽量回答六个问题：
1. 当时需要回答什么问题？
2. 使用了什么证据？
3. 采用了什么分析或判断方法？
4. 因此做出了什么产品决策？
5. 产出了什么可复核材料或界面？
6. 这个结论的证据边界是什么？

【证据规则】
先审计事实，再写页面。将材料划分为三个等级：

A 类｜直接证据
- 已实现产品、代码、数据库结构、PRD、原型、设计稿；
- 测试记录、验收记录、缺陷记录、发布记录；
- 可公开操作的 Demo、真实产品截图和决策文档。

B 类｜外部行为证据
- 可追溯的公开用户帖子、评论、复盘记录；
- 竞品官网、帮助文档、公开产品界面和功能事实；
- 行业公开资料。

B 类证据只能证明某种现象或模式存在，不能自动代表目标用户总体，也不能写成“我访谈了这些用户”。

C 类｜待验证假设
- 根据公开内容推导出的用户画像；
- AI 扮演角色的模拟反馈；
- 专家走查、启发式评估和预设任务测试；
- 未来目标、预计收益和商业假设。

C 类材料必须明确标注为“假设”“行为角色”“专家模拟走查”或“未来计划”，不能写成真人访谈、真人可用性测试、真实完成率或真实业务结果。

严格遵守以下限制：
1. 不编造用户数量、访谈数量、市场份额、完成率、留存、转化、收入、满意度或效率提升。
2. 只有能从文件、测试或来源中复核的数字才能展示。
3. 研究样本数、竞品数、任务数和测试数只能描述研究或交付规模，不能冒充用户价值。
4. 技术测试通过数、接口数、表数量和代码量不能冒充产品结果。
5. 没有证据的内容不要放在“成果”中，移入“未来验证计划”。
6. 如果材料之间互相矛盾，以最新、可复核且更接近直接事实的材料为准，并在审计结果中说明冲突。

【联网研究规则】
如果“是否允许联网研究”为“是”，可以补充以下只读研究：

1. 搜索目标用户在真实社区发布的第一人称经历、问题记录和替代方案用法；
2. 研究当前竞品的公开官网、帮助文档、产品截图和定价/能力边界；
3. 记录来源链接、访问日期、用户可观察行为和对产品判断的影响；
4. 优先使用原始帖子、官方产品文档和官方页面；
5. 不把公开帖子包装成正式用户访谈，不虚构未出现的原话；
6. 不根据少量帖子计算没有统计意义的比例；
7. 若来源无法访问或无法复核，将结论标记为待验证，不补写确定性描述。

如果“是否允许联网研究”为“否”，只使用项目内已有材料；研究不足时输出缺口和后续研究计划。

【第一阶段：项目与证据审计】
在修改页面前完成以下工作：

1. 阅读项目级说明文件和开发约束，例如 AGENTS.md、README、产品文档、设计文档和部署配置。
2. 检查 Git 状态，识别并保护用户现有的未提交修改。
3. 定位：
   - 当前设计案例页；
   - 官网或营销页；
   - 产品 Demo 页面；
   - 用户研究和竞品研究文档；
   - PRD、需求池、用户故事、JTBD、信息架构和业务流程；
   - 原型、产品截图和视觉素材；
   - 测试、验收、缺陷、发布和复盘记录。
4. 实际运行项目或检查现有线上版本，确认案例页当前展示了什么。
5. 输出证据审计表，至少包含：

   阶段｜已有工作｜证据文件或页面｜证据等级｜可用于案例页的结论｜不可使用的表述｜缺口

6. 按以下类别检查缺口：
   - 项目背景与问题定义；
   - 用户研究；
   - 竞品与替代方案；
   - 需求分析；
   - 用户定位；
   - 机会判断与首版范围；
   - 信息架构、业务流程和产品规则；
   - 界面设计与方案产出；
   - 验证、验收和迭代；
   - 真实结果、证据边界和未来计划。
7. 将缺口分为：
   - 必须补齐：缺少后案例逻辑无法成立；
   - 建议补齐：能增强产品思维表达，但不阻塞重构；
   - 未来补齐：需要真人用户、真实运营或长期数据才能完成。
8. 对每个缺口给出最低成本、可真实执行的补齐方式和预期产出物。

如果本轮模式为“只输出方案”，完成第一阶段后停止修改，向我展示：
- 证据审计摘要；
- 当前设计页最主要的问题；
- 建议页面结构；
- 每一节使用的真实证据和配图计划；
- 需要我确认的缺口。

等我确认后再进入实施阶段。

【建议的案例页内容结构】
页面结构可以根据项目调整，但必须保留完整推导链。推荐使用以下章节：

00｜案例概览
- 一句话说明产品面向谁、解决什么场景、提供什么价值；
- 我的真实角色、负责范围、项目时间和交付形态；
- 只展示可复核的项目规模数字；
- 在首屏或靠前位置写明证据边界；
- 提供“查看产品 Demo”或“查看线上产品”的真实入口。

01｜项目背景与问题重构
- 项目最初的想法或触发场景；
- 初始假设是什么；
- 研究后核心问题如何被重新定义；
- 项目目标、约束、非目标和成功判断；
- 明确展示“原先以为……，证据显示……，因此改为……”。

02｜研究设计与证据
- 需要回答的研究问题；
- 使用了哪些研究材料和选择标准；
- 公开帖子、竞品事实、项目文件和模拟走查分别能证明什么；
- 研究方法、编码维度、证据强弱和局限；
- 用“证据 → 洞察 → 产品动作”展示分析，而不是只列痛点。

03｜竞品与替代方案
- 同时研究直接竞品、间接竞品和用户当前替代方案；
- 只比较与本项目决策有关的维度；
- 每个比较结论对应一个产品判断；
- 展示竞品截图、功能矩阵、体验流程或定位坐标；
- 截图标注产品名称、来源和访问日期；
- 不写“市场上没有”，除非能够严格证明；优先写“现有方案在哪一环节较弱”。

04｜需求分析
- 从行为证据进入问题聚类，再转译成 JTBD、Job Stories 或用户任务；
- 建立可视化需求映射：

  行为证据 → 用户问题 → Job Story / JTBD → 产品响应 → 优先级 → 验证方式

- 说明哪些需求进入首版，哪些需求被延后或主动排除；
- 展示取舍原因，不要只展示完整功能清单；
- 验收标准必须能够在当前产品或测试中验证。

05｜用户定位
- 优先使用行为分群，不用虚构年龄、城市、收入等装饰性人口属性；
- 可使用渠道数量、任务频率、工作流复杂度、维护意愿、生命周期阶段等维度；
- 区分核心角色、次要角色、生命周期延伸角色和边界角色；
- 每个角色写清：
  - 可观察行为；
  - 触发场景；
  - 核心任务；
  - 当前产品适配度；
  - 关键风险；
- 如果画像来自公开资料和产品推导，命名为“行为角色”或“假设画像”，不要称为“访谈用户画像”。

06｜机会判断与产品范围
- 说明产品真正优先解决的机会；
- 可以使用 P0/P1/P2、IN/OUT 或其他范围模型；
- 不虚构 RICE、Kano、满意度或市场规模分数；
- 优先级至少考虑：
  - 是否服务核心角色；
  - 发生频率；
  - 是否破坏核心闭环；
  - 证据强度；
  - 实现成本与风险；
- 用一条主链路说明首版闭环；
- 明确“主动不做”的内容及原因。

07｜产品方案设计
- 不从页面数量开始，而从产品语义和业务对象开始；
- 展示与当前项目有关的：
  - 设计原则；
  - 信息架构；
  - 用户流程；
  - 业务流程；
  - 状态模型或状态机；
  - 关键对象关系；
  - 事件、历史和下一步之间的关系；
  - AI、自动化、人工确认和降级边界；
- 每个核心机制使用以下结构：

  用户问题｜证据｜设计决策｜工作机制｜风险或边界

- 流程图必须表达真实产品逻辑，不制作只有装饰作用的流程图。

08｜界面与交付产出
- 优先使用当前产品的真实界面截图；
- 按用户主链路组织截图，而不是按页面目录罗列；
- 每个界面案例说明：
  - 用户当时的问题；
  - 关键设计决策；
  - 界面如何承载产品机制；
  - 仍未验证的边界；
- 可展示桌面端、移动端、关键状态、空状态、错误状态和前后对比；
- 截图应有清晰裁切、重点标注和说明文字；
- 不使用与实际产品无关的模板 Mockup 冒充设计产出。

09｜验证与迭代
- 先检查项目是否已有真人访谈、可用性测试、验收或线上数据；
- 没有真人数据时，可以进行“专家模拟走查”，但必须遵守以下方法：
  1. 根据证据建立 3—4 个边界清楚的行为角色；
  2. 每个角色预先定义任务和预期结果；
  3. 每个角色从相同、可恢复的演示数据开始；
  4. 在桌面和移动视口执行真实操作；
  5. 记录满足、未满足、观察、严重度和影响；
  6. 将发现的问题区分为核心闭环、体验增强和待验证；
  7. 本轮不新增产品功能时，只把缺口写入未来计划；
  8. 如果用户另行授权修复，修复后使用隔离数据重新走查；
  9. 模拟结果只能称为“预设结果覆盖”或“专家走查结果”，不能称为“用户任务完成率”。
- 用“观察 → 判断 → 修改或计划 → 复测结果”展示迭代闭环。
- 不记录 AI 角色虚构的满意度、推荐意愿或主观评分。

10｜结果、边界与未来计划
- 分开呈现：
  - 产品设计证据；
  - 交付和质量证据；
  - 真实用户或业务结果；
- 没有真实运营结果时，诚实写成“完成可操作产品、核心闭环、公开 Demo 和验收”，不要写成“提升用户效率”或“获得市场验证”；
- 单独列出“当前项目真正证明了什么”；
- 单独列出“还没有证明什么”；
- 未来计划优先验证现有设计是否有效，不默认继续增加功能；
- 给出下一阶段需要真人完成的访谈、任务测试、连续试用或指标验证。

【视觉与配图策略】
案例页应该有足够的视觉材料，但每张图都要承担信息表达任务。

优先级如下：
1. 真实产品截图、原型、PRD、验收记录和研究材料；
2. 根据真实项目数据绘制的流程图、状态图、需求映射、矩阵和时间线；
3. 为解释抽象场景生成的概念插画；
4. 纯装饰图片。

建议至少覆盖：
- 项目主链路总览图；
- 研究材料到产品决策的转译图；
- 竞品或替代方案矩阵；
- 行为角色图；
- 需求优先级或 IN/OUT 范围图；
- 信息架构图；
- 用户流程或业务流程图；
- 状态模型 / 对象关系图；
- 3—6 张真实产品界面截图；
- 验证任务、问题和修复前后对照。

配图规则：
1. 有真实截图时，不生成相似假截图替代；
2. 概念插画必须标注“概念图 / 原创插画 / 非研究参与者照片”；
3. 竞品截图必须标注来源，不伪造竞品界面；
4. 图表中的数字必须来自可复核材料；
5. 使用项目现有视觉语言，控制色彩、字体、圆角和间距；
6. 避免无意义的玻璃卡片、渐变大字、装饰性 3D 和模板化 Logo 墙；
7. 为图片提供准确的 alt 文本；
8. 同时检查桌面端和移动端，不允许靠缩小桌面布局应付移动端；
9. 优先使用项目已有组件、CSS、SVG 或 Mermaid；只有确有表达价值时才生成新图。

【第二阶段：实施要求】
在我确认方案，或本轮模式明确允许直接实施后：

1. 先列出将修改的文件和不会修改的页面。
2. 只修改案例页及其必要的局部组件、样式、研究文档和图片资源。
3. 不修改营销首页的内容结构，不新增产品功能。
4. 保持现有导航、品牌语言和响应式体系，避免为了案例页引入大体积依赖。
5. 先复用已有真实材料；需要新增图表时，从证据文件生成。
6. 对研究、竞品、测试和结果使用清晰标签，保证读者不会混淆证据等级。
7. 如果发现某条文案无法被项目材料证明，删除、降级为假设或移入未来计划。
8. 页面应该可快速扫描：章节导航明确，结论优先，细节可展开，长表格在移动端可读。
9. 所有链接、按钮和图片都必须可访问；不能留下占位 CTA、假链接或空图片。
10. 实施后检查 Git diff，避免覆盖用户同时进行的其他修改。

【验证要求】
完成实施后至少执行：
- 案例页相关 lint / typecheck / build；
- 桌面视口页面走查；
- 移动视口页面走查；
- 控制台错误检查；
- 图片加载、alt 文本和链接检查；
- 章节锚点与导航检查；
- 明暗主题检查（如果项目支持）；
- 与营销首页的变更范围对比，确认营销页没有被误改；
- Git diff 检查和未跟踪文件检查。

如果项目已有自动化浏览器工具，优先用真实浏览器截图验证。测试失败时说明失败原因、影响和是否与本次修改有关，不隐瞒。

只有在我明确要求上线时，才提交、推送或部署；上线后验证远程提交、部署版本和线上设计页是否一致。

【最终交付格式】
完成第一阶段时输出：
1. 当前证据审计摘要；
2. 设计页缺口与严重度；
3. 推荐信息架构；
4. 每一节的证据来源、核心结论和配图计划；
5. 不能放入当前案例页的内容；
6. 需要我确认的事项。

完成第二阶段时输出：
1. 已完成的重构结果；
2. 修改文件和设计页路由；
3. 新增或复用的图片资产；
4. 研究、需求、用户、范围、方案和验证如何形成闭环；
5. 已证明与未证明的边界；
6. 执行过的验证及结果；
7. 仍需真人或真实业务环境完成的工作；
8. 如果已上线，给出线上设计页地址和对应提交。

现在请先按本轮模式执行。如果模式为“只输出方案”，不要直接修改文件；如果模式允许实施，也必须先完成证据审计，再开始重构。
```

## 五、案例页完成度检查表

### 内容

- [ ] 读者能看懂项目面向谁、解决什么问题；
- [ ] 能看到问题如何被研究证据修正；
- [ ] 竞品分析产生了具体产品判断；
- [ ] 需求从证据推导，不是功能倒推；
- [ ] 用户定位基于行为，不是虚构人口属性；
- [ ] 优先级和主动不做的内容有依据；
- [ ] 信息架构、流程、状态和关键机制可视化；
- [ ] 界面截图按用户主链路组织；

- [ ] 最终汇报包含仍需真人完成的验证工作。
