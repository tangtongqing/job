## 四、项目从 0 到 1 的完整实现流程

### 4.1 阶段 1：发现问题与定义目标用户

项目源于真实求职场景：用户同时浏览多个招聘平台，岗位信息散落；收藏不等于准备投递；投递后的测评、面试和 Offer 通过邮件或聊天通知，难以持续维护和复盘。

为避免把个人感受直接当成市场结论，后续补做了 19 条国内外公开求职记录的人工编码。公开记录能够支持“用户已在使用表格、Notion、飞书、Google Sheets 等替代方案”“记录会因维护成本中断”“通知与日程分散”等行为判断，但不能替代一对一访谈，也不能证明问题在人群中的发生比例。详细证据见 [公开求职行为证据](../research/public-job-search-evidence.md)与[公开情景研究及角色走查](../research/online-scenario-role-walkthrough-2026-07-28.md)。

没有把用户定义成泛化的“大学生”，而是采用行为分群：

> 近一个月使用 3 个以上招聘渠道、累计投递 20 个以上岗位的高频跨平台求职者。

这种分群方式比“应届生”“秋招用户”更稳定，因为它由行为和任务复杂度决定，不受招聘季节限制。

### 4.2 阶段 2：竞品研究与机会判断

分析 BOSS 直聘、牛客、实习僧、看准、超级简历和 LinkedIn Jobs 等主要产品，比较岗位来源、筛选能力、投递追踪、数据复盘和提醒能力。

得到的机会不是“市场上没有投递管理”，而是：

- 招聘平台擅长岗位发现，但用户跨平台后的统一管理能力弱。
- 部分产品支持静态状态标签，但缺少可回溯的状态变化和待办。
- 简历类产品强调简历优化，JobPulse 选择聚焦岗位信息、投递状态和行动安排。
- 国内求职工具普遍缺少基于个人事件数据的有效进展复盘。

这一结论经过修正：超级简历和 LinkedIn 已有投递追踪，因此差异化不是“有或没有”，而是“静态标记与动态状态系统的深度差异”。

### 4.3 阶段 3：用 JTBD 组织需求

使用 Jobs To Be Done 将功能需求改写为用户任务：

> 当我同时在多个平台寻找机会时，我想把值得关注的岗位放进统一清单，以便比较和决定下一步。

> 当我收到测评或面试通知时，我想用很低的成本更新状态并记录时间，以便不遗漏重要节点。

> 当投递一段时间后，我想看到真正进入测评、面试和 Offer 的机会，而不是只看投递总量，以便调整策略。

最终形成问题清单和 20 条 Job Stories，并建立“公开证据/产品假设—任务—功能—验证方式”映射。

### 4.4 阶段 4：优先级和范围控制

采用 P0/P1/P2 管理范围：

| 优先级 | 定义 | 代表能力 |
|---|---|---|
| P0 | 缺失则核心闭环不成立 | 岗位数据、投递状态、低成本更新、待办、无回应关闭 |
| P1 | 增强产品价值 | 看板、订阅、硬条件筛选、有效进展趋势 |
| P2 | 未来能力 | 多用户、支付、简历匹配、原生 App、商业化 |

明确不在 Demo 中实现简历生成、社区、自动投递、支付、多租户和生产级通知。范围控制的判断标准是：是否直接验证“用户能否更低成本地维护求职进度”。

### 4.5 阶段 5：核心产品方案

核心闭环：

> 发现岗位 → 收藏 / 待投递 → 创建投递 → 更新状态 → 处理待办 → 看板复盘

关键概念拆分：

- **收藏**：认为岗位值得保留，但不代表准备投递。
- **待投递**：已经形成行动意图，准备提交申请。
- **投递记录**：真实提交后创建，初始状态为已投递。
- 创建投递时结束待投递标记，但收藏可以继续保留。
- **事件记录**：保存每次状态变化、面试、测评、材料、Offer 和备注。

### 4.6 阶段 6：信息架构与界面设计

产品采用三表面架构：

| 表面 | 目标用户 | 核心任务 |
|---|---|---|
| SaaS 官网 | 潜在用户 | 理解价值并进入产品 |
| 产品后台 | 求职者 | 完成岗位、投递、待办和复盘任务 |
| 案例页 | 招聘方 / 面试官 | 理解研究、决策、实现和验证 |

产品后台导航按用户任务排序：看板、岗位、收藏与待投递、投递、近期安排、订阅。采集页面降级为系统工具，不占用普通用户的主任务流。

视觉设计采用官网与产品后台不同的信息密度：官网强调真实产品展示和连续叙事，后台强调效率、状态可读性和操作反馈。主视频支持停止并回到静态界面，辅助视频仅在悬停时播放，减少与页面元素重叠和持续自动播放造成的干扰。

### 4.7 阶段 7：实现、验收和部署

按照以下工作包推进：

1. 后端地基：配置、数据库、状态机、事件服务。
2. API：岗位、收藏、投递、待办、订阅、看板和采集管理。
3. 数据：演示快照、公开 ATS 接入、清洗、去重和核验。
4. AI：招聘通知解析、降级、缓存、限流和人工确认。
5. 前端：三表面、响应式、主题、错误反馈和真实视频。
6. QA：单元、接口、约束、流程、构建和浏览器验收。
7. 部署：Codex Sites 前端、Railway 后端及持久化数据卷。

## 五、关键产品理论与设计逻辑

### 5.1 BRD、MRD、PRD 的关系

三类文档分别回答不同层次的问题：

~~~text
BRD：为什么值得做、业务希望得到什么
  ↓
MRD：市场和用户是否存在、从哪里切入
  ↓
PRD：具体做什么、如何工作、怎样才算完成
  ↓
原型 / 技术方案 / 测试用例 / 上线复盘
~~~

它们不是固定模板，也不一定必须拆成三个独立文件。关键是业务、市场、产品、研发和测试需要的信息是否完整、前后是否可追溯。

JobPulse 的实际对应关系：

| 理论文档 | 项目中的实际文件 | 回答的问题 |
|---|---|---|
| BRD / 项目章程 | `PROJECT-CHARTER.md`、`ROADMAP.md` | 为什么做、做成什么形态、投入边界、未来如何演进 |
| MRD | `MRD.md`、`competitor-analysis.md`、`PERSONAS.md` | 市场是否存在、目标用户是谁、竞品如何解决、机会在哪里 |
| PRD | `PRD.md`、`JTBD.md` | 核心流程、功能、状态、数据、AC、风险与范围 |
| 设计说明 | PRODUCT.md、DESIGN.md、shape 系列、REDESIGN-BRIEF.md | 信息架构、页面职责、交互、视觉与响应式 |
| 技术方案 | system-architecture、database-schema、api-contract 等 | 系统如何落地、数据如何一致、接口如何协作 |
| 验收与复盘 | qa 目录、PROGRESS、TASK-PIPELINE | 是否完成、有什么问题、下一步是什么 |

### 5.2 BRD 怎么做

BRD 是 Business Requirements Document，核心不是写功能，而是明确业务问题、业务目标和投入边界。常见读者是业务负责人、决策者、项目负责人和产品负责人。

一份可用 BRD 通常包含：

1. **业务背景**：发生了什么问题，为什么现在处理。
2. **业务目标**：希望改变什么业务结果。
3. **目标对象**：谁受影响，谁使用，谁决策。
4. **业务价值**：收入、成本、效率、风险或体验价值。
5. **解决方向**：描述能力，不急于写页面按钮。
6. **范围边界**：做什么、不做什么。
7. **关键约束**：时间、预算、技术、合规和资源。
8. **成功标准**：达到什么结果继续，什么情况停止。
9. **风险与依赖**：外部数据、团队、政策和供应商。
10. **里程碑**：验证、MVP、上线和后续演进。

JobPulse 的 BRD 思路：

| BRD 要素 | 项目实践 |
|---|---|
| 业务问题 | 求职信息与进度分散，持续维护成本高 |
| 目标对象 | 高频跨平台投递者 |
| 价值 | 降低整理和状态维护成本，减少遗漏，支持复盘 |
| 当前目标 | 完成可验证、可演示的产品闭环，而非立即商业化 |
| 交付路径 | 路径 B：作品集 Demo + 演进蓝图 |
| 范围 | 聚合、状态、待办、看板、订阅 |
| 不做 | 登录、支付、简历生成、社区、自动投递、原生 App |
| 约束 | 单人维护、低成本、合规采集、外部服务可降级 |
| 成功标准 | 核心流程走通、数据完整、可重复演示、可公开部署 |
| 演进 | M0 Demo → M1 个人 SaaS → M2 Team |

具体步骤：

1. 从个人问题出发，但不把个人感受直接等同市场需求。
2. 将问题转成可以验证的业务假设：用户是否因维护成本高而漏掉节点、放弃记录或无法复盘。
3. 比较路径 A“正式 SaaS”、路径 B“作品集 Demo”和路径 C“未来上线”，按成本与目标选择路径 B。
4. 建立 IN/OUT 清单，防止营销页、AI、支付和多用户不断扩大范围。
5. 为未来能力只保留架构接缝，不提前实现。

面试表达：

> 我没有单独创建名为 BRD 的文件，但在立项决策和演进路线图中完整处理了业务问题、目标用户、价值、范围、成本、风险和里程碑。项目当前目标不是证明收入，而是先证明求职进度管理闭环是否成立。

### 5.3 MRD 怎么做

MRD 是 Market Requirements Document，目标是回答“市场、用户和竞争是否支持这个机会”。它承接 BRD 的业务方向，为 PRD 提供用户和市场证据。

MRD 常见结构：

1. 市场背景与趋势。
2. 市场规模：TAM、SAM、SOM。
3. 用户细分与优先级。
4. 用户需求、替代方案和付费意愿。
5. 竞品格局和竞争维度。
6. 市场空白与差异化。
7. 进入策略和渠道。
8. 市场、政策、数据与竞争风险。
9. 需要继续验证的关键假设。

三个规模概念：

- **TAM**：理论上所有可能服务的市场。
- **SAM**：当前产品与能力真正能够覆盖的细分市场。
- **SOM**：在明确时间、渠道和资源限制下可能获得的部分。

估算时应同时考虑：

- Top-down：从公开宏观数据逐层缩小。
- Bottom-up：用户数 × 可触达比例 × 使用或付费假设。
- 数据来源、统计口径、时间和不确定性。
- 市场规模是决策输入，不是项目业绩。

JobPulse 的 MRD 实践：

- 从大学生求职大市场收窄到互联网/科技方向，再收窄到高频跨平台投递者。
- 用“信息覆盖度 × 投递管理深度”建立竞争维度。
- 比较招聘平台、求职社区、简历工具和 Excel/Notion 等替代方案。
- 识别多源聚合、动态投递状态和个人复盘三个机会。
- 将 Excel 视为主要替代品，而不只是把 BOSS 等平台视为竞品。
- 选择“采集先行 + 演示 + 验证”的路径 B，不把作品集项目和创业冷启动混为一谈。
- 明确合规、数据源变化、用户不愿维护状态和冷启动数据不足等风险。

`MRD.md` 中的 TAM、SAM、SOM 和增长目标属于早期量级估算，并未通过真实商业运营验证。简历和面试可以讲估算方法及取舍，不能把这些数字描述成真实用户或市场结果。

面试表达：

> MRD 不是为了证明市场一定成功，而是系统整理市场规模、用户细分、竞品和替代方案。我在研究中修正了“市场没有投递管理”的过度结论，确认差异在动态状态深度，而不是功能有无；同时把市场规模数字保留为假设，没有写进项目业绩。

### 5.4 PRD 怎么做

PRD 是 Product Requirements Document，目标是把市场和用户问题转成研发、设计、测试都能理解和验收的产品要求。

PRD 不应只是页面截图或功能清单。一个功能至少需要说明：

> 用户故事 → 使用条件 → 输入 → 处理规则 → 输出 → 异常与边界 → 验收标准 → 数据与指标

标准 PRD 结构及 JobPulse 实践：

| PRD 模块 | 应回答的问题 | JobPulse 实践 |
|---|---|---|
| 文档信息 | 版本、作者、状态、修订原因 | v1→v2→v3，记录状态机与数据模型修订 |
| 产品概述 | 产品是什么、给谁、解决什么 | 招聘聚合 + 投递管理，目标为高频跨平台求职者 |
| 用户和场景 | 谁在什么情况下使用 | 行为画像、典型一天、20 条 Job Stories |
| 业务流程 | 用户如何完成核心任务 | 采集、发现、收藏、投递、状态、待办、复盘 |
| 状态与规则 | 哪些状态、允许怎样变化 | 9 状态、5 终态、纠错和多轮面试 |
| 功能需求 | 每个功能如何工作 | A 数据、B 看板、C 投递、D 订阅四模块共18个功能点 |
| 验收标准 | 怎样判断功能完成 | 功能、异常、性能和数据口径 AC |
| 非功能需求 | 性能、可用性、安全、兼容、合规 | 响应式、降级、公开来源、输入安全 |
| 数据模型 | 需要保存哪些实体和关系 | Job、Action、Application、Event 等核心实体 |
| 范围边界 | 明确不做什么 | 登录、支付、简历、社区、多租户 |
| 依赖与风险 | 什么可能导致失败 | 数据源、采集合规、AI、数据质量和维护意愿 |
| 自检 | 是否可开发、可测试、可解释 | 交付清单与面试追问 |

JobPulse PRD 的具体制作过程：

1. 将痛点和 Job Stories 映射到功能，避免凭感觉堆功能。
2. 按核心闭环组织模块，而不是按页面数量组织。
3. 先定义收藏、待投递和投递状态三个概念，解决数据语义冲突。
4. 为状态机写合法路径、非法路径、终态、纠错和多轮面试。
5. 每个功能写用户故事、输入、输出、规则、AC 和异常情况。
6. 将数据模型提前放进 PRD，避免前端概念与数据库字段不一致。
7. 加入性能、安全、合规、兼容和可用性等非功能要求。
8. 用研发、测试和数据视角反向审查是否可实现、可验证。
9. 通过 v2、v3 修订跨文档冲突，而不是把第一版当最终答案。

以“AI 招聘通知解析”为例：

| 要素 | PRD 定义 |
|---|---|
| 用户问题 | 收到通知后不愿打开系统逐项填写 |
| 用户故事 | 希望粘贴文本后快速得到状态建议 |
| 输入 | 招聘邮件或消息文本 |
| 处理 | 提取公司、岗位、状态、置信度和依据 |
| 输出 | 可编辑的预览，不自动执行 |
| 异常 | 无 Key、低置信度、未匹配、模型错误 |
| AC | 结果可修改；用户确认后才更新；失败时仍可手动操作 |
| 指标 | 解析成功率、确认率、修正率、平均更新时间 |

### 5.5 BRD、MRD、PRD 的区别与传递

| 对比 | BRD | MRD | PRD |
|---|---|---|---|
| 核心问题 | 为什么做 | 为谁做、从哪里切入 | 做什么、怎么验收 |
| 主要视角 | 业务 | 市场与用户 | 产品与交付 |
| 主要读者 | 决策者、业务负责人 | 产品、市场、运营 | 产品、设计、研发、测试 |
| 主要产出 | 目标、价值、范围、投入 | 市场、用户、竞品、机会 | 流程、功能、规则、AC、数据 |
| 失败表现 | 目标模糊、范围失控 | 伪需求、错误赛道 | 无法开发、无法测试、口径冲突 |

需求可追溯链：

> 业务问题 → 市场证据 → 用户痛点 → Job Story → 功能 → 页面/API/数据 → 测试 → 指标

JobPulse 示例：

> 跨平台进度分散 → 用户使用多个渠道 → 状态维护成本高 → 希望低成本记录通知 → AI 解析建议 → parse-email API + 确认交互 → AI/接口测试 → 解析成功率与修正率

### 5.6 用户研究怎么做

常见研究方法：

| 方法 | 适用阶段 | 解决的问题 |
|---|---|---|
| 桌面研究 | 立项前 | 行业、公开行为、替代方案和竞品 |
| 深度访谈 | 问题发现 | 用户为什么这样做、真实障碍是什么 |
| 问卷 | 已有明确假设 | 行为比例、偏好和分群 |
| 可用性测试 | 有原型后 | 用户能否完成任务、卡在哪里 |
| 行为数据 | 上线后 | 用户实际如何使用、在哪流失 |
| 客服/反馈分析 | 运营期 | 高频问题、异常和改进方向 |

访谈不应该问“你想不想要这个功能”，而应询问最近发生过的真实行为：

1. 最近一次同时使用多个招聘平台是什么时候？
2. 当时如何保存岗位，为什么采用这种方式？
3. 最近一次漏掉或忘记测评/面试是怎样发生的？
4. 现在如何维护状态，最麻烦的一步是什么？
5. 最近一次复盘投递结果时看了什么信息？
6. 如果没有这个工具，现有替代方案是什么？

JobPulse 当前已经完成桌面研究、自身场景记录、6 个主要竞品分析、19 条国内外公开求职记录的人工编码，以及 4 类行为角色的专家模拟走查。公开材料和模拟走查不等于访谈，也不能用于推断人群比例；当前画像因此统一称为 Proto-Persona。项目尚未完成计划中的 3 次首轮探索性访谈，面试时必须区分“已观察的公开行为”“专家走查结果”“由此形成的产品假设”和“待验证的用户效果”。

下一步研究方案：

- 招募符合行为条件的高频跨平台投递者。
- 完成 3 次首轮半结构化访谈，验证维护方式、频率、放弃原因和替代工具；若持续出现新主题，再扩展至 7 人。
- 用 5 人执行“发现岗位—创建投递—更新通知—查看待办—完成复盘”可用性任务。
- 邀请 3—5 人进行 7 天轻量试用，验证真实环境中的持续更新意愿。
- 记录完成率、耗时、错误、求助和主观负担。
- 根据证据修改画像、优先级和流程。

访谈提纲、任务脚本、指标口径与通过阈值见 [用户验证计划](../research/user-validation-plan.md)。

### 5.7 用户画像与用户分群

用户分群是用可观察特征区分人群；Persona 是把某一重要分群具体化，帮助团队理解行为、目标和场景。当前没有访谈样本，因此 JobPulse 文档中的画像属于 Proto-Persona：行为条件可用于招募和设计假设，未验证的人口属性、动机和使用频率不能写成事实。

常见分群维度：

- 人口属性：年龄、职业、地区。
- 行为：使用频率、渠道数、任务量。
- 价值：收入、付费、贡献。
- 生命周期：新用户、活跃、沉默、流失。
- 需求：效率、风险、成长或情绪需求。

JobPulse 使用行为分群，而不是只用“大学生”“应届生”：

- 核心画像：跨 3 个以上渠道、月投递 20 个以上的高频用户。
- 次要画像：岗位数量少但匹配要求高的定向实习用户。
- 延伸场景：招聘季结束后的复盘。

这样做的原因是渠道数量和投递规模直接决定管理复杂度，更能解释用户为什么需要产品。

### 5.8 JTBD、User Story、Job Story 和 AC

| 工具 | 典型格式 | 用途 |
|---|---|---|
| JTBD | 用户雇佣产品完成什么进步 | 理解真实任务和动机 |
| Job Story | 当……时，我想……以便…… | 强调情境、动机和结果 |
| User Story | 作为……我希望……以便…… | 将需求交给产品和研发 |
| AC | Given / When / Then 或检查项 | 判断功能是否完成 |

JobPulse 示例：

- Job Story：当我同时收到多个公司的通知时，我想快速记录状态和时间，以便不遗漏下一步。
- User Story：作为高频求职者，我希望粘贴通知文本并获得状态建议，以便减少手动录入。
- AC：未配置 API Key 时仍返回规则建议；解析结果不自动修改状态；用户确认后生成状态事件。

四者不能互相替代：JTBD 决定为什么做，User Story 决定为谁做什么，AC 决定完成的客观标准。

### 5.9 需求优先级怎么做

常见方法：

| 方法 | 适用情况 | 核心维度 |
|---|---|---|
| P0/P1/P2 | 小团队、MVP、快速对齐 | 对核心闭环的重要程度 |
| MoSCoW | 交付范围协商 | Must / Should / Could / Won't |
| RICE | 候选需求较多且有数据 | Reach × Impact × Confidence ÷ Effort |
| Kano | 体验和满意度研究 | 基础、期望、兴奋、无差异 |
| 价值—成本矩阵 | 早期粗排 | 用户价值与实现成本 |

JobPulse 选择 P0/P1/P2，因为个人 Demo 缺乏可信 Reach、Impact 和满意度数据，强行使用 RICE 或 Kano 会制造伪精确。

优先级判断问题：

1. 没有它，核心任务还能完成吗？
2. 它是否验证核心用户假设？
3. 是否依赖尚未稳定的数据或外部服务？
4. 实现和维护成本是否超过当前阶段价值？
5. 是否可以人工或规则方式降级？
6. 是否引入账号、支付、隐私或合规等新复杂度？

示例：

| 需求 | 决策 | 理由 |
|---|---|---|
| 状态更新 | P0 | 没有它就没有投递管理 |
| 近期待办 | P0 | 直接解决遗漏节点 |
| 基础漏斗 | P1 | 有价值，但小样本解释力有限 |
| 个性化订阅 | P1 | 增强岗位发现，不是状态主链路 |
| 简历匹配 | P2 / 不做 | 进入另一条产品线，范围和成本过大 |
| 支付 | P2 / 不做 | 尚未验证使用和付费 |

### 5.10 MVP 与路线图怎么做

MVP 不是“功能很少”，而是用最小成本验证最关键的价值假设。

JobPulse 的核心假设：

> 如果把跨平台岗位、投递状态和近期安排连接起来，并降低状态维护成本，高频求职者会更稳定地维护和复盘求职进度。

M0 Demo 验证产品闭环和实现可行性；M1 只有在真实用户验证后才进入个人 SaaS；M2 才考虑团队、机构和协作能力。

路线图不应只列功能日期，应包含：

- 阶段目标和要验证的结果；
- 进入下一阶段的触发条件；
- 能力增量；
- 数据、技术和运营依赖；
- 明确延后的范围；
- 停止或调整条件。

JobPulse 路线图将“真实 SaaS 能力”作为触发式演进，而不是默认一定开发。例如只有当用户持续维护状态并愿意长期使用时，才投入账号隔离、数据库迁移和受控调度。

### 5.11 信息架构、原型与交互设计

信息架构回答“内容和任务如何组织”；原型回答“用户如何完成任务”；视觉设计回答“信息如何被快速理解”。

具体流程：

1. 从核心任务流而不是数据库表设计导航。
2. 为每个页面定义首要问题和关键动作。
3. 先画低保真流程和异常分支，再进入高保真。
4. 建立页面、组件、状态和数据的对应关系。
5. 同时设计空、错、加载、权限、重复操作和移动端。
6. 用真实数据与真实操作视频验收，不用假仪表盘掩盖流程问题。

JobPulse 把看板、岗位、收藏与待投递、投递、待办和订阅按用户任务组织；将采集降级为系统工具；将官网、后台和案例分为三个表面，避免营销叙事和高密度操作界面互相干扰。

### 5.12 需求管理、项目推进和验收

产品经理交付的不只是 PRD，还要保证需求从提出到上线不丢失、不变形。

需求管理闭环：

> 收集 → 澄清 → 评估 → 排序 → 评审 → 拆解 → 实现 → 验收 → 上线 → 复盘

JobPulse 的具体做法：

- 用 PROGRESS 维护当前事实源。
- 用 TASK-PIPELINE 管理依赖和阶段状态。
- 用 BLOCKED-LIST 记录外部输入和阻塞。
- 用版本说明记录 PRD、架构和设计的修订原因。
- 用 AC 和自动化测试将需求转成可验证条件。
- 用 Demo 重置和演示路径完成 UAT 式验收。
- 用部署与 QA 文档记录实际环境、风险和回滚准备。

项目没有正式 Scrum 团队，因此不应声称主持 Sprint。更准确的说法是采用阶段门禁和任务流水线：一个阶段达到文档、实现和测试标准后再进入下一阶段。

评审时重点检查：

- 需求是否对应真实问题；
- 业务规则和术语是否一致；
- 是否存在异常、空状态和权限边界；
- 数据是否足以支持页面和指标；
- 开发是否能实现；
- 测试是否能客观判断通过；
- 新需求是否改变原有范围和成本。

### 5.13 为什么使用状态机

普通标签只描述“现在是什么”，状态机同时定义“可以从哪里到哪里”。求职流程存在不可逆进展、终态、多轮面试和纠错需求，因此需要明确流转规则。

9 个投递状态：

1. 已投递 applied
2. 测评笔试 test
3. 面试中 interviewing
4. Offer 待决定 offer_pending
5. Offer 已接受 offer_accepted
6. Offer 已婉拒 offer_declined
7. 公司拒绝 rejected
8. 无回应关闭 no_response
9. 主动撤回 withdrawn

5 个终态为 Offer 已接受、Offer 已婉拒、公司拒绝、无回应关闭和主动撤回。终态不能常规回流；如果录错，必须走纠错流程并填写原因。

### 5.14 为什么状态与事件分开

Application.status 用于快速回答“当前处于什么状态”；ApplicationEvent 用于回答“过去发生了什么”。

如果只保存当前状态：

- 无法知道是否曾进入测评或面试；
- 无法形成准确漏斗；
- 无法支持多轮面试；
- 无法记录纠错；
- 无法从计划时间生成待办。

因此状态更新和事件写入必须在同一事务中，要么全部成功，要么全部回滚。

### 5.15 漏斗为什么按事件计算

漏斗统计的是“曾到达该阶段的独立投递数”，而不是当前状态分布。

例如某条投递已经进入面试，它仍然应该计入“已投递”和“测评”阶段。系统从非纠错的 status_change 事件中按 application_id 去重统计，避免后续状态覆盖历史阶段。

### 5.16 为什么设置无回应关闭

大量投递不会收到明确拒绝。如果系统只有“进行中”和“拒绝”，用户会积累大量永久悬空记录。no_response 让用户主动结束长期无反馈机会，同时与公司明确拒绝区分，便于复盘渠道质量。

### 5.17 为什么 AI 只给建议

招聘通知可能存在歧义、Prompt 注入、岗位匹配错误和模型幻觉。直接自动更新会污染关键记录，所以采用 Human-in-the-loop：

> AI 解析 → 展示建议、置信度和依据 → 用户确认 → 状态机校验 → 写入事件

### 5.18 成功指标如何设计

当前没有真实运营用户，因此不虚构 DAU、留存或商业转化。现阶段指标分为：

- **数据质量**：JD 完整率、投递链接完整率、要求字段覆盖率、重复采集新增数。
- **流程质量**：核心任务是否走通、非法流转是否被拒绝、重置是否可重复。
- **交付质量**：自动化测试、Lint、构建、HTTP 和线上验收。
- **未来用户指标**：首次整理完成率、每周状态更新率、待办按时完成率、周复盘率。

### 5.19 产品经理需要掌握的技术知识

产品经理不一定亲自编码，但需要理解技术概念对需求、成本、风险和体验的影响。

| 技术知识 | 产品经理需要理解什么 | JobPulse 实践 |
|---|---|---|
| 前后端分离 | 页面与业务服务如何通信，失败如何反馈 | Next.js 通过 REST API 调用 FastAPI |
| HTTP / REST | GET/POST/PUT/DELETE、状态码、分页、幂等与错误 | 32 个 API，统一 data/error envelope |
| JSON 与 Schema | 输入输出字段、类型、必填和枚举 | Pydantic + TypeScript 类型 |
| 关系数据库 | 实体、关系、主外键和范式 | 7 张表拆分岗位、动作、投递和事件 |
| 索引与约束 | 查询性能与数据一致性 | 唯一索引、部分索引、CHECK |
| 事务 | 多步操作要么都成功、要么都失败 | 状态更新与事件写入原子提交 |
| 状态机 | 合法流转、终态、回退和纠错 | 9 状态、5 终态、多轮面试 |
| 事件数据 | 当前值与历史事实的差异 | Application + ApplicationEvent |
| 缓存 | 性能、时效、一致性和隐私 | AI 结果 1 小时 TTL、哈希键 |
| 限流与重试 | 防止滥用、雪崩和外部依赖故障 | 采集按来源限流、AI 每分钟10次 |
| 数据采集 | API、网页解析、字段变化和合规 | Greenhouse API、robots fail-closed |
| AI / LLM | Prompt、结构化输出、幻觉、置信度和降级 | 0.7 阈值、本地规则、人工确认 |
| 安全 | CORS、鉴权、隐私、密钥和权限 | 精确 CORS、无密钥、公开版禁采集 |
| 部署 | 环境变量、持久化、日志和成本 | Sites + Railway + SQLite 卷 |
| 测试 | 单元、接口、约束、端到端和 UAT | 120 自动化测试 + 浏览器验收 |

遇到技术方案时，产品经理至少应追问：

1. 这个方案解决的是功能、性能、成本还是风险问题？
2. 输入输出、异常和降级路径是什么？
3. 数据从哪里来，能否追溯，如何保证一致？
4. 并发、超时、重试、重复提交会发生什么？
5. 是否需要收集个人数据或调用第三方服务？
6. 如何监控，如何回滚，出现问题用户还能做什么？
7. 当前实现是 Demo 方案还是生产方案，迁移成本是什么？

### 5.20 BRD、MRD、PRD 面试回答模板

**问：你是怎么做 BRD 的？**

> 我先明确业务问题不是“缺一个岗位网站”，而是跨平台求职进度维护成本高；再定义目标用户、价值、项目形态和成功条件。考虑到项目目标是求职作品集且没有商业团队，我选择 Demo 路径，并通过 IN/OUT 边界排除支付、多租户和简历产品线。对应产出是立项决策和演进路线图。

**问：你是怎么做 MRD 的？**

> 我从市场背景、用户细分、竞品和替代品四个方向研究。除 BOSS、牛客等直接竞品外，也分析 Excel、Notion 和简历工具。我最重要的修正是承认部分产品已有投递追踪，因此机会不是“市场没有”，而是动态状态、待办和复盘深度不足。市场规模只作为量级假设，没有包装成真实业绩。

**问：你是怎么做 PRD 的？**

> 我先从痛点和 Job Stories 建立需求映射，再定义收藏、待投递和投递状态的概念边界，之后写核心流程、9 状态机和四个功能模块。每个功能包含用户故事、输入、处理、输出、异常和 AC，并同步数据模型、非功能要求、风险和不做清单。PRD 经历多轮修订，重点解决了状态口径、Offer 字段和事件数据冲突。

**问：PRD 写完以后怎么保证落地？**

> 我把 PRD 的 AC 继续映射到 API、数据库约束和测试。比如“同一岗位只能有一个进行中投递”同时有接口校验、部分唯一索引和自动化测试；“AI 不自动改状态”由解析 API 与 transition API 分离，并测试解析不写事件。这样需求、实现和验收形成闭环。

### 5.21 指标体系、北极星指标、OKR 与 KPI

指标需要从目标推导，而不是因为数据可采集就展示。

常见指标层级：

| 层级 | 回答的问题 | 示例 |
|---|---|---|
| 业务结果 | 产品是否创造业务价值 | 收入、成本、续费、风险损失 |
| 用户价值 | 用户是否完成关键任务 | 完成率、成功率、节省时间 |
| 产品行为 | 用户如何使用功能 | 激活、留存、频率、路径转化 |
| 功能效果 | 某能力是否有效 | 解析成功率、提醒完成率 |
| 质量护栏 | 是否以错误方式增长 | 错误率、投诉、延迟、误操作 |

常见框架：

- **North Star Metric**：最能代表用户持续获得核心价值的一个指标。
- **OMTM**：当前阶段唯一最重要指标，随着阶段变化。
- **AARRR**：获取、激活、留存、收入、推荐，适合增长链路。
- **HEART**：愉悦、参与、采用、留存、任务成功，适合体验评估。
- **OKR**：Objective 定方向，Key Results 描述可衡量结果。
- **KPI**：长期或岗位需要持续监控的关键绩效指标。

JobPulse 当前仍处于 Demo 与验证前阶段，因此不应把 DAU 或收入设为核心指标。

建议的阶段指标：

| 阶段 | OMTM | 配套指标 |
|---|---|---|
| Demo 交付 | 核心演示任务通过率 | 数据完整率、错误率、测试与构建 |
| 可用性验证 | 用户独立完成核心流程的比例 | 完成时间、错误、求助次数 |
| 小规模使用 | 每周持续维护求职进度的用户比例 | 状态更新率、待办完成率、周复盘率 |
| 商业验证 | 核心活跃用户的付费转化 | 留存、续费、获客成本、服务成本 |

未来可候选的北极星指标：

> 每周完成至少一次有效状态更新或待办处理，并查看进展复盘的活跃用户数。

它同时包含记录行为和获得反馈，优于单纯统计投递数量，因为产品不鼓励无效海投。

OKR 示例：

- **O**：验证 JobPulse 是否能帮助高频求职者持续维护求职进度。
- **KR1**：5 名可用性测试用户中至少 4 名独立完成核心流程。
- **KR2**：核心流程中位完成时间低于 5 分钟。
- **KR3**：连续两周仍更新状态的测试用户比例达到预设门槛。
- **KR4**：关键状态误操作率和数据丢失为 0。

这些是未来验证目标，不是当前已经达成的项目结果。

### 5.22 利益相关方与跨部门协作

正式产品项目常见利益相关方包括业务、用户、研发、设计、测试、运营、市场、销售、客服、法务、财务和管理层。产品经理需要理解每一方的目标、影响力和信息需求。

常见工具：

- **Stakeholder Map**：按影响力和关注度确定沟通方式。
- **RACI**：Responsible 执行、Accountable 最终负责、Consulted 被征询、Informed 被告知。
- **Decision Log**：记录选择、备选方案、理由和日期。
- **RAID Log**：Risks、Assumptions、Issues、Dependencies。
- **需求评审**：业务价值、产品逻辑、技术可行性和验收标准共同确认。

JobPulse 是个人项目，不存在真实企业跨部门团队，因此不能把 AI 工具描述成研发或设计同事。但项目采用了类似的协作控制：

| 协作需求 | 项目做法 |
|---|---|
| 信息同步 | PROGRESS 单一事实源 |
| 决策追踪 | PROJECT、REDESIGN-BRIEF 和版本说明 |
| 任务依赖 | TASK-PIPELINE |
| 风险与阻塞 | BLOCKED-LIST、部署与 QA 记录 |
| 质量责任 | 自动化测试、构建和浏览器验收 |
| 变更控制 | 用户反馈 → 问题定位 → 文档/实现修改 → 回归验收 |

面试时可以强调“具备跨角色思考和交付协调能力”，但不要声称“管理跨部门团队”。如果进入正式团队，下一步会用 RACI 明确负责人，用评审纪要和决策日志管理变更。

### 5.23 产品生命周期与迭代

典型产品生命周期：

1. **Discovery**：发现问题、研究市场和用户。
2. **Definition**：明确目标、范围、需求和成功标准。
3. **Design**：流程、信息架构、原型和体验。
4. **Delivery**：研发、测试、验收和上线。
5. **Growth**：激活、留存、传播和商业化。
6. **Maturity**：效率、稳定性、平台化和成本优化。
7. **Retirement**：功能下线、数据迁移和用户沟通。

JobPulse 已完成 Discovery 到 Delivery 的主要工作，并完成公开 Demo 上线；尚未进入真实 Growth。当前最合理的下一步不是继续增加功能，而是回到 Discovery，用访谈和行为验证确认核心假设。

迭代闭环：

> 假设 → 最小方案 → 数据/反馈 → 判断 → 保留、修改或停止

本项目的实际迭代示例：

- 假设招聘平台可以提供足够数据 → 发现受限平台风险和字段不足 → 转向公开 ATS。
- 初版仅强调岗位与看板 → 发现收藏、待投递和投递概念混乱 → 重构三层状态。
- 初版营销视频持续播放 → 用户反馈干扰页面 → 调整播放规则并删除无意义装饰。
- 早期架构规划较多依赖 → 实现阶段收敛到原生 Fetch 和公开 API → 降低部署风险。

这比“按既定方案完成所有功能”更能体现产品经理根据证据迭代的能力。

### 6.4 数据库设计

| 表 | 核心职责 |
|---|---|
| Job | 岗位、JD、要求、官方链接、来源、分类和有效性 |
| UserJobAction | 收藏与待投递；通过 ended_at 保留结束记录 |

| ApplicationEvent | 状态历史、面试、测评、材料、Offer、备注和纠错 |

关键约束：

- Job 使用 source + company + title + location 唯一索引避免同源重复。
- Application 使用部分唯一索引，保证同一岗位同时只有一个非终态投递。
- 所有枚举在数据库中存英文 code，由应用层显示中文。
- CHECK 约束限制岗位、投递、事件、操作和采集状态。
- 待办、漏斗和纠错使用部分索引减少无效扫描。

### 6.5 状态流转事务

状态更新流程：

1. 在事务内读取 Application。
2. 校验目标状态是否在 TRANSITIONS 中。
3. 纠错时要求 correction_reason。
4. 更新 Application.status 和 updated_at。
5. 同事务写入 ApplicationEvent。
6. 成功后统一提交；任一步失败则回滚。

SQLite 不支持 SELECT FOR UPDATE 行级锁，因此 Demo 使用数据库事务与应用层校验；如果迁移到 PostgreSQL，再引入行锁或乐观版本号处理高并发。

创建投递时也使用同一事务：

- 创建初始状态 applied；
- 写入初始 status_change 事件；
- 结束对应 to_apply 记录；
- 保留 favorite 状态。

### 6.6 REST API

实际实现 32 个业务端点，统一使用 /api/v1 前缀：

| API 组 | 代表能力 |
|---|---|
| Jobs | 搜索筛选、统计、详情、新建、核验、收藏、待投递 |
| Applications | 列表、创建、库外补录、详情、流转、批量流转、事件、邮件解析 |
| Dashboard | KPI、累计漏斗、有效进展趋势、分布 |
| Todo | 未来 N 天的面试、测评和材料待办 |
| Subscriptions | 查询、新建、编辑和删除 |

### 6.7 采集与数据处理

真实数据链路：

~~~mermaid
flowchart LR
    A[来源配置] --> B[Greenhouse API 适配器]
    B --> C[限流与重试]
    C --> D[HTML 转纯文本]
    D --> E[字段提取与规范化]
    E --> F[同源/跨源精确去重]
    F --> G[批量写入 SQLite]
    G --> H[采集日志与链接核验]
~~~

实际启用 Figma、Webflow、Intercom 和 Stripe 四个公开 Greenhouse Job Board 来源。API 无需登录，并返回公开发布岗位。

字段处理：

- BeautifulSoup + lxml 将 JD HTML 转为可读文本。
- 按明确标题提取 Requirements、Qualifications、Who you are 等要求段落。
- 使用规则提取薪资、学历、经验、岗位分类、发布时间和截止时间。
- 公司与地点做别名、后缀和空格规范化。

去重策略：

- 同源：规范化后的公司、岗位、地点精确相等。
- 跨源：同样只允许三字段精确相等。
- 禁止 substring 模糊合并，避免把相似但不同的岗位误合并。
- 合并时只补齐缺失字段，不覆盖已有字段。

合规与稳定性：

- 普通网页采集使用 robots fail-closed；无法确认允许时默认不采集。
- BOSS、牛客等受限来源默认关闭，不绕过登录、验证码或反爬。
- 按来源限流，并使用有限次数指数退避。
- 大批量数据分批提交，避免 SQLite 长事务锁库。
- 公开线上版本关闭匿名采集触发，接口返回 403。
- 岗位核验通过官方链接 HEAD 状态更新 is_valid、status 和 last_verified_at。

### 6.8 AI 招聘通知解析

输入不是邮箱账号，而是用户主动粘贴的一段招聘通知文本。

输出字段：

- parsed
- company
- title
- suggested_status
- confidence
- degraded
- matched_application_id
- reasoning

处理流程：

1. 空文本直接返回无法解析。
2. 对文本计算哈希并查询 1 小时 TTL 缓存，缓存不保存原文键。
3. 无 API Key 时直接走正则。
4. 每分钟超过 10 次时降级正则。
5. LLM 调用设置 5 秒超时，并要求 JSON Object 输出。
6. 非法 JSON、非法状态、异常或低于 0.7 置信度时降级正则。
7. 正则仍无法识别时返回 parsed=false。
8. 只有唯一匹配到某条投递时才返回 matched_application_id。
9. 解析端点不写事件、不修改状态；用户确认后另行调用 transition。

线上没有配置 OpenAI、DeepSeek 或邮件服务密钥，实际走免费本地规则路径。

## 七、面试介绍话术

### 7.1 30 秒版本

我从自己的跨平台求职场景出发，设计并上线了 JobPulse 招聘信息聚合与投递管理产品。我编码 19 条国内外公开求职记录并研究 6 个竞品，将机会聚焦到降低状态维护成本；随后完成需求分级、PRD、9 状态流程和指标设计，并推进数据、前后端、AI 降级、120 项测试及公开部署，形成可以现场操作的 SaaS Demo。当前证明的是产品闭环和交付质量，真实用户效果仍待验证。

### 7.2 90 秒版本

我做了一个叫 JobPulse 的招聘信息聚合与投递管理产品。问题来自真实求职场景：用户同时使用多个平台，岗位信息分散，而且投递后的测评、面试和 Offer 还要靠表格、邮件和聊天记录维护。

我先人工编码 19 条国内外公开求职记录并研究 6 个同类产品。公开行为显示，一些求职者会用表格、Notion、飞书或 Google Sheets 记账，但维护容易中断，通知和日程仍然分散。因此我没有把方向停留在岗位聚合，而是聚焦“降低状态维护成本”，整理 20 条 Job Stories，并用 P0、P1、P2 控制 MVP 范围。产品上，我把收藏、待投递和已投递拆开，设计 9 状态流程，通过事件时间线支持多轮面试、纠错、待办和累计漏斗；AI 只给建议，用户确认后才更新状态。

在落地阶段，我推进了数据、前端、后端、测试和部署。针对初版岗位少且缺完整 JD 和官方链接的问题，项目转向 4 个企业公开 ATS 来源，本地验收 56 条岗位，JD 和官方投递链接完整率达到 100%；同时落地 32 个业务 API、7 张数据表和 120 项测试，并将官网、后台和案例页部署成公开 Demo。

项目目前仍是共享演示产品，没有虚构商业用户和增长结果。如果继续迭代，我会先通过真实用户测试验证状态更新频率和每周复盘率，再决定是否投入账号隔离、定时采集和通知。

### 7.3 三分钟结构

1. **背景**：跨平台求职信息和进度分散。
2. **研究**：19 条国内外公开求职记录、竞品、JTBD、用户行为分群与证据分级。
3. **取舍**：聚焦岗位、状态、待办、复盘；不做简历、社区、支付。
4. **方案**：收藏与待投递分离、9 状态、事件时间线。
5. **实现**：公开 ATS、FastAPI、SQLite、Next.js、AI 降级。
6. **验证**：56 条岗位、100% JD/链接、26 项专家模拟走查、120 项测试和线上闭环。
7. **反思**：没有真实用户指标；下一步先做小规模验证。

### 7.4 八分钟现场演示顺序

1. 官网：用 30 秒说明问题和价值。
2. 岗位页：筛选一个岗位，打开完整 JD 和官方链接。
3. 收藏与待投递：解释两个意图为什么分开。
4. 创建投递：观察待投递标记结束。
5. 投递详情：从已投递推进到测评或面试，展示事件时间线。
6. AI 解析：粘贴通知，强调“只建议、不自动执行”。
7. 待办：查看未来测评和面试。
8. 看板：解释累计漏斗和有效进展趋势。
9. 案例页：总结取舍、验证和未来计划。

| 用户需求是否经过访谈验证？ | 尚未。当前已人工编码 19 条国内外公开求职记录、研究 6 个竞品并完成 4 类角色模拟走查，这能支持既有行为、替代方案和产品缺口判断，但不能替代访谈或证明问题比例；下一步完成 3 次首轮访谈、5 次可用性测试和 3—5 人的 7 天试用。 |
| 最大的产品取舍是什么？ | 不做简历生成、AI 匹配、社区和支付，集中验证状态维护主链路。 |
| 为什么收藏和待投递要分开？ | 收藏是信息价值判断，待投递是行动承诺；混合会让清单失去优先级意义。 |
| 为什么有 9 个状态？ | 覆盖主要求职进度、Offer 决策和三种关闭原因，同时保持可解释性。 |
| 为什么需要无回应关闭？ | 解决长期悬空记录，并区分平台无反馈和明确拒绝。 |
| 如何定义 MVP 成功？ | 核心闭环可用、数据完整、状态可追溯、外部服务失败不阻断；真实用户效果留待验证。 |
| 如果只能保留一个功能？ | 保留投递状态 + 事件时间线，因为岗位可手动录入，但历史进度无法靠静态标签还原。 |
| 如何规划商业化？ | 当前不验证付费；长期可围绕自动同步、提醒和数据复盘探索个人订阅，但先验证使用频率。 |
| 你如何避免范围蔓延？ | P0/P1/P2、IN/OUT 边界和七阶段验收门禁；新需求先判断是否验证核心假设。 |

### 8.2 数据与运营问题

| 问题 | 回答重点 |
|---|---|
| 为什么漏斗不用当前状态统计？ | 当前状态会覆盖历史阶段；漏斗必须用事件判断“曾到达”。 |
| 如何保证漏斗不重复？ | 按 application_id distinct，并排除 correction 事件。 |
| 有哪些数据指标？ | JD/链接完整率、去重结果、流程通过率、投递累计到达、有效进展和待办完成。 |
| 为什么没有 DAU、留存？ | 尚未进行真实用户运营，不能虚构；当前先用交付和数据质量指标。 |
| 数据从哪里来？ | 24 条确定性演示快照 + 4 个企业公开 Greenhouse ATS 的 32 条真实岗位。 |
| 如何处理重复岗位？ | 规范化公司和地点后，对公司、岗位、地点精确匹配；不做 substring 模糊合并。 |
| 为什么去重不使用语义模型？ | 样本小且误合并成本高；精确规则可解释，语义去重应先积累标注数据再评估。 |
| 产品运营下一步做什么？ | 完成 3 次首轮访谈、5 次可用性测试和 3—5 人的 7 天试用，跟踪任务成功率、维护耗时、周更新率和周复盘率；若访谈持续出现新主题，再扩展样本。 |

### 8.3 技术问题

| 问题 | 回答重点 |
|---|---|
| 为什么选择 FastAPI？ | Pydantic 校验、OpenAPI、Python 数据采集生态和快速 Demo 交付。 |
| 为什么使用 SQLite？ | 单用户 Demo、零配置、低成本；通过 SQLAlchemy 保留 PostgreSQL 迁移路径。 |
| SQLite 有什么限制？ | 并发写入、行锁和规模有限；正式多用户版迁移 PostgreSQL。 |
| 如何保证状态与事件一致？ | 同一数据库事务内更新 Application 并写 ApplicationEvent。 |
| 同一岗位能重复创建投递吗？ | 同一岗位同时只允许一个非终态投递，由应用校验和部分唯一索引双重保证。 |
| 为什么使用事件表？ | 支持历史、漏斗、多轮面试、纠错、待办和审计。 |
| 32 个 API 如何组织？ | 按 Jobs、Applications、Dashboard、Todo、Subscriptions、Crawler、Demo 分组。 |
| 采集为什么选 Greenhouse？ | 公开 JSON API、无需登录、数据权威、JD 与官方链接完整，合规和稳定性优于受限平台。 |
| robots fail-closed 是什么？ | 无法确认 robots 明确允许时默认禁止采集，避免不确定情况下继续请求。 |
| AI 如何避免幻觉？ | 固定结构输出、状态白名单、0.7 阈值、异常降级、人工确认和状态机二次校验。 |
| 为什么无 API Key 还能演示？ | 核心价值不依赖 LLM；本地正则可以提供低置信度建议，失败也不阻断手动更新。 |
| 为什么早期架构和最终技术不同？ | 早期方案包含更多库；实现阶段按 Demo 范围收敛依赖，用公开 API 和原生 Fetch 降低维护成本。 |
| 如何测试？ | 120 项测试覆盖业务规则、数据库约束、采集、AI、API、演示数据和部署配置，并用 26 项专家模拟走查验证端到端产品路径。 |
| 如何上线？ | Codex Sites 承载前端，Railway Docker 承载 FastAPI，SQLite 使用持久化卷。 |
| 正式商业化需要改什么？ | OAuth、用户隔离、PostgreSQL、RBAC、受控调度、监控、费用上限、隐私政策和备份。 |

## 九、可使用的 STAR 案例

### 9.1 数据不足与字段缺失

**S**：初版后台岗位数量少，而且缺少完整 JD 和投递链接，无法形成可信产品体验。

**T**：在不绕过登录、验证码或反爬的前提下补足真实、可追溯的数据。

**A**：评估招聘平台和企业 ATS，选择公开 Greenhouse API；实现适配器、字段提取、规范化、精确去重、日志与核验，并设置数据完整度指标。

**R**：接入 4 个公开来源和 32 条真实岗位，本地共验收 56 条数据，JD 与官方投递链接完整率达到 100%。

### 9.2 状态机口径纠正

**S**：早期方案存在状态数、Offer 结果和终态口径不一致，直接实现会导致 API、数据库和看板冲突。

**T**：统一产品、数据和接口口径，并保证漏斗可追溯。

**A**：重构为 9 状态、5 终态，删除重复的 offer_result 字段，引入 ApplicationEvent，明确终态纠错和事件排除规则。

**R**：形成统一状态契约，状态流转、漏斗、待办和纠错均有自动化测试覆盖。

### 9.3 营销页视频体验优化

**S**：官网视频持续自动播放，与页面元素重叠，装饰曲线缺少明确含义。

**T**：保留真实产品动态展示，同时减少视觉干扰。

**A**：区分主视频和辅助视频：主视频增加停止并恢复静态页面，辅助视频改为鼠标悬停播放；删除无业务含义曲线。

**R**：官网展示层级更清晰，视频交互与完整演示通过验收。

### 9.4 公开部署的成本与安全

**S**：项目需要公开体验，但共享数据、匿名采集、付费 API 和托管费用都可能带来风险。

**T**：在零付费 API 的前提下形成可演示部署，并控制外部写入。

**A**：前后端分离部署，Railway 挂载持久化卷，配置精确 CORS，关闭匿名采集触发，不配置 LLM 与邮件密钥，并记录免费试用到期风险。

**R**：官网和 API 公开可用，线上收藏、创建投递、CORS、采集保护和重置流程验收通过。

### 9.5 从公开证据修正产品方向

**S**：早期需求主要来自个人经历与竞品分析，虽然能提出问题，但不足以说明其他求职者是否存在相同行为，也容易把“岗位分散”写成过宽的机会。

**T**：在没有现成访谈对象的情况下，补充可追溯的用户侧证据，同时明确公开材料的证据边界。

**A**：人工编码 19 条国内外公开求职记录，按场景、既有做法、触发问题、结果和证据强度整理；将表格、Notion、飞书、Google Sheets 等视为直接替代品，并区分“公开行为事实”“产品推断”和“仍需访谈验证的假设”。

**R**：确认手工建账、记录中断、通知与日程分散是值得继续验证的行为线索，将产品方向从泛化的岗位聚合收敛到“降低状态维护成本”，并形成 3 次首轮访谈、5 次可用性测试和 7 天试用计划；尚未把这些结果表述为用户规模或使用效果。

## 十、不能夸大的内容

面试时主动保持以下边界：

| 不应表述 | 正确表述 |
|---|---|
| 完成大量真实用户访谈 | 已人工编码 19 条国内外公开求职记录并形成假设；3 次首轮探索性访谈仍待完成 |
| 用户画像来自真实访谈 | 当前为行为分群和 Proto-Persona，未验证的人口属性与动机只是假设 |
| 提升用户留存或转化率 | 当前验证数据完整度、流程和交付质量，暂无真实运营指标 |
| 带领研发、设计团队 | 以个人项目负责人拆解任务，使用 AI 工具辅助并独立评审验收 |
| 搭建大模型或 Agent | 接入可选 OpenAI 兼容接口并设计结构化解析与降级 |
| 爬取 BOSS、牛客大量数据 | 受限平台默认关闭，真实数据来自公开 Greenhouse API |
| 正式商业化 SaaS | 公开共享 Demo，未实现账号、支付、多租户和商业运营 |
| 邮件自动同步 | 用户粘贴通知文本后解析，不收发邮件 |
| 永久零成本运行 | 当前使用免费试用，额度或政策变化可能导致服务暂停 |
