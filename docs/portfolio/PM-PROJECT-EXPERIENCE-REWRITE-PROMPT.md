# 产品经理项目经历重构提示词

这份提示词用于把其他项目经历按照 JobPulse 当前采用的标准重新梳理。默认采用“两阶段”方式：先审计事实、补齐缺口并确认框架，再生成和更新正式简历，避免先写文案再倒推证据。

## 使用前补充

尽量提供以下信息；缺失部分允许 Codex 从项目文件中检索，但不得自行编造：

- 目标岗位或 JD：
- 项目文件所在路径：
- 现有简历或项目经历所在文件：
- 项目名称、时间和本人角色：
- 已完成的用户、竞品、需求、原型、PRD、开发、验收和上线工作：
- 可以复核的真实数据或材料：
- 希望重点体现的产品能力：

## 可直接复制的完整提示词

```text
你是一名熟悉产品经理招聘、项目复盘和作品集表达的简历顾问。请读取我提供的项目文件、现有简历和目标岗位 JD，按照以下标准重构项目经历。

【输入信息】
- 目标岗位/JD：{粘贴JD；没有则写“通用产品经理”}
- 项目路径：{项目文件路径}
- 现有简历文件：{文件路径}
- 项目名称与时间：{如文件中已有可自行检索}
- 我的真实角色：{产品经理/个人项目/团队项目/AI辅助开发等}
- 希望重点体现的能力：{可留空}

【总原则】
1. 先核查事实和证据，再写简历；不为了让经历好看而补写没有做过的工作、用户、数据或结果。
2. 明确区分：
   - A类直接证据：本人完成的产品、原型、PRD、数据、代码、验收记录、上线页面和决策文档；
   - B类外部行为证据：公开用户记录、公开评论、竞品事实，只能证明现象存在；
   - C类待验证假设：用户画像、预估收益、模拟访谈、专家走查和AI角色回答，不能写成真人研究或真实用户结果。
3. 如果使用AI角色、模拟用户或专家走查，必须明确标注“模拟”或“专家走查”，不得表述为真人访谈、真人测试或真实完成率。
4. 没有真实用户、留存、转化、收入或效率数据时，不虚构业务结果，也不使用后端测试数、接口数、数据表数或代码量冒充产品结果。
5. 技术测试、接口、数据库和构建数据可以保留在技术证据、作品集或面试补充中；除非目标是技术产品经理，否则不占主投简历核心篇幅。
6. 项目如已完成产品发现、定义、设计、实现和上线，可以表述为“0→1产品设计与上线交付”；没有真实运营和持续增长证据时，不表述为“完整产品生命周期”。
7. 产品经理专业能力要在具体动作中显性出现，包括用户研究、竞品分析、需求分析、版本规划、信息架构、业务流程、原型设计、PRD、项目推进、功能验收和上线交付；不能只在技能栏罗列名词。
8. P0/P1/P2、IN/OUT等内部管理术语可以用于项目材料和面试展开，但主投简历使用“根据用户价值、使用频率、业务影响和实现成本确定首版范围”等自然语言表达。
9. 只写本人真实承担的动作，避免“项目组完成”“参与了”“负责相关工作”等无法判断个人贡献的表达。
10. 保持简洁：项目介绍控制在1—2行，主投版使用4条核心经历，精简版使用3条；每条都要包含具体动作、判断或产出。

【第一阶段：事实审计与缺口分析】
先检索并阅读项目目录内与以下内容有关的材料：
- 用户研究、访谈、问卷、公开行为证据和用户画像；
- 市场、行业、竞品和替代方案分析；
- 问题定义、目标用户、使用场景、用户旅程和JTBD；
- 需求池、需求拆解、首版范围、路线图和优先级依据；
- 信息架构、业务流程、状态规则、原型、PRD和交互说明；
- 项目计划、需求评审、开发协作、联调、验收、发布和复盘；
- 真实用户、业务、产品、交付及技术数据；
- 现有简历、面试材料和项目案例页。

输出一张“阶段—已完成工作—证据文件—证据等级—简历可用性—缺口”的审计表，覆盖：
1. 用户研究与问题定义；
2. 需求分析与产品规划；
3. 产品方案与交互设计；
4. 项目推进与上线交付；
5. 上线后的真人验证、指标监控和持续迭代。

随后将缺口分为：
- 必须补齐：缺少后会导致项目逻辑不成立或简历表述无法自证；
- 建议补齐：能够增强产品能力，但不阻塞当前简历；
- 暂不补齐：投入较大，或需要真实用户和业务环境后才能完成。

对每个缺口给出最低成本、可真实执行的补齐方案和产出物。未经我确认，不要虚构补全，也不要直接修改简历文件。

【第二阶段：确认后的正式重构】
在我确认缺口处理方式和框架后，按照以下固定结构生成项目经历：

一、项目基本信息
- 项目名称；
- 项目角色，准确标注个人项目、团队项目或AI辅助开发；
- 项目时间；
- 项目形态及公开链接。

二、一句话项目介绍
使用“面向谁/什么场景—提供什么产品或服务—解决什么问题”的结构，不堆砌技术栈。

三、产品经理主投版
固定采用4条：
1. 用户研究与问题定义；
2. 需求分析与产品规划；
3. 产品方案与交互设计；
4. 项目推进与上线交付。

每条采用“专业能力标签｜具体动作＋分析或判断方法＋关键决策或产品产出”的表达。优先体现对产品效果影响最大的动作，不写研发流程流水账。

四、三点精简版
压缩为：
1. 用户研究与产品规划；
2. 产品方案与交互设计；
3. 项目推进与上线交付。

五、岗位关键词映射
列出目标JD中的关键词、项目中的真实证据和建议放入哪条经历；没有证据的关键词明确标为缺口，不强行写入。

六、面试展开材料
使用STAR整理背景、任务、关键动作、决策依据、取舍、交付和反思。STAR只用于面试展开，不作为简历的显式目录。

七、证据边界
单独说明：
- 当前项目真正证明了什么；
- 尚未证明什么；
- 哪些数据是研究样本、交付数据、技术质量数据或真实用户结果；
- 面试中被追问时应如何诚实解释。

【结果写法】
- 有真实业务或用户结果：写“动作—真实指标变化—业务/用户价值”，并注明统计口径。
- 没有真实业务结果但已上线：写“形成什么可操作产品—完成哪些产品模块—交付什么材料—达到什么上线状态”。
- 只有方案未上线：写“完成什么研究和方案—解决什么决策问题—输出什么可评审材料”，不得写成已经产生用户价值。
- 研究样本数、竞品数和任务数只有在真实、可复核且能解释决策时才使用，不能为了量化而堆数字。

【写作检查】
最终逐条检查：
- 是否能直接看出用户研究、需求分析、产品设计和项目交付能力；
- 是否写清本人做了什么以及为什么这样决策；
- 是否出现只有技术人员才关心、却被包装成产品结果的数据；
- 是否混淆公开材料、模拟走查和真人用户研究；
- 是否存在无法经受面试追问的数字或结论；
- 是否与目标JD自然匹配，而不是机械堆关键词；
- 是否准确使用“0→1产品设计与上线交付”而没有夸大为完整生命周期。

【文件更新规则】
如果我要求更新文件：
1. 先定位现有主投版、精简版、面试版和证据材料；
2. 只替换已经确认的内容，保留仍有价值的研究和面试材料；
3. 保证项目短介绍、固定框架、主投版和精简版表达一致；
4. 不覆盖与本次任务无关的已有修改；
5. 修改后输出变更摘要、文件路径以及仍待补齐的真实工作。

现在先执行第一阶段：读取材料、建立证据审计表、指出缺口并提出候选框架。不要直接写最终简历，等我确认后再进入第二阶段。
```

## 快速使用方式

如果项目材料已经比较完整，只需要把最后一句替换为：

> 已确认采用上述标准。请完成证据审计后直接生成主投版、三点精简版和面试展开版，并更新到指定文件；发现无法自证的内容时保留为缺口，不要代替我编造。
