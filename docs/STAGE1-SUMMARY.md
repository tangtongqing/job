## 三、关键决策（已锁定，后续阶段不再轻易变动）

1. **项目形态**：作品集 Demo（路径 B），本地 SQLite + 无账号体系，不追求真实用户规模
2. **目标用户优先级**：P1 秋招海投型为首批 → P2 实习定向 → P3 春招复盘
3. **差异化定位**：把"发帖手记"升级为状态机 + 用数据看板掌握求职节奏
4. **MVP 四模块**：数据采集与展示 / 看板统计 / 投递管理 / 个性化订阅（均 P0）
5. **技术栈**：Python+FastAPI / Next.js+TS / Playwright / SQLite
6. **投递状态机**：8 状态（含 Offer 三终态），强制状态变更日志支持漏斗分析
7. **明确不做**：简历/面经/公司点评/社交/账号体系/完整推送/移动原生

## 四、Codex 主智能体工作模式复盘

阶段 1 验证了双智能体协作模式：

- **Mimo 产出稳定的"标准结构"**：八个部分齐全、字段齐全、模板规范，作为初稿基础
- **Codex 在 4 个任务上做了实质补强**：每次都识别出 Mimo 看不到的硬伤（同质化/数据不可信/状态机不自洽/AC 伪测试），并亲自修正
- **典型补强模式**：
  - TASK-001：洞察同质化 → Web 核实 → 补行为证据
  - TASK-002：裁决 Mimo 自相矛盾的优先级标注
  - TASK-003：识别时间窗口与立项日期矛盾、修正不可信数据
  - TASK-004：用 sequential-thinking 系统核对状态机自洽性，发现 8 处硬伤
- **结论**：Mimo 适合"按简报执行结构化产出"，Codex 必须**守住策略/自洽性/作品集级质量**这条线

## 五、风险记录（带到阶段 2）

1. **状态变更日志是漏斗分析的命脉**——架构设计必须保证写入的原子性与完整性
2. **去重精度**已诚实降级为"观测项"——架构要预留用户反馈通道用于持续改进
3. **采集合规**——阶段 2 的 Backend Security Gate 重点审查项
4. **Offer 三终态**对前端交互有要求——"接受/拒绝 Offer"的确认流程要在设计阶段（阶段 3）明确
