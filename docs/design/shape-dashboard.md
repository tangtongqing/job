# 看板首页设计简报（shape-dashboard）

> TASK-013 产出。看板是产品的差异化亮点和面试演示第一屏，必须设计得"一眼看清求职节奏"。
>
> ---
> **版本**：v2（主智能体校准版）
> **v2 修订说明**：v1 质量高（线框图清晰 + 三态完整 + 反 AI 自检到位），但发现 5 处问题，其中 2 处是数据语义错误：
> 1. **【中】漏斗点击语义错误**：v1"点击笔试阶段→筛选 status=test"是错的。漏斗的"笔试 20"是"曾经到达过笔试"的累计数，不是"当前在笔试"。筛选 status=test 会漏掉已流转走的。v2 改为"到达过该阶段"（基于 ApplicationEvent）或转化详情
> 2. **【中】无回应超期条件太窄**：v1 只检测"applied > 14 天"，但面试后石沉大海也是无回应。v2 改为"任意非终态，最后一次状态变更 > 14 天"
> 3. **【小】待办数趋势箭头语义模糊**：↓2 不清是好事还是坏事。v2 改为绝对值+本周完成数
> 4. **【小】公司类型分布数据依赖**：需 company 表，Demo 可能不全，标注
> 5. **【小】行动提醒 API 拆分不清**：/todo 和 /applications 混用。v2 拆成 3 个明确来源

---

## 一、任务与用户上下文

### 1.1 谁在看板

**P1 林晓**（高频跨平台投递者）：近一个月跨 3 个以上渠道、累计投递 20 个以上岗位的高频求职者。

### 1.2 看板要回答的核心问题

| 问题 | 对应区块 | 优先级 |
|------|---------|--------|
| "我今天该关注什么？" | KPI 卡片 + 行动提醒 | P0 |
| "我的投递进展如何？" | 漏斗 + 趋势 | P0 |
| "整体收录了多少？" | KPI 卡片（收录总数） | P0 |

### 1.3 核心任务路径

```
用户进入看板
    ↓
第一屏：快速扫一眼 KPI + 行动提醒
    ↓
发现 DDL 临近 / 待办 → 点击跳转处理
    ↓
第二屏：查看漏斗和趋势，了解整体进展
    ↓
第三屏：查看分布，了解投递结构
```

## 二、信息架构（核心）

### 2.1 第一屏（above the fold）

> 一眼看到关键数字和紧急行动。

**KPI 卡片行**（4 个核心数字）：

| KPI | 说明 | 点击行为 |
|-----|------|---------|
| 今日新增岗位 | 今日采集入库的岗位数 | 跳转岗位列表（筛选今日新增） |
| 收录总数 | 系统累计收录的岗位数 | 跳转岗位列表 |
| 我的投递数 | 用户累计投递的岗位数 | 跳转投递列表 |
| 待办数 | 未来 7 天的笔试/面试/材料 | 跳转待办视图 |

**行动提醒区**：

> ⚠️ **v2 关键修正：无回应超期条件**
> v1 只检测"applied > 14 天"，但面试后石沉大海也是无回应（如面试完 14 天没消息）。
> v2 改为：**任意非终态状态，最后一次状态变更 > 14 天前**（基于 Application.updated_at 或最后一条 ApplicationEvent.occurred_at）。
> 这与 PRD v3 §3.3 的"无回应关闭"状态机触发逻辑一致（系统建议 + 用户确认）。

| 提醒类型 | 条件 | 数据来源 | 展示形式 |
|---------|------|---------|---------|
| DDL 临近 | job.deadline ≤ 3 天且未投递 | `GET /applications?deadline_within=3days` | Alert + Badge（warning） |
| 无回应超期 | 任意非终态，updated_at > 14 天前 | `GET /applications?status=non_terminal&stale_days=14` | Alert + Button（标记无回应） |
| 今日待办 | 今日有笔试/面试/材料提交 | `GET /todo?date=today` | Alert + Button（查看详情） |

> **v2 补充**：三条提醒的数据来源已拆清楚（呼应硬伤 5 修正）。/todo 只管"未来待办"（笔试/面试/材料的时间），DDL 和无回应从 /applications 取。

### 2.2 第二屏

> 了解投递转化和进展趋势。

**投递漏斗**：
- 展示：投递→笔试→面试→Offer 的转化
- 数据来源：`GET /dashboard/funnel`
- 交互：每个阶段可点击（筛选该阶段投递）

**有效进展趋势**：
- 展示：近 7 天进入笔试/面试/Offer 的数量
- 数据来源：`GET /dashboard/trend`
- 交互：可切换时间范围（7天/30天/全部）

### 2.3 第三屏

> 了解投递结构和分布。

**分布维度**：
- 展示：按公司类型/地点/岗位方向的投递分布
- 数据来源：`GET /dashboard/distribution`
- 交互：可切换维度

> ⚠️ **v2 数据依赖说明**：
> - **岗位方向分布**（job_category）：来自 Job 表，采集时提取，数据可靠 ✅
> - **地点分布**（location）：来自 Job 表，归一化后可靠 ✅
> - **公司类型分布**（company.category）：需 join Company 表。Demo 阶段 Company 表填充率可能不全（很多 Job 只有 company 文本，无 Company 记录）。**Demo 阶段可能数据不全，需在 UI 上标注"基于已分类公司"或提供"补充公司信息"引导**。

## 五、交互设计

### 5.1 KPI 卡片交互

| 交互 | 行为 |
|------|------|
| 点击"今日新增" | 跳转岗位列表，筛选 `collected_at = today` |
| 点击"收录总数" | 跳转岗位列表 |
| 点击"我的投递" | 跳转投递列表 |
| 点击"待办数" | 跳转待办视图 |
| 悬停 | 显示阴影 + cursor: pointer |

### 5.2 漏斗交互

> ⚠️ **v2 关键修正：漏斗阶段的语义是"曾经到达过该阶段"，不是"当前处于该状态"**
> 漏斗的"笔试 20"表示累计有 20 个投递曾经进入过笔试（可能现在已是面试/Offer/拒绝）。
> v1"筛选 status=test"是错的——只会显示当前在笔试的，漏掉已流转走的。
> v2 改为按 ApplicationEvent 历史（event_type=status_change, to_status=test）筛选。

| 交互 | 行为 |
|------|------|
| 点击"投递"阶段 | 跳转投递列表，筛选"曾经投递过"（全部投递） |
| 点击"笔试"阶段 | 跳转投递列表，筛选"到达过笔试"（基于 ApplicationEvent: to_status=test） |
| 点击"面试"阶段 | 跳转投递列表，筛选"到达过面试"（基于 ApplicationEvent: to_status=interviewing） |
| 点击"Offer"阶段 | 跳转投递列表，筛选"到达过 Offer"（基于 ApplicationEvent: to_status=offer_pending） |
| 悬停阶段 | 显示详细数据（累计数 + 从上一阶段转化率 + 当前仍在该状态的数量） |

**实现说明**：这要求 API 支持按"历史阶段"筛选。两种方案：
- 方案 A（推荐）：投递列表新增 `reached_stage` 筛选参数，后端查 ApplicationEvent
- 方案 B：漏斗点击跳转到"该阶段转化详情"弹窗，显示从上一阶段到该阶段的具体名单 + 转化率

Demo 阶段建议方案 A（简单直接）。

### 5.3 趋势交互

| 交互 | 行为 |
|------|------|
| 切换时间范围 | 重新请求数据（7天/30天/全部） |

### 5.4 分布交互

## 七、数据契约映射

| 区块 | API 端点 | 请求参数 | 响应字段 |
|------|---------|---------|---------|
| KPI 卡片 | `GET /dashboard/kpi` | - | today_new_jobs, total_jobs, total_applications, pending_applications |
| 行动提醒 | `GET /todo` + `GET /applications` | days=3, status=applied | deadline, scheduled_at |
| 漏斗 | `GET /dashboard/funnel` | date_from, date_to | funnel[].status, funnel[].count, funnel[].rate |
| 趋势 | `GET /dashboard/trend` | days=7 | trend[].date, trend[].count |
| 分布 | `GET /dashboard/distribution` | dimension | distribution[].label, distribution[].count, distribution[].rate |
