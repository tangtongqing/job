## 一、实施原则

1. **先隔离，后邀请**：任何真实用户进入前，账号、所有权和跨用户测试必须完成；
2. **先迁移，后改模型**：所有生产 schema 变化通过 Alembic，不用运行时 `create_all` 代替；
3. **先可取回，后托管**：真实数据进入前，导出、删除和备份恢复必须有方案；
4. **先手工可用，后自动化**：收件箱、提醒和集成都必须保留人工入口与失败降级；
5. **先个人，后组织**：M1 使用 `user_id`，不引入 tenant、organization 或 RBAC；
6. **先私测，后收费**：支付不进入 R1–R4 的关键路径。
7. **先官方，后平台**：国内校招官方公告和岗位是供给主干；无授权招聘平台不进入自动采集。
8. **公共轻索引，私人完整岗位**：公共库只保存公司、招聘活动、岗位轻量引用与变化证据；完整 JD 仅在用户主动收藏后进入私人岗位库。

### 已确认的产品边界（2026-08-18）

- 首页是整个数据库的每日变化看板，不突出某一家公司的变化；
- 首页分别展示新收录公司、开始招聘公司、有更新公司、新增岗位和关闭岗位；
- “今日新增岗位”必须由稳定官方岗位 ID 或规范化 URL 与昨日快照差分得出；
- 只能确认页面变化而无法确认岗位差额时，展示“招聘页面有更新”，不得计入新增岗位；
- 公司详情页承载单家公司招聘活动和历史变化；
- 用户通过后续浏览器插件主动收藏岗位后，才保存完整 JD、备注和投递信息。

### 已完成的设计基线（2026-08-18）

- 已完成全站招聘变化首页、公司库、公司详情、私人收藏与投递、插件收藏确认和移动首页 6 个高保真画板；
- 已配置“今日变化 → 公司库 → 公司详情”和“收藏与投递 → 插件侧栏”的核心点击链路；
- 当前画板用于冻结成功态的信息架构与视觉层级，不能替代 PRD 中的加载、空数据、失败、重复收藏和来源降级要求；
- 研发实现以 [PRD-M1.md](PRD-M1.md) 的字段、口径和验收标准为准，不从原型演示数字反推业务规则。

## 二、需要先完成的架构决策

以下决策以 ADR 形式记录在 `docs/architecture/decisions/`，未完成前不开始对应生产实现。

| ADR | 决策问题 | 必须回答 | 默认倾向 |
|---|---|---|---|
| ADR-001 | 鉴权方案 | 登录方式、会话模型、令牌验证、找回、撤销、供应商退出方案 | 托管身份优先，后端验证标准令牌；不自研密码系统 |
| ADR-002 | PostgreSQL 托管与连接 | 供应商、连接池、迁移权限、备份、恢复、成本 | 支持标准 PostgreSQL 与可导出备份 |
| ADR-003 | 用户数据归属 | 公共岗位与私人岗位边界、`user_id` 放置、唯一索引调整 | 公共岗位共享；手工岗位和所有行为归个人 |
| ADR-004 | 后台任务 | 队列、调度、重试、幂等、失败查看 | 提醒与采集不依赖 Web 进程内存 |
| ADR-005 | 文件与简历引用 | 对象存储、签名 URL、病毒检查、删除 | R1 不上传简历；R4 再启用 |
| ADR-006 | 产品分析与错误监控 | 数据最小化、环境隔离、保留期、告警 | 先事件字典和错误监控，拒绝敏感正文 |
| ADR-007 | 国内校招官方采集 | 公司池、来源注册、公告/岗位分层、模板族、覆盖率和合规门禁 | 采用[来源注册表驱动的官方优先架构](../architecture/domestic-campus-ingestion.md) |

## 三、R0.5：国内校招官方供给基础

### 工作流 D0：停止错误数据进入

#### M1-D0-01 停用海外默认源

- `config/sources.yaml` 中 Figma、Webflow、Intercom、Stripe 全部关闭；
- Greenhouse 适配器和历史验收记录保留，不再作为默认实时岗位；
- 现有海外岗位通过可回退任务标记为 `out_of_scope`，不直接物理删除；
- 默认岗位列表和订阅增加 `country_code=CN` 与校招范围门禁。

**验收**：重置/启动后不会自动采集海外来源；海外岗位不出现在默认实时目录或订阅结果中。

### 工作流 D1：来源注册表与公司池

#### M1-D1-01 确认首批公司池

- 默认从 100 家开始，按用户关注度、校招规模和行业代表性排序；
- 每家公司必须有标准名称、别名、官方域名、至少一个招聘入口和运营负责人；
- 首批开发先用 10 家技术样本覆盖自建站及 3 个高复用 ATS 模板族；
- 公司池变更保留版本和原因，不用临时 URL 列表代替。

#### M1-D1-02 建立 `CompanySourceRegistry`

- 保存官网、校招专题、职位页、公告页、ATS 模板族和已核验公众号；
- 记录 robots/条款检查、刷新频率、来源状态、最近成功、解析器版本与错误；
- 状态使用 `candidate/reviewing/approved/enabled/degraded/paused/rejected/retired`；
- 调度器只处理 `enabled` 来源，无法确认许可时 fail closed。

### 工作流 D2：公司、招聘活动与轻量岗位索引

#### M1-D2-01 模型与迁移

- 扩展 `Company`，新建 `RecruitmentCampaign`、`CampaignGraduationYear`、`ObservedPositionRef`、`SourceSnapshot`、`CompanyChangeEvent`；
- `ObservedPositionRef` 只保存官方岗位 ID、规范化 URL、标题、城市、岗位类别、首次/最后发现时间、关闭状态和指纹，不保存完整 JD；
- `SourceSnapshot` 分别保存抓取状态、完整性状态和比较状态；只有总数对账或分页穷尽已验证的成功快照能建立基线或参与差分；
- `CompanyChangeEvent` 分开保存新增、重新开放、关闭和变更岗位数，使用 UTC 发生时间与中国区报表日期驱动首页全站指标；
- 用户后续主动收藏产生的完整岗位继续进入私人 `Job`，并关联 `ObservedPositionRef`；
- 活动年份与毕业届别分开保存；多届别不得压成单值；
- 去重后保留所有来源证据，冲突字段进入复核队列。

#### M1-D2-02 分类器

- 识别秋招、春招、暑期实习、日常实习、补录和滚动招聘；
- 识别 2027/2028 等一个或多个届别；
- 识别技术、产品、设计、运营、市场、销售、商业、供应链、制造、财务、法务、人力、行政、研究、医疗、教育、客服和其他岗位类别；
- 不从发布时间直接推断毕业届别；
- 无法确认时输出 `unknown` + 证据 + 置信度并保留岗位，不编造或丢弃。

### 工作流 D3：官方来源适配器

#### M1-D3-01 模板族适配器

- 先实现通用 JSON-LD/结构化页面、Moka、北森、用友大易；
- 定时任务默认只覆盖岗位列表、分页/游标穷尽、部门与城市入口、轻量字段、关闭状态、空结果和模板变化；
- 完整岗位详情不在每日公共采集中抓取；只有分类缺少必要证据且来源允许时才按最小范围读取详情；
- 生产采集不得配置岗位关键词或 `max_jobs` 上限；来源公开总数时必须完成源端岗位数对账；
- 企业自建站按复用模式归类，只有无法复用时才增加公司专用解析器；
- 动态页面优先使用公开结构化请求；Playwright 只在来源许可且必要时使用。

#### M1-D3-02 公告发现器

- 从官方入口、站点地图、公告索引、政府/高校就业平台和已知公众号公开文章 URL 发现候选；
- 搜索结果只用于发现，正式字段必须回到官方原文或标记二级核验；
- 公众号不自动化搜索微信客户端，不默认长期保存完整文章；
- BOSS、猎聘无书面许可时不创建自动适配器。

### 工作流 D4：覆盖与人工复核

- 首页展示全站今日新收录公司、开始招聘公司、有更新公司、新增岗位、关闭岗位及分类分布；
- 运营看板另行展示公司池来源登记率、健康率、人工审计发现率、岗位对账率、P50/P95 延迟、字段完整度和复核积压；
- 低置信度届别、截止时间冲突、来源权威性不明和模板突变进入人工队列；
- 来源连续返回 0 条、字段完整度骤降或超过两个刷新窗口未成功时告警；
- 来源不健康时订阅停止发送“没有新岗位”的结论。

### R0.5 完成定义

- 默认启用的海外来源为 0；
- 10 家技术样本端到端完成列表采集、轻量索引、快照差分、分类、去重、核验和关闭状态；
- 10 家样本中官方职位页公开可见的全部校招岗位 100% 对账到轻量索引、隔离或带原因失败记录；
- 首页所有增量指标均能下钻到 `CompanyChangeEvent` 和来源快照，不使用演示常量冒充实时统计；
- 100 家试点公司全部登记至少一个已核验官方入口；
- 每周人工审计样本中的官方活动发现率 ≥95%，高峰期 P95 延迟 ≤24 小时；
- BOSS、猎聘等受限平台没有未经授权的自动抓取路径。

> 当前进度（2026-08-18）：10 家技术样本已完成官方入口首轮登记；招商银行公开接口适配器完成技术对账；公共公司招聘雷达模型、两级 Alembic 迁移、旧库安全接管与数据完整性约束已经落地，全套 171 项测试通过。真实 `data/jobpulse.db` 的副本升级前后 M0 数量一致，源文件仍未被自动修改；正式来源因最终条款审核保持关闭。实施证据见[国内校招采集工程记录](../engineering/DOMESTIC-CAMPUS-INGESTION.md)。

### 下一冲刺：全站招聘变化最小闭环

**冲刺目标**：让首页能够基于真实快照可信展示“整个数据库今天新增了多少公司和岗位”，并可下钻到公司与官方来源。

| 属性 | 计划 |
|---|---|
| 周期 | 2 周 |
| 团队假设 | 单人开发配合 AI；暂无历史 velocity |
| 规划容量 | 20 点 |
| 承诺范围 | 16 点 |
| 缓冲 | 4 点（20%，用于来源变化、迁移和缺陷） |

| 顺序 | 用户故事 | 点数 | 依赖 | 状态 | 验收结果 |
|---:|---|---:|---|---|---|
| 1 | 对齐 PRD、架构与数据字典，移除“公共完整岗位库”旧假设 | 1 | 无 | 已完成 | PRD、实施计划、数据库字典和工程记录的公共/私人边界一致 |
| 2 | 建立公司、招聘活动、轻量岗位、来源快照和变化事件模型 | 5 | 1 | 已完成 | 迁移往返、旧库副本接管/失败恢复、严格漂移拒绝、跨进程互斥与模型一致性检查通过；模型、迁移和启动安全 35 项定向测试通过 |
| 3 | 将招商银行采集改为列表快照与幂等差分 | 3 | 2 | 下一步 | 首次生成基线，第二次零新增，模拟新增/关闭/重开计算正确 |
| 4 | 实现届别、招聘性质与岗位类别的轻量分类 | 3 | 2 | 待开始 | 2027/2028、正式校招、暑期/日常实习和未知值均有测试 |
| 5 | 提供全站今日指标、变化流和公司下钻 API | 2 | 3、4 | 待开始 | 所有数字均可追溯到变化事件；不重复计数 |
| 6 | 改造首页为全站数据变化看板 | 2 | 5 | 待开始 | 展示六项核心指标、分类分布、变化列表和数据更新时间 |

**当前执行入口**：先按[项目重构计划](PROJECT-RESTRUCTURE-PLAN.md)统一产品事实、主 PRD、架构和核心原型；达到恢复功能开发门禁后进入故事 3。故事 3 仍从招行“列表轻量化 → 完整性判断 → 首次基线 → 后续差分 → 幂等事件”闭环开始，再进入分类器或首页 API。

**本冲刺不做**：扩展到 100 家、浏览器插件、完整 JD 抓取、BOSS/猎聘采集、复杂推荐和通知渠道。

**关键风险与应对**：

- 官网没有稳定岗位 ID：使用规范化 URL 与轻量字段指纹；仍无法确认时只记录“页面更新”；
- 来源总数变化但分页不一致：整次快照标记失败，不生成新增/关闭事件；
- 首次采集产生虚假“今日新增”：首个成功快照只建立基线，不计入今日新增；
- 招聘届别分类不确定：保存 `unknown`、证据和置信度，不从发现日期推断届别；
- 单一招商银行数据使首页样本偏少：先验证数据闭环，第二冲刺再接入 3–5 个允许自动化的官方来源。

## 四、R1：安全私测

### 工作流 F1：数据库迁移基线

#### M1-F1-01 初始化正式 Alembic 环境

> 2026-08-18 进度：Alembic 环境、M0 基线 revision 和 M1 公共模型 revision 已建立，并已完成 SQLite 往返迁移验证；本地与单实例容器启动已切换到安全迁移入口。独立生产迁移任务、schema 健康检查和真实 PostgreSQL 执行验证仍未完成。

**工作**：

- 建立 `alembic.ini`、迁移环境和首个基线版本；
- CI/启动流程分开执行 `alembic upgrade head`；
- 禁止生产使用 `Base.metadata.create_all()` 自动补 schema；
- 增加 schema 版本健康检查。

**验收**：

- 空 PostgreSQL 可升级到最新；
- 已有上一版本库可升级；
- 重复执行保持幂等；
- 未迁移到最新版本时生产健康检查不报告就绪。

#### M1-F1-02 建立 PostgreSQL 测试矩阵

**工作**：

- 保留 SQLite 单元测试；
- 新增 PostgreSQL 集成测试；
- 覆盖部分索引、唯一约束、事务回滚、时间和布尔差异；
- CI 使用隔离数据库并在完成后清理。

**验收**：核心状态机、事件、导入和隔离测试在 PostgreSQL 通过。

#### M1-F1-03 M0 数据迁移工具

**工作**：

- 导出现有 SQLite 对象与计数；
- 写入 M1 PostgreSQL schema；
- 为历史演示数据指定 `data_kind=demo`，不归入真实用户；
- 输出写入、跳过、冲突和校验摘要；
- 支持 dry-run。

**验收**：迁移前后岗位、投递、事件、收藏、待投递和订阅数量及关系一致；失败时目标事务回滚。

### 工作流 F2：账号与数据归属

#### M1-F2-01 用户与身份映射

建议模型：

```text
User
  id
  auth_subject        外部身份稳定 ID，唯一
  email_normalized    可空；不作为授权主键
  timezone
  status              active / deletion_pending / deleted
  created_at / updated_at / last_login_at
```

**工作**：

- 接入 ADR-001 选择的身份方案；
- 服务端验证令牌并解析稳定 subject；
- 首次成功登录幂等创建 User；
- 退出、过期、撤销和禁用账号有统一行为；
- 前端 `(app)` 路由增加会话保护。

**验收**：伪造、过期、撤销令牌均不能访问私人 API；重复首次登录不创建重复用户。

#### M1-F2-02 私人对象增加用户归属

**直接增加 `user_id`**：

- `user_job_action`
- `application`
- `subscription`
- 后续的 `inbox_item`、`import_job`、`reminder_delivery`

**间接归属**：

- `application_event` 必须从已授权的 `application` 进入；

**岗位边界**：

- 公开采集岗位：`owner_user_id = NULL`，所有登录用户只读；
- 手工、导入、私人 URL 岗位：`owner_user_id = 当前用户`；
- 私人岗位不能出现在公共岗位接口或其他用户搜索中。

**索引变化**：

- 活跃收藏/待投递唯一索引改为 `(user_id, job_id, action_type)`；
- 同一岗位一个进行中投递改为 `(user_id, job_id)`；
- 订阅、列表和待办查询建立 `user_id` 前导索引。

#### M1-F2-03 所有权查询层

**工作**：

- 建立获取当前用户的统一依赖；
- 为私人资源建立 `get_owned_*` 查询函数；
- 路由不得先按 ID 查询后在应用层判断所有者；
- 创建请求不接受可改变所有权的 `user_id`；
- 批量接口逐项验证所有权并拒绝混入其他用户对象。

**验收矩阵**：

| 操作 | 自己的数据 | 他人数据 | 未登录 |
|---|---:|---:|---:|
| 列表 | 可见 | 不出现 | 拒绝 |
| 详情 | 可见 | 404/拒绝 | 拒绝 |
| 修改 | 成功 | 不改变 | 拒绝 |
| 批量更新 | 只处理自己的 | 整体拒绝或逐项明确失败 | 拒绝 |
| 导出 | 只含自己的 | 0 条 | 拒绝 |
| 删除 | 只删除自己的 | 不改变 | 拒绝 |

#### M1-F2-04 两阶段数据迁移

采用扩展—回填—约束流程：

1. 新增可空 `user_id` / `owner_user_id`；
2. 历史共享 Demo 数据标记为 Demo，不绑定真实账号；
3. 部署双读或兼容代码；
4. 私人表回填测试所有者或清空重建策略；
5. 验证无孤儿数据；
6. 私人表加 NOT NULL、外键和索引；
7. 删除旧的全局唯一索引。

禁止一步增加 NOT NULL 列并假设所有历史数据都属于首个登录用户。

### 工作流 F3：环境与安全边界

#### M1-F3-01 环境配置

新增明确环境配置：

- `APP_ENV=development|demo|production`
- `AUTH_REQUIRED`
- `DEMO_RESET_ENABLED`
- `ANONYMOUS_WRITE_ENABLED`
- `DATABASE_URL`
- `PUBLIC_APP_URL`
- `AUTH_ISSUER` / `AUTH_AUDIENCE`

生产启动时执行 fail-fast 校验：生产若开启 Demo 重置、匿名写入或 SQLite，直接拒绝启动。

#### M1-F3-02 Demo 与生产分离

- Demo 保持确定性共享数据与重置；
- Production 不加载 Demo 数据，不展示重置入口；
- 测试、Demo、Production 使用不同数据库、Cookie 域、身份应用和第三方密钥；
- 产品事件携带环境，不允许聚合 Demo 与真实行为。

#### M1-F3-03 安全基线

- 安全响应头、严格 CORS、Cookie 与 CSRF 策略；
- 登录、导入、解析、导出和删除限流；
- 请求 ID 与结构化日志；
- 日志脱敏：令牌、Cookie、通知、备注、简历正文不得输出；
- 依赖漏洞扫描和 secrets 扫描；
- 高风险操作重新验证身份。

### 工作流 F4：数据权利与恢复

#### M1-F4-01 用户导出

- 异步生成导出包；
- 包含 CSV 索引与 JSON 全量关系；
- 下载使用短时签名链接；
- 导出包自动过期；
- 导出任务和下载写安全审计。

#### M1-F4-02 账号删除

- 用户重新验证身份；
- 账号进入 `deletion_pending`，停止第三方同步；
- 后台任务删除私人业务数据和文件；
- 公共岗位不因用户删除而删除；
- 完成后令牌失效；
- 备份保留期在隐私说明中公开。

#### M1-F4-03 备份与恢复

- 数据库自动备份；
- 建立恢复 runbook；
- 在隔离环境定期恢复并校验对象数量、外键和关键查询；
- 记录最近成功恢复演练时间；
- 不以“备份任务成功”代替“数据可以恢复”。

### 工作流 F5：监控、审计和质量门禁

#### M1-F5-01 可观测性

监控：

- API 可用性、P95 延迟和 5xx；
- 数据库连接与迁移版本；
- 登录失败异常峰值；
- 后台任务积压、重试和永久失败；
- 提醒和订阅送达；
- 采集来源成功率；
- 前端运行时错误。

#### M1-F5-02 最小产品事件

首批只实现：

- `account_created`
- `workspace_first_item_created`
- `import_started/completed`
- `inbox_item_confirmed/ignored`
- `application_status_changed`
- `reminder_created/delivered/completed`
- `export_requested/completed`
- `integration_connected/disconnected`

禁止属性：通知原文、JD、备注、邮箱正文、联系人、简历正文和任意令牌。

#### M1-F5-03 R1 发布门禁

- 单元、集成、E2E 和隔离测试通过；
- PostgreSQL 迁移与回退通过；
- 备份恢复演练通过；
- 数据导出与删除通过；
- Production 配置安全检查通过；
- 无 P0/P1 安全缺陷；
- 仅通过邀请开放私测。

## 五、R2：低成本激活

### 工作流 A1：CSV 导入导出

#### M1-A1-01 模板与数据字典

- 发布固定 CSV 模板；
- 明确日期、时区、状态 code、长度和 URL 规则；
- 提供 Excel/飞书/Notion 导出示例；
- 不在第一版支持任意表头 AI 映射。

#### M1-A1-02 导入暂存区

建议模型：

```text
ImportJob
  id, user_id, status, source_filename, file_hash
  total_rows, valid_rows, invalid_rows, imported_rows
  created_at, confirmed_at, completed_at

ImportRow
  id, import_job_id, row_number, normalized_payload
  validation_status, error_codes, idempotency_key, target_application_id
```

- 文件先解析到暂存区；
- 逐行校验并显示错误；
- 用户确认后才写 Job/Application/Event；
- 每行独立结果，导入任务可重试；
- 临时原文件按保留策略删除。

#### M1-A1-03 导入用户体验

`下载模板 → 上传 → 映射/预览 → 修正默认值 → 确认 → 结果摘要 → 查看投递`

空文件、错误编码、超大文件、重复行、部分失败和取消均有明确状态。

### 工作流 A2：求职收件箱

#### M1-A2-01 收件箱模型

```text
InboxItem
  id, user_id, kind, status
  input_type, source_url, raw_content_ref
  parsed_payload, confidence, evidence
  matched_application_id
  content_fingerprint, expires_at
  created_at, confirmed_at, ignored_at
```

状态：`pending / confirmed / ignored / expired / failed`。

原始内容与结构化结果分离；原始内容默认短期保留，产品分析只记录类型和结果。

#### M1-A2-02 统一解析与确认

- URL 输入：优先公开结构化元数据，失败时只保存链接；
- 通知文本：复用现有解析器，返回类型、状态、时间、匹配和依据；
- 最小手工信息：公司、岗位即可；
- 未匹配时生成新投递草稿；
- 确认时复用现有事务服务，禁止在路由层重复拼装状态和事件。

#### M1-A2-03 收件箱界面

- 全局“收进 JobPulse”入口；
- 待确认、失败和已处理分组；
- 确认卡明确展示将创建/修改的内容；
- 允许编辑、忽略、删除原文和重新解析；
- 不将“解析成功”描述为“状态已更新”。

### 工作流 A3：新用户激活

- 首次进入选择“导入历史”或“收进第一条”；
- Demo 示例可查看，但不自动混入用户数据；
- 第一条真实数据创建后进入“今天”；
- 记录首次激活时间，不以注册完成代替激活；
- 完成 3–5 次任务测试后才能扩大邀请。

## 六、R3：每日行动与真实提醒

### 工作流 D1：“今天”

- 后端提供统一 action feed，不由前端分别拼接多个接口；
- 支持逾期、今日、待确认、未来和无回应建议；
- 每项包含来源、关联对象、计划时间、优先原因和可执行动作；
- 看板保留为复盘页，侧栏默认入口改为“今天”。

### 工作流 D2：提醒引擎

建议模型：

```text
Reminder
  id, user_id, application_event_id, scheduled_for
  channel, status, dedupe_key, timezone

ReminderDelivery
  id, reminder_id, attempt, status, provider_message_id
  attempted_at, delivered_at, error_code
```

- 计划时间变更时取消旧提醒并创建新提醒；
- 每个渠道使用幂等键；
- 指数退避并限制重试；
- 永久失败进入可见死信列表；
- 用户关闭权限不计为系统送达失败。

### 工作流 D3：订阅匹配

- 只对新入库或重新开放岗位执行；
- 使用 `user_id + subscription_id + job_id` 唯一约束；
- 匹配结果进入站内收件箱，之后才触发通知；
- 已读、忽略、收藏和待投递动作可追溯；
- 数据源不健康时停止发送，避免陈旧或虚假提醒。
- 支持招聘季、实习类型和多毕业届别条件；只消费已核验的国内校招岗位。

## 七、R4：外部入口与集成

### 工作流 I1：浏览器扩展

先支持允许访问的官方 ATS 和常见岗位详情页；采用域名白名单与通用降级，禁止绕过访问控制。BOSS、猎聘无授权时只保存当前 URL 并由用户手工补字段，不自动读取页面内容。扩展只向当前登录用户创建收件箱草稿，不直接改变投递状态。

### 工作流 I2：邮件转发

- 给每位用户生成可撤销的转发地址或安全 token；
- 入站邮件先做发件人、大小、附件和恶意内容检查；
- 正文进入短期收件箱，解析后由用户确认；
- 不自动回复、不自动转发到第三方模型；
- 价值和准确率通过后再决定是否做全邮箱授权。

### 工作流 I3：日历

1. 单个事件下载 ICS；
2. 用户级只读订阅日历；
3. 只有出现真实编辑需求后评估双向同步。

每一步都必须支持撤销和失效，不把外部日历成功写入与 JobPulse 事务混为一次不可回退操作。

### 工作流 I4：简历版本引用

- 第一版只保存版本名称、哈希、上传时间和受控文件引用；
- 每次投递记录不可变地引用当时版本；
- 文件访问使用短时授权；
- 不进入 AI 改写和模板制作。

## 九、第一实施批次

第一批先完成 R0.5 的数据边界和 10 家技术样本，再进入 R1；不并行开发插件、邮件、支付或新图表。

- 数据可以从备份恢复；
- 故障和高风险操作可被发现；
- 没有任何 R2/R3 功能以牺牲上述门禁为代价提前上线。

## 十、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 在路由中遗漏用户过滤 | 严重数据泄露 | 统一 owned query、跨用户测试、代码审查门禁 |
| 直接把历史 Demo 数据绑定首个用户 | 数据混淆与隐私风险 | Demo 数据单独标记或独立库，不自动归属 |
| SQLite 与 PostgreSQL 行为不同 | 上线后约束或事务失效 | 双数据库测试，生产以 PostgreSQL 集成为准 |
| 登录完成被误认为 SaaS 完成 | 缺少导出、删除、恢复 | R1 完成定义强制包含数据生命周期 |
| 提醒依赖 Web 进程 | 重启丢任务或重复发送 | 持久任务、幂等键、重试和死信 |
| 收件箱保留敏感通知全文 | 隐私和合规风险 | 原文分离、短期保留、主动删除、日志禁入 |
| 同时开发过多新功能 | 安全基础被拖延 | R1 冻结功能范围，其他工作只做设计 |
| “全网全量”没有公司池边界 | 无法验收且容易虚假承诺 | 版本化目标公司池，按人工审计样本计算发现率 |
| ATS 模板静默变化 | 错误显示为没有岗位 | 连续 0 条和字段骤降告警，契约测试与人工复核 |
| 公众号成为唯一公告渠道 | 官网发现率下降 | 维护官方账号清单、公开 URL 提交和运营复核；规模化后评估授权服务 |
| 平台岗位诱导违规抓取 | 合规、账号和业务风险 | BOSS/猎聘默认关闭，仅接受书面授权/API/合作 |
