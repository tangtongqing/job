## 1. 目标

本计划解决的不是“继续补几篇文档”，而是把项目从多个历史阶段收口为一套可以指导成熟产品建设的事实体系。

完成后应达到：

1. 一个清晰的产品定位：国内校招公司招聘雷达 + 私人求职工作台；
2. 一个当前有效的主 PRD，历史 PRD 只用于追溯；
3. 一套与真实代码一致的当前架构，以及明确但不过度设计的目标架构；
4. 一套覆盖成功、空、失败、过期和数据不完整状态的 Figma 原型；
5. 文档、代码、测试、验收报告、README 和作品集不再互相矛盾；
6. 下一轮功能开发可直接从已满足 Definition of Ready 的用户故事开始。

## 2. 已确认的规划假设

- 近期以单人开发配合 AI 为执行方式，暂无可用的历史 velocity；
- 每个两周冲刺按 20 点规划，承诺 16 点，保留 4 点（20%）处理缺陷、外部来源变化和文档返工；
- 公司池按 10 家技术样本、约 30 家核心监控和约 100 家扩展公司分阶段建设；公司是监控单位，企业类型用于保证代表性，先证明 3–5 个不同官方站点结构再扩面；
- 架构采用模块化单体，不提前引入微服务、消息队列、组织租户或复杂 RBAC；
- 公共招聘雷达、私人求职工作台和数据运营是三个业务边界，但可以共享同一代码仓库和数据库；
- 先确认 PRD 和原型，再进行大范围代码目录调整或前端重构。

## 3. 关键依赖与执行顺序

```text
市场与用户证据
    ↓
项目章程 / MRD / Personas / JTBD
    ↓
唯一主 PRD
    ├──→ 系统架构 / API / 数据模型 / ADR
    └──→ 信息架构 / Figma 原型 / 状态矩阵
                    ↓
            实施计划与可开发故事
                    ↓
             QA / README / 作品集
```

主 PRD 是架构和原型的共同上游。README、案例页和作品集必须最后更新，避免再次把目标能力写成已实现能力。

## 5. 四个执行冲刺

### Sprint A：统一产品事实与主 PRD

**目标**：建立唯一、可评审、能区分现状与目标的产品事实源。

**逐批审核规则**：

| 审核批次 | 本批只修改 | 本批明确不修改 | 提交给项目所有者的审核重点 |
|---|---|---|---|
| A1 市场与竞品证据 | `MRD.md`、`competitor-analysis.md` | 章程、画像、JTBD、PRD 和原型 | 市场事实是否可信；竞品分组和差异化是否成立 |
| A2 用户与问题定义 | `PROJECT-CHARTER.md`、`PERSONAS.md`、`JTBD.md` | PRD 功能规则、架构和原型 | 核心用户是否应从“高频投递者”调整为“目标公司机会监控者”；公共/私人边界是否合理 |
| A3 V3 PRD 骨架 | 新增 `PRD-V3-DRAFT.md`；仅更新本计划中的阶段状态和过渡方式 | 不修改 `PRD.md`、`PRD-M1.md`，不归档旧 PRD，不进入架构/原型/代码 | 四维需求状态、统一功能编号、术语、迁移表和冲突裁决能否支撑完整 PRD |
| A4 V3 PRD 需求合并 | 在 `PRD-V3-DRAFT.md` 补齐有效需求、流程、口径、实现证据与 AC；审核通过后再提升为主 `PRD.md` | 不生成 Word，不归档或删除历史，不进入架构和原型 | 公司招聘雷达与私人工作台是否形成完整链路；每项状态和 AC 是否有证据 |
| A5 PRD 发布收口 | `archive/prd/`、`PRD.docx`、文档索引 | 不进入架构和代码重构 | 当前入口是否唯一；历史是否可恢复；Markdown、Word 与索引是否一致 |

每一批完成后暂停，提供“修改文件、关键变化、删除/保留的旧结论、验证结果和待决策项”；只有项目所有者确认后才进入下一批。

| A1 更新市场证据与竞品分组 | 3 | 无 | `MRD.md`、`competitor-analysis.md` | 结论有来源日期，事实与假设分开 |
| A2 重写章程、画像与 JTBD | 4 | A1 | `PROJECT-CHARTER.md`、`PERSONAS.md`、`JTBD.md` | 核心人群、任务和产品边界一致 |

## 6. Figma 重绘清单

第一批必须包含：

1. 招聘动态首页（桌面）；
2. 公司库（桌面）；
3. 公司详情与招聘活动（桌面）；

5. 插件支持站点收藏确认；

7. 数据源健康与人工复核队列；
8. 招聘动态、公司详情和私人收藏移动端。

账号、登录、设置、通知渠道和订阅管理进入第二批，不阻塞公共招聘雷达闭环。

## 7. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 文档先写成“全部实现” | 作品集可信度下降 | 所有功能标记 implemented/current/next/future |
| 市场数据或竞品信息过期 | MRD 决策失真 | 更新时只引用有日期的官方或一手来源 |
| PRD、架构和原型并行失控 | 规则再次分叉 | 先评审 PRD，再进入架构和高保真 |
| 为成熟感提前上复杂架构 | 延迟核心数据闭环 | 保持模块化单体，设置明确升级触发条件 |
| Figma 只画成功状态 | 无法指导真实产品实现 | 用页面×状态矩阵作为原型验收件 |
| 旧材料被直接删除 | 丢失作品集复盘证据 | 先归档、加替代入口，再更新当前文档 |
| 外部招聘站变化 | 排期波动 | 保留 20% 容量，先做适配器契约和失败降级 |

## 8. 阶段门禁

### 进入 Sprint A

- 项目所有者确认本计划；
- 确认唯一 V3 PRD 策略；
- 确认“公司招聘雷达为主入口、私人工作台为下游”的产品结构。

### 进入 Sprint B

- 章程、MRD、Personas、JTBD 与 PRD 不再冲突；
- PRD 的公共/私人数据边界和核心指标通过评审。

### 进入 Sprint C

- 核心页面数据契约稳定；
- 每个页面明确数据来源、空状态、失败状态与官方跳转方式。

### 恢复功能开发

- V3 PRD、目标架构和核心原型通过评审；
- M1 实施计划中故事 3 达到 Definition of Ready；
- 不存在阻断快照差分的 P0 文档或数据模型冲突。

## 9. 下一执行动作

A1 与 A2 已通过，当前只审核 A3 的 `PRD-V3-DRAFT.md` 结构和安全过渡方式。A3 通过后才进入 A4：逐项核对代码、数据迁移、接口、测试和原型，把 M0/M1 的有效需求补入草稿；A4 再次审核通过后，才提升为唯一主 `PRD.md`，并在 A5 归档旧稿、更新 Word 与索引。

在 Sprint A–C 通过前不恢复大范围功能开发。后续恢复开发时，不默认绑定单一公司；先由确认后的 PRD、公司池样本和数据门禁决定首个“列表轻量化 → 完整性判断 → 首次基线 → 后续差分 → 幂等事件”实现样本。
