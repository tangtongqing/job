## 一、产品简介

### 1.1 文档目的

本文档是 JobPulse 当前产品需求与验收口径的事实源，回答三个问题：

1. 本期 M0 Demo 需要交付什么；
2. 每项能力为什么存在、如何运行；
3. 产品、设计、研发和测试如何判断交付完成。

市场规模、竞争与机会结论以 [MRD](../product/MRD.md) 为准；页面视觉细节以 [设计文档](../design/DESIGN.md) 为准；代码与接口细节以 [架构文档](../architecture/system-architecture.md) 和 [API 契约](../architecture/api-contract.md) 为准；已发生的验证事实以 [验收报告](../qa/ACCEPTANCE-REPORT.md) 为准。

### 1.2 背景与用户问题

公开内容研究证明以下现象存在，但不能证明其在人群中的发生比例：

- 求职岗位分散在企业官网、招聘平台、社区、群聊和公众号；
- 高频求职者会使用 Excel、Notion、飞书、邮箱或日历维护进度；
- 投递量增加后，记录可能中断，通知、时间和渠道信息可能丢失；
- 重要测评、面试和材料截止时间存在遗漏或冲突风险；
- 邮箱、日历和表格也是强替代方案，新产品只有明显减少重复录入才有迁移价值。

因此，本期核心问题不是“再做一张更漂亮的表格”，而是：

> 如何在保留来源和历史可追溯性的同时，降低从发现岗位到记录下一步行动的维护成本？

### 1.3 本期核心目标

本期以 M0 Demo 为边界，建立并验证以下闭环：

`发现岗位 → 收藏或待投递 → 建立投递 → 更新状态 → 形成计划事件 → 查看近期安排 → 回看历史`

本期必须做到：

- 岗位来源、更新时间、核验信息和演示快照边界清楚；
- 收藏和待投递表达两种独立意图；
- 投递状态和事件历史可追溯；
- 招聘通知只生成建议，用户确认后才改变状态；
- 明确的面试/测评时间与状态在同一事务中写入；
- 岗位库外投递可用最少字段进入统一时间线；
- 桌面端完整可用，390px 移动端可走通核心流程。

### 1.4 本期范围

| 范围 | 优先级 | 交付状态 |
|---|---:|---|
| 公开岗位列表、详情、来源与有效性信息 | P0 | 已实现，需按本 PRD 验收 |
| 收藏与待投递双清单 | P0 | 已实现 |
| 创建投递、9 状态流转、事件时间线 | P0 | 主流程已实现；前端纠错入口待补 |
| 招聘通知解析、人工确认、计划事件与近期安排 | P0 | 已实现 |
| 岗位库外投递最小补录 | P0 | 已实现 |
| 确定性演示快照与公开 ATS 采集质量可见性 | Ops-P0 | 已实现 |
| 求职概览和基础累计漏斗 | P1 | 已实现，用户价值待验证 |

### 1.5 本期不做

以下能力不进入 V2.0 验收：

- 账号、登录、多用户、租户隔离、云同步和团队权限；
- 支付、真实套餐限制、邮件/微信/系统推送；
- 自动读取用户邮箱或日历；
- 自动投递、代替用户提交申请或修改外部招聘平台数据；
- 绕过登录、验证码、访问控制或反爬限制的采集；
- BOSS、牛客等受限平台的在线采集；
- 简历制作、简历优化、面经、课程、公司点评、社交与内推；
- Excel / Notion 历史投递导入；
- 从一封未知通知自动建立全新投递；
- 实习天数、实习周期等专项结构化筛选；
- 按公司、岗位方向或来源的策略性细分转化分析；
- 原生 iOS / Android App。

### 1.6 未来目标与进入条件

| 未来目标 | 进入条件 | 当前里程碑 |
|---|---|---|
| 历史投递导入 | 真人研究证明迁移成本是首要阻力；先支持固定 CSV 模板 | M1 候选 |
| 邮箱/日历集成 | 用户明确接受权限；完成隐私、撤权和数据最小化设计 | M1 候选 |

| 未知通知自动建档 | 匹配准确率、重复建档和人工确认机制通过测试 | M1 候选 |
| 账号与云同步 | 5–8 次访谈、3–5 次可用性测试和持续使用出现复用信号 | M1 |

| 团队与导师协作 | 真实团队需求出现，不以作品集设想代替证据 | M2 |
| 原生 App | Web 数据显示移动端高频使用且核心任务受 Web 限制 | M2 |

### 1.7 证据边界与已知限制

| 类型 | 当前事实 | 不能推导出的结论 |
|---|---|---|
| 真人研究 | 计划中的 3 人探索性访谈尚未执行，完成数为 0 | 不能声称“访谈用户后得出” |
| 公开内容研究 | 编码 12 条公开记录，证明问题和替代方案存在 | 不能推断总体发生率 |
| 合成角色 | 3 个 AI 合成角色用于找反例和预演访谈 | 不能计入样本、完成率或用户引语 |
| 专家走查 | 修复后核心 19/23、全部 20/26 预设结果覆盖 | 不是用户任务完成率 |
| 自动化测试 | 2026-07-28 基线为 120 项后端测试通过 | 不证明易用性、性能或持续使用 |
| 实现快照 | 14 张当前页面与状态截图 | 不证明用户理解或真实效果 |

### 1.8 名词术语

| 术语 | 定义 |
|---|---|
| 演示快照 | 用于稳定演示的确定性岗位数据，字段完整但不代表仍在招聘 |
| 公开 ATS | 企业使用的公开招聘系统 API；M0 验证过 Greenhouse 类型，海外默认源现已停用 |
| 收藏 | 保留可能性，不代表已经决定投递 |
| 待投递 | 已形成行动意图，但尚未创建正式投递记录 |
| 投递 | 已经在外部渠道完成申请，并进入 JobPulse 状态机 |
| 状态事件 | 一次投递阶段变化，如“已投递 → 测评/笔试” |
| 计划事件 | 未来要发生的面试、测评或材料提交，有计划时间且尚未完成 |
| 纠错 | 修复误操作产生的状态，必须保留纠错原因和事件历史 |
| 无回应关闭 | 长期无反馈后由用户确认的终态，不等同于公司明确拒绝 |

## 二、用户角色描述

### 2.1 角色划分原则

产品角色按会改变页面、默认入口、提示和验收规则的行为状态划分，不按学校、年龄、专业或招聘季节划分。

会改变产品行为的差异：

- 当前是在筛选机会、准备行动，还是维护已经发生的投递；
- 是否已有投递和未来计划事件；
- 当前投递是否进行中或已结束；
- 是否需要回看历史和复盘。

不直接成为产品角色的市场标签：

- 应届生、实习生、产品经理、开发者；
- 高频海投、定向求职等人群描述；
- 985/211、城市、年龄等人口属性。

这些标签可用于招募和市场分析，但只有当它们改变页面或规则时，才进入产品角色。

### 2.2 角色表

| 角色 ID | 名称 | 进入条件 | 核心目标 | 产品策略 | 退出条件 |
|---|---|---|---|---|---|
| R-01 | 机会筛选者 | 进入岗位库，尚未形成明确行动 | 找到可信、值得继续处理的岗位 | 强调来源、时效、结构化信息；允许收藏和待投递独立存在 | 创建正式投递或离开 |
| R-02 | 行动准备者 | 至少有一个收藏或待投递岗位 | 把“可能”转成明确行动 | 双清单、低成本切换、从待投递建立投递 | 建立投递或取消意图 |
| R-03 | 进展维护者 | 至少有一个进行中投递 | 用最少操作记录进展和下一步 | 快捷状态、通知解析、计划事件、批量操作、时间线 | 投递进入终态 |
| R-04 | 回看复盘者 | 有已结束投递或阶段性暂停求职 | 找回历史、理解进展并决定下一步 | 状态历史、累计漏斗、近期安排和重新发现入口 | 开始新一轮筛选或行动 |

一个用户会在这些角色之间迁移，同一用户也可能同时拥有多个岗位对象，因此角色描述的是“当前任务状态”，不是永久身份。

### 2.3 市场人群与产品角色映射

| 市场 / 研究分群 | 主要产品角色 | 次要产品角色 | 说明 |
|---|---|---|---|
| 高频跨平台维护者 | R-02、R-03 | R-01、R-04 | 核心闭环覆盖最完整 |
| 定向机会监控者 | R-01、R-02 | R-03 | 订阅价值可能较高，但通知尚未交付 |
| 复盘再投者 | R-04 | R-01 | 是生命周期阶段，不是独立永久画像 |
| 低维护意愿者 | R-03（仅关键行动） | 无 | 是产品边界角色；若仍需大量手工维护，产品价值不成立 |

    R01 -->|收藏或加入待投递| R02["R-02 行动准备者"]
    R02 -->|建立正式投递| R03["R-03 进展维护者"]
    R03 -->|投递进入终态| R04["R-04 回看复盘者"]

### 2.5 角色体验矩阵

| 体验环节 | R-01 机会筛选者 | R-02 行动准备者 | R-03 进展维护者 | R-04 回看复盘者 |
|---|---|---|---|---|
| 默认入口 | 岗位列表 | 收藏与待投递 | 投递进展 / 近期安排 | 求职概览 |
| 首要信息 | 来源、更新、岗位要求 | 意图类型、截止时间 | 当前状态、下一步时间 | 历史状态、累计到达 |
| 主要动作 | 筛选、收藏、待投递 | 切换意图、建立投递 | 更新状态、解析通知、补录 | 查看历史、重新发现 |
| 主要风险 | 误信快照仍有效 | 收藏与待投递混淆 | 维护成本、误操作、时间错误 | 不完整数据导致误导 |
| 成功信号 | 找到并保留目标岗位 | 把一个岗位转成投递 | 关键进展和时间被记录 | 能回答“到哪一步、下一步是什么” |

## 三、产品概述

### 3.1 产品目标

1. 让用户在一个工作台中完成从岗位发现到下一步行动的闭环；
2. 降低状态、通知和日程之间的重复录入；
3. 保留来源、状态和事件历史，避免“自动化但不可解释”；
4. 用 M0 Demo 验证产品逻辑和研究问题，不把作品集演示包装成生产 SaaS。

### 3.2 成功指标

#### 3.2.1 未来真实产品实验目标

| KR | 指标与计算口径 | 研究门槛 | 判定 |
|---|---|---|---|
| KR-01 | 核心闭环完成率 = 独立完成“发现→待投递→投递→状态更新”的人数 / 参与人数 | 5 名目标参与者 | 至少 4/5 无关键帮助完成 |
| KR-02 | 通知到行动完成率 = 独立完成“粘贴→理解建议→确认→在近期安排找回”的人数 / 参与人数 | 5 名目标参与者 | 至少 4/5 完成，且无人误以为系统已自动执行 |
| KR-03 | 维护持续性 = 7 天内至少 3 天记录真实进展的人数 / 试用人数 | 3–5 名目标参与者 | 至少 60%；不足则优先降低维护成本 |
| KR-04 | 迁移信号 = 明确愿意替换或补充现有表格/邮箱方案的人数 / 访谈人数 | 5–8 次真人访谈 | 达到 60% 才讨论 M1 |
| KR-05 | 时间准确率 = 正确提取且经用户确认的明确时间 / 含明确时间样本 | 至少 30 条脱敏样本 | 目标 ≥90%，低置信度必须提示 |

这些是研究目标，不是已取得结果。样本小，只用于发现阻塞问题和决定是否继续，不用于推断市场总体。

#### 3.2.2 当前已取得结果

- 当前可演示闭环已通过自动化和专家走查；
- 2026-07-28 基线：120 项后端测试通过，前端 lint/build 通过；
- 24 条演示快照可离线复现；
- 核心专家走查覆盖 19/23，全部覆盖 20/26；
- 390×844 核心路由无横向溢出。

#### 3.2.3 尚未验证的假设

- 用户愿意离开或补充现有表格；
- 用户愿意连续维护状态；
- 通知解析会显著降低维护成本；
- 看板会改变求职策略；
- 订阅规则会带来持续使用；
- 用户存在付费意愿。

### 3.6 功能摘要与优先级

| 功能 ID | 功能 | 用户价值 | 实施复杂度 | 优先级 | 当前状态 |
|---|---|---:|---:|---:|---|

### 4.3 F-03 投递状态与事件时间线（P0）

| 项目 | 内容 |

| 目标 | 让 R-03 可追溯地推进投递，并在误操作时恢复 |

#### 4.3.2 业务规则

- `F03-FR-01`：投递初始状态为 `applied`，创建时同步写入初始状态事件。
- `F03-FR-02`：常规流转只能前进；进行中状态可进入公司拒绝、无回应关闭或主动撤回。
- `F03-FR-03`：`interviewing → interviewing` 是唯一常规自环，用于多轮面试。
- `F03-FR-04`：终态不可常规流转；纠错必须使用 `is_correction=true` 并填写原因。
- `F03-FR-05`：纠错写独立事件，不覆盖或删除原事件；漏斗排除纠错事件。
- `F03-FR-06`：同一岗位同时最多一个非终态投递。
- `F03-FR-07`：单条状态更新与对应状态事件在同一事务中提交。
- `F03-FR-08`：批量更新按条独立事务执行，允许部分成功，必须返回逐项失败原因。

#### 4.3.3 页面与结构

- 投递列表：阶段概览、全部/进行中/已结束、单条更新、批量选择、库外补录入口。
- 投递详情：关联岗位、合法下一状态、通知解析、即将到来、历史时间线。
- **目标缺口**：终态详情需增加“纠正状态”入口；当前高保真未覆盖。

#### 4.3.4 状态与异常

| 场景 | 要求 |
|---|---|
| 空列表 | 分筛选展示“当前筛选下没有投递记录” |
| 非法流转 | 不改变状态，显示原状态、目标状态和可行动建议 |
| 终态 | 隐藏常规更新，显示流程已结束和纠错入口 |
| 纠错 | 二次确认、必填原因、成功后显示纠错标识 |
| 批量部分失败 | 保留成功结果；展示失败对象和原因，不只显示总数 |
| 并发冲突 | 返回冲突，页面刷新当前状态后要求用户重试 |
| 服务失败 | 不乐观写入；保留选择，允许重试或取消 |

#### 4.3.5 交互规则

- 单条下拉只展示当前状态允许的目标状态。
- 终态和纠错不能混在普通快速更新中。
- 批量更新前显示目标状态和选中数量；不可逆终态要求二次确认。
- 返回操作优先回到来源页面；无历史时回投递列表。

#### 4.3.6 数据、持久化与事件

核心对象为 `Application` 和 `ApplicationEvent`。状态事件包含 `from_status`、`to_status`、`occurred_at`、`is_correction`、`correction_reason`。事件只追加，不因页面刷新重建。

目标分析事件：`application_created`、`application_status_changed`、`application_batch_changed`、`application_correction_started`、`application_corrected`。禁止采集备注全文和招聘通知全文。

#### 4.3.7 验收标准

- `F03-AC-01`：创建投递后，投递状态为已投递，时间线有“未记录 → 已投递”事件。
- `F03-AC-02`：所有合法流转成功，非法回退返回错误且不写新事件。
- `F03-AC-03`：面试中可自环，若填写轮次则为 1–20。
- `F03-AC-04`：终态普通更新被拒绝；纠错缺少原因时被拒绝。
- `F03-AC-05`：纠错成功后当前状态更新，原事件仍在，新增事件带纠错原因。
- `F03-AC-06`：同一岗位已有进行中投递时，再次创建返回已有记录冲突。
- `F03-AC-07`：批量更新部分失败时，响应列出成功 ID、失败 ID 和原因。
- `F03-AC-08`：页面刷新后状态与时间线一致；漏斗不计纠错事件。
- `F03-AC-09`：前端纠错入口完成前，本模块不得标记为“完整交付”。

### 4.4 F-04 通知解析与近期安排（P0）

| 项目 | 内容 |

#### 4.4.1 业务规则

- `F04-FR-01`：解析端点只返回建议，不更新状态、不写事件。

- `F04-FR-06`：状态与计划事件类型不一致时整笔拒绝，不留部分更新。
- `F04-FR-07`：未匹配唯一投递时，只能使用当前详情页投递作为确认对象，不自动创建未知投递。

- 近期安排页：按计划时间升序，显示类型、轮次、公司、岗位、时间和剩余天数。

#### 4.4.4 状态与异常

- 空输入时解析按钮禁用；输入最多 10,000 字符。
- 解析中禁用重复请求；新解析清空旧结果和旧错误。
- 无法解析时提示“未能解析出有效信息”，不展示确认按钮。
- 低置信度和正则降级必须可见，不能伪装成高确定性 AI。
- 计划时间在过去时在时间线标“已过期”，不进入未来待办。
- 确认失败保留解析结果和输入，允许用户修正或改用手动流转。

#### 4.4.5 交互规则

- 确认按钮文案必须包含目标投递、目标状态以及是否加入近期安排。
- 确认前页面需显示“AI 结果仅为建议”。
- 移动端输入区与确认按钮不得被底部导航遮挡。
- 本期不读取剪贴板、邮箱或通知权限；只有用户主动粘贴。

#### 4.4.6 数据、持久化与事件

通知原文仅作为单次请求输入，本期不写数据库。确认后只保存结构化状态、计划时间、轮次和“由招聘通知确认”备注。

目标分析事件：`notification_parse_requested`、`notification_parse_succeeded`、`notification_parse_failed`、`notification_suggestion_confirmed`、`schedule_created`。禁止采集通知全文、邮箱地址、电话、联系人原文和附件。

#### 4.4.7 验收标准

- `F04-AC-01`：解析但未确认时，投递状态、事件数量和近期安排均不变化。
- `F04-AC-02`：含公司、岗位、面试状态和明确时间的文本能展示结构化建议。
- `F04-AC-03`：确认面试建议后，状态事件与面试计划事件同时写入；任一失败则全部回滚。
- `F04-AC-04`：确认测评建议时只能创建 `test` 计划事件；类型不符返回校验错误。
- `F04-AC-05`：无完整时间的通知不创建计划事件。
- `F04-AC-06`：未匹配唯一投递时，页面明确显示将使用当前投递。
- `F04-AC-07`：同一计划事件同时出现在详情时间线和近期安排，时间、公司和岗位一致。
- `F04-AC-08`：解析失败后可以修改原文并重试，失败不会留下事件。

#### 4.4.8 依赖

AI/正则解析器、匹配器、F-03 状态机、计划事件服务、F-07 不依赖。

## 五、其他产品需求

### 5.1 性能与响应目标

以下是目标口径，不是现有生产性能结论。

| 指标 | 目标 | 验收环境 | 方法 |
|---|---:|---|---|
| 核心页面首次可交互 | ≤2 秒 | 本地 API、24–1000 条岗位、桌面 Chrome 最新版 | 5 次冷启动取中位数 |
| 筛选响应 | ≤500 毫秒 | 同上，组合 3 个条件 | 从提交到结果稳定 |
| 状态更新 | ≤1 秒 | 本地 API、单条投递 | 从确认到成功反馈 |
| 通知解析（正则降级） | ≤1 秒 | 10,000 字符以内 | 从提交到结果展示 |
| 看板聚合 | ≤1 秒 | 10,000 条岗位、1,000 条投递、10,000 条事件 | API P95 |
| 公开 ATS 单源采集 | ≤60 秒 | 来源可访问、最多 15 条相关岗位 | 服务日志 |

网络、来源站点或 LLM 不可用时必须触发降级/失败状态，不能为了满足时间目标返回伪成功。

### 5.2 监控与分析需求

#### 5.2.1 业务可观测性

- 状态流转成功率、非法流转和冲突需要可追踪；
- 解析需要区分 LLM 与正则降级，并统计解析/确认漏斗；
- 采集需要按来源记录成功、失败、跳过和耗时；
- 任何分析都不得把演示快照或专家走查写成真实用户使用。

#### 5.2.2 事件命名与最小参数

| 事件组 | 事件 | 必要参数 | 禁止采集 |
|---|---|---|---|
| 发现 | `job_search_applied` | 条件是否存在、结果数 | 搜索原文、完整 JD |
| 意图 | `job_favorited`、`job_to_apply_added` | job_id、source_kind | 岗位原文 |
| 投递 | `application_created`、`application_status_changed` | application_id、from/to、是否批量 | 用户备注原文 |
| 解析 | `notification_parse_succeeded`、`notification_suggestion_confirmed` | 是否降级、置信度区间、是否含时间 | 通知全文、邮箱、电话 |
| 计划 | `schedule_created` | event_type、是否有轮次 | 备注原文 |
| 订阅 | `subscription_created` | 填写了哪些条件 | 条件原文 |
| 采集 | `crawl_succeeded`、`crawl_failed` | source、count、duration | 凭据、Cookie |

当前项目未建立生产分析系统。上述事件是后续真实验证的目标需求，未实现前不得声称有留存或转化数据。

### 5.4 无障碍要求

- 所有核心操作可用键盘完成，焦点顺序符合视觉顺序；
- 焦点指示不能仅依赖浏览器默认且不可见；
- 状态不只依赖颜色，同时使用文案、图标或形状；
- 表单错误与字段关联，动态反馈使用 `role=alert` 或适当的 live region；
- 移动端主要触控目标不少于 44×44 CSS px；
- 正文、按钮和状态标签满足 WCAG AA 对比度目标；
- 弹层、抽屉或确认框出现时，焦点进入并被限制在容器中，关闭后回到触发点；
- 当前页面主要使用内联表单，没有通用 Modal；新增纠错/删除确认时必须按上述规则实现。

### 5.5 数据、安全与隐私

| 主题 | 本期要求 |
|---|---|
| 用户数据 | M0 无账号和用户隔离；公开 Demo 的数据可能被其他访客看到或重置 |

| 输入校验 | 使用参数化查询、长度限制、URL 协议校验和枚举校验 |
| 重置 Demo | 连续两次确认；生产/非演示环境必须可关闭 |
| 采集合规 | 只访问公开来源，遵守 robots/限速，不绕过登录、验证码和反爬 |
| 日志 | 不记录密钥、Cookie、通知全文或用户备注全文 |
| 数据删除 | M0 没有个人账号删除能力；进入 M1 前必须补数据导出、删除和撤权 |

### 5.6 内容与国际化

- V2.0 界面与交付语言为简体中文；
- 状态、事件和错误使用稳定英文 code 持久化，中文只在应用层显示；
- 日期在数据层使用 ISO 8601，界面按本地时区显示；
- Offer、JD、ATS 等英文术语首次出现时提供中文说明；
- 公开岗位原文可以是英文，但产品控制和错误信息保持简体中文；
- 进入多语言版本前不得把中文文案硬编码到状态或数据库约束中。

### 5.7 降级与恢复

| 故障 | 降级 | 恢复 |
|---|---|---|
| LLM 不可用 | 本地正则并显示“正则降级” | 配置恢复后不重跑已确认事件 |
| 公开来源不可用 | 记录失败，保留已有岗位和演示快照 | 下次手动/定时采集 |
| 后端不可用 | 页面显示离线/错误和重试 | 后端恢复后重新请求 |
| 状态+计划写入失败 | 整笔回滚 | 保留解析建议，用户重试 |
| 批量部分失败 | 成功项提交，失败项列明原因 | 用户只重试失败项 |
| 本地数据损坏 | 停止写入并提示恢复 | Demo 可重置；真实版本需备份/导出方案 |
| 误操作 | 纠错事件，不删除历史 | 前端纠错入口完成后可用 |

### 5.8 发布与回退

| 阶段 | 相对周期 | 进入条件 | 退出条件 |
|---|---|---|---|
| PRD 评审 | 1–2 个工作日 | V2.0 文档、原型和审计完成 | D-01 至 D-04 有明确决策 |
| P0 缺口修复 | 2–4 个工作日 | 评审通过 | 纠错 UI、批量失败详情等阻塞项关闭 |
| 回归与文档同步 | 1–2 个工作日 | 代码冻结 | 自动化、桌面和移动端回归通过 |
| 真人可用性测试 | 1–2 周 | 演示环境稳定、招募完成 | 5 名目标参与者完成核心任务 |
| 7 天持续试用 | 1 周 | 可用性阻塞项关闭 | 获得维护持续性信号 |

回退原则：

- 状态机、事件结构和数据迁移变化必须先备份；
- 无法安全迁移时保留旧 code 的只读兼容，不直接删除；
- 影响公开 Demo 的发布需保留上一可用版本和确定性数据重置方式。

### 6.4 需求变更门槛

以下变化必须更新 PRD 版本并跨职能评审：

- 增删 P0 功能或改变本期/未来边界；
- 改变产品角色、默认入口或关键任务流程；
- 改变 9 状态 code、终态、合法流转或事件语义；
- 改变通知文本的存储/传输边界；
- 引入邮箱、日历、账号、支付、团队或外部通知；
- 改变采集来源合规策略；
- 改变会影响历史数据的表结构或唯一约束。

文案修正、非关键视觉微调和不改变行为的无障碍修复可以走小版本，但仍需相关回归。
