# JobPulse 国内校招数据源策略

| 属性 | 内容 |
|---|---|
| 版本 | V1.2 |
| 决策日期 | 2026-08-18 |
| 产品范围 | 中国大陆校招、春招、秋招与实习机会 |
| 优先级 | 官方招聘信息 P0；招聘平台补充 P2 |
| 技术方案 | [国内校招采集架构](../architecture/domestic-campus-ingestion.md) |

## 1. 决策摘要

JobPulse 不再把海外公开 ATS 岗位当作默认实时数据。岗位供给改为“国内校招、官方优先、公告与岗位分层、覆盖率可度量”：

1. 先覆盖企业官方招聘官网、官方校招专题、官方公告和公开 ATS；
2. 再用教育部、人社部门、国聘、高校就业网等可信公共渠道发现和交叉核验；
3. 公众号用于发现官方招聘公告，但不把“抓遍所有公众号”当作可承诺能力；
4. BOSS、猎聘等平台不做未经授权的批量爬取，只在获得书面授权、官方接口或数据合作后接入；
5. 目标公司池内直接覆盖官方发布的全部校招岗位，采集时不按岗位方向筛选、不设置单源岗位数量上限；
6. 每条信息保留原始来源、官方链接、核验时间和证据，聚合平台信息不得覆盖官方事实。

“全部收录”在产品上定义为：

> 在已公布的目标公司池内，对公开可访问且允许收集的官方招聘公告建立来源登记，并完整遍历官方招聘入口中公开展示的全部校招正式岗、毕业生项目和实习岗位；持续度量覆盖、健康、岗位对账和发现延迟，但不宣称覆盖无法定义边界的“全网所有公司”。

第一阶段建议以 100 家目标公司为公司池，完成后再扩展到 300/1000 家。公司池名单按用户订阅需求、校招规模和行业代表性共同决定。

## 2. 校招分类口径

日历年份和毕业届别必须分开保存，避免把“2027 届春招”和“2027 年春季发布”混为一件事。

| 维度 | 建议值 | 例子 |
|---|---|---|
| `recruitment_type` | `campus_full_time` / `internship` / `graduate_program` / `unknown` | 校招正式岗、实习生、管培生、待确认 |
| `season` | `autumn` / `spring` / `early` / `makeup` / `rolling` / `unknown` | 秋招、春招、提前批、补录、滚动招聘 |
| `campaign_year` | 四位年份 | 2026 年启动的招聘活动 |
| `CampaignGraduationYear` | 关联表中的多值年份 | `[2027, 2028]`，不可只保留一个年份 |
| `internship_type` | `not_applicable` / `summer` / `daily` / `winter` / `unknown` | 非实习、暑期实习、日常实习、寒假实习 |
| `job_category` | `technology` / `product` / `design` / `operations` / `marketing` / `sales` / `business` / `supply_chain` / `manufacturing` / `finance` / `legal` / `hr` / `administration` / `research` / `medical` / `education` / `customer_service` / `other` / `unknown` | 技术、产品、职能、生产制造等；未知类别仍保留 |
| `campaign.status` | `upcoming` / `active` / `closed` / `unknown` | 即将开始、开放申请、关闭、待确认 |
| `position.status` | `open` / `closed` / `unknown` | 岗位开放、关闭、待确认 |

推荐给用户展示组合标签，例如“2027 届秋招”“2028 届暑期实习”“日常实习 · 2027/2028 届”“2027 届春招补录”。无法从原文确认时显示“届别待确认”，不得根据当前日期猜测。

## 3. 信息对象分层

招聘公告、招聘活动、公共岗位引用和用户收藏后的完整岗位不是同一对象：

- `Company`：公司主数据与集团/分支关系；
- `RecruitmentCampaign`：一次招聘活动，例如“某公司 2027 届秋季校园招聘”；公告先出现、岗位尚未开放时也可以建立；
- `CampaignGraduationYear`：活动面向的一个或多个毕业届别，支持跨 SQLite/PostgreSQL 筛选；
- `ObservedPositionRef`：公共轻量岗位引用，只保存身份、标题、城市、分类与生命周期，不保存完整 JD；
- `SourceSnapshot`：一次来源观测及完整性证据；只有有效快照参与差分；
- `CompanyChangeEvent`：可回溯到来源快照的公司级变化事实，驱动首页统计；
- 私人 `Job`：用户主动收藏后保存的完整岗位快照，后续增加 owner 归属并关联公共引用。

公告 URL、标题、时间与分类证据先作为活动/快照证据保存；多公告关系与人工复核队列在公告发现故事中单独扩展，不能为了填表而伪造岗位。

## 4. 数据源优先级

| 层级 | 来源 | 作用 | 产品规则 |
|---|---|---|---|
| S0 | 企业公开 API、RSS、结构化 feed | 最稳定的岗位明细 | 逐源评估并优先接入 |
| S1 | 企业官方招聘官网、校招专题、官方 ATS 页面 | 公告和岗位的主要事实源 | P0，来源注册后按模板族采集 |
| S2 | 企业官网新闻、官方公众号文章、高校就业网、政府就业平台 | 发现活动、补录和宣讲信息 | P0 发现层；尽量回链企业官方申请页 |
| S3 | 获得授权的聚合平台/API/数据合作 | 扩大职位覆盖 | 有合同、授权范围和数据保留规则后接入 |
| S4 | 用户手工保存的 BOSS/猎聘等链接 | 个人追踪与补充 | 私人数据；不进入公共岗位目录 |

权威性冲突时顺序为 `企业官方 > 政府/高校官方转载 > 获授权平台 > 用户输入`。平台信息可补全薪资或活跃度等非官方字段，但不得覆盖官方截止时间、届别、申请入口和关闭状态。

## 5. 官方信息怎么收全

### 5.1 建立目标公司池，而不是直接爬“全网”

每家公司先建立 `CompanySourceRegistry`：

- 企业标准名称、别名、统一社会信用代码（可得时）和官方域名；
- 招聘主页、校招主页、公告页、职位列表页、公众号名称与已核验账号主体；
- 使用的 ATS 模板族、允许访问状态、检查日期和证据；
- 预期刷新频率、最近成功时间、最近发现时间、解析器版本和健康状态；
- 采集范围：官方发布的全部校招正式岗、毕业生项目和实习岗位，以及春招、秋招、补录、届别和城市信息。

只有注册并审核过的 URL 才能进入调度器。用户提交的新公司或链接先进入“来源候选池”，由发现任务和人工复核补齐来源登记。

### 5.2 官网与 ATS 采用“模板族 + 公司配置”

不为每家公司从零写一个爬虫，而是优先识别常见模板族：企业自建站、Moka、北森、用友大易及其他实际出现的 ATS。每个模板族提供列表、详情、分页、关闭状态和字段映射；每家公司只保存域名、入口、活动范围与少量差异配置。

正式采集使用“完整遍历”契约：

- 遍历所有分页、游标、部门、岗位族、城市和招聘项目入口，直到来源明确结束；
- 采集层不得配置岗位关键词白名单、岗位方向过滤或 `max_jobs` 数量上限；
- 无法识别岗位类别时保存为 `unknown/other` 并进入分类复核，不能丢弃原岗位；
- 来源提供岗位总数时，必须对账 `source_total = persisted + excluded_by_reason + parse_failed`；不提供总数时，以分页穷尽、首尾页证据和人工抽检确认完整性；
- 只允许按有记录的原因排除国外岗位、纯社招、禁止访问内容或无法形成最小有效记录的数据，不得静默丢弃。

遇到动态页面时优先寻找页面自身公开调用的结构化接口；只有在条款和 robots 允许、且没有稳定结构化入口时才使用受限频率的浏览器渲染。不得通过代理池、验证码绕过、登录态共享或伪装用户规避限制。

### 5.3 公告发现采用多信号，不把搜索结果当最终事实

发现任务监听：

- 官方招聘页、官网新闻/公告页、站点地图和公开 feed；
- 目标公司官方公众号的已知公开文章链接；
- 国家大学生就业服务平台、人社公共招聘平台、国聘和高校就业网的公告线索；
- 用户提交的官方招聘链接。

发现到新 URL 后先判断公司、来源权威性和招聘类型，再进入解析与人工抽检。搜索引擎摘要只用于发现，不直接作为岗位正文或截止时间来源。

### 5.4 公众号的现实方案

公众号没有可供第三方检索“全网所有企业文章”的通用开放接口，因此分三步做：

1. 维护目标公司的官方公众号清单和主体核验结果；
2. 接收人工运营、用户提交或可信公共渠道发现的公开文章 URL，保存标题、发布日期、官方链接、摘要和结构化招聘字段；
3. 当规模扩大且官网确实无法覆盖时，再评估获得授权的内容监测服务。

不自动登录微信、不自动化搜索微信客户端、不绕过访问控制；默认不复制保存完整文章，只保留完成招聘核验所需的结构化事实和原文链接。

## 6. BOSS、猎聘等平台的处理

BOSS 用户协议明确把未经许可使用爬虫、拟人程序等读取或转存平台内容定义为非法获取；猎聘用户协议也明确禁止以程序或非正常浏览等技术手段抓取、读取、复制或转存平台数据。因此：

- 当前 `BossAdapter` 保持禁用和空实现；不新增猎聘批量采集器；
- 不把“降低频率、轮换 UA、代理池”当作合规方案；
- 只接受官方 API、书面授权或数据合作；
- 用户可以手工保存职位链接和自己的投递记录，但它们默认属于私人数据；
- 浏览器扩展对 BOSS、猎聘域名默认只允许“保存当前 URL + 手工补字段”，是否连当前页字段也自动读取需在获得明确许可后再决定。

平台接入是 P2 加分项，不能阻塞官方校招数据主干。

## 7. 去重、核验与更新

### 7.1 去重

- 同源优先使用官方 `external_job_id`、公告 ID 或规范 URL；
- 跨源使用公司实体 + 活动届别 + 招聘季 + 规范化标题/地点形成候选组；
- 跨源合并后仍保留各自 `ObservedPositionRef`、`SourceSnapshot` 与事件证据，不删除冲突事实；
- 多城市、多届别岗位不得因标题相同被错误合并。

### 7.2 核验

- 官方 URL 可访问且字段一致时标记 `official_verified`；
- 只有公共平台/高校转载时标记 `secondary_verified`，并继续寻找官方申请页；
- 截止时间、届别或招聘类型冲突时进入人工队列；
- 来源失效不立即删除记录，先标记 `stale` 或 `closed_candidate`，复核后关闭。

## 8. 覆盖率与服务指标

“采集成功条数”不是主指标，使用以下口径：

| 指标 | 试点目标 |
|---|---:|
| 目标公司来源登记覆盖率 | 100% 的试点公司至少登记一个已核验官方招聘入口 |
| 健康来源覆盖率 | ≥95% 的高优先级来源在预期窗口内成功检查 |
| 官方活动发现率 | ≥95%，基于每周人工审计样本计算，不自称理论全量 |
| 已审计官方职位页岗位对账率 | 100%，源端可见岗位均进入岗位库、隔离区或带原因的失败队列 |
| 高峰期发现延迟 | P95 ≤24 小时 |
| 官方链接保留率 | 100% |
| 届别/招聘类型可确认率 | ≥90%，其余明确显示待确认 |
| 失效状态复核延迟 | P95 ≤48 小时 |

覆盖看板必须可以按公司、来源类型、秋招/春招/实习、毕业届别和时间区间下钻，并公开展示缺口，而不是只展示累计岗位数。

## 9. 实施顺序

### D0：停止错误供给（立即）

- 停用 Figma、Webflow、Intercom、Stripe 等海外默认源；
- 保留 Greenhouse 适配器代码作为历史链路验证能力，但不进入国内实时岗位；
- 不自动删除已有海外数据，先标记/隔离，提供可回退清理任务。

### D1：100 家公司官方公告试点（第一开发批次）

- 确认公司池与行业配额；
- 建立来源注册表、活动/公告模型和校招分类；
- 先完成 3 个高复用 ATS 模板族和 10 个高优先级自建站；
- 建立人工核验队列与覆盖看板；
- 在一个秋招/春招周样本上评估发现率和延迟。

### D2：扩大岗位明细与订阅

- 将公告关联到职位列表和具体申请页，完整遍历目标公司公开的全部校招岗位；
- 扩展到 300 家目标公司；
- 采集层不按岗位方向缩减数据；用户侧按届别、实习类型、城市与岗位方向筛选和订阅；
- 来源不健康时停止发送“无新增”结论。

### D3：公众号与授权平台补充

- 扩展官方账号清单和文章发现入口；
- 评估授权内容监测或招聘平台合作；
- 只有授权完成后才把平台岗位放入公共目录。

## 10. 已确认与待共同决定的产品参数

已确认：目标公司池内收录官方发布的全部校招岗位，采集层不做岗位方向筛选或数量截断。

仍需共同决定：

1. 首批 100 家公司的行业配额和具体名单；
2. 用户看到的时效承诺是 24 小时内还是每日固定批次更新。

在公司池名单确定前，可以先完成数据模型、来源注册表和 10 家技术样本；“全部岗位”只对已经登记且通过完整性验收的官方来源成立。
