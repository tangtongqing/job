## 一、三阶段演进总览

```mermaid
graph LR
    M0[M0 · Demo<br/>当前] --> M1[M1 · Pro SaaS]
    M1 --> M2[M2 · Team 版]

    M0 -.->|架构预留| M1
    M1 -.->|真实实现| M2
```

| 里程碑 | 形态 | 鉴权 | 数据库 | 计费 | 采集 | 目标 |
|--------|------|------|--------|------|------|------|
| **M0 Demo**（现在） | 单用户本地 | 无 | SQLite | 无 | 公开源+低频 | 作品集交付、路径 B 验证 |
| **M1 Pro SaaS** | 多用户云 | OAuth | PostgreSQL | 订阅 | 合规采集 + API 优先 | 副业试水、真实获客验证 |
| **M2 Team 版** | 组织/角色 | RBAC | PostgreSQL | 团队席位 | 同 M1 + 团队共享 | 求职社群/辅导机构场景 |

> **演进纪律**：M0→M1 的切换**必须**由路径 B 验证窗口触发（market-analysis.md v3 的 5-8 次访谈 + 3-5 次原型测试 + 作者本人真实投递，证明有人愿意持续用）。无验证信号，不升级。

## 二、M0 · Demo（当前，路径 B）

**已在 PROJECT.md v4 充分定义，此处只列演进相关要点。**

### 2.1 M0 交付边界
- ✅ 产品面 5 页 + 营销面 2 页（落地页 + 定价页）
- ✅ SQLite + 单用户 + 无鉴权
- ✅ 公开源采集 + 人工兜底数据
- ✅ 响应式 Web + PWA

### 2.2 M0 为 M1 留的接缝（架构层，不实现）
1. **数据库**：7 张表 schema 标注「多租户预留字段位」（迁移注释，不加列）
2. **API**：按 `/public/*`、`/app/*`、`/admin/*` 三层命名空间组织（admin 层为空，位置留好）
3. **数据库抽象层**：`get_engine()` 已支持 SQLite/PostgreSQL 切换（system-architecture.md §7.4）
4. **配置**：`.env` 已支持 dev/demo/prod 切换
5. **采集合规**：robots.py + rate_limiter.py 已在 crawler 目录占位

> 这些接缝在 M0 的**成本几乎为零**（几行注释 + 命名规范），但让 M1 的升级是"增量"而非"重构"。这是架构前瞻性的作品集展示点。

## 三、M1 · Pro SaaS（演进目标一）

### 3.1 触发条件（必须全部满足才启动）
- [ ] 路径 B 验证窗口完成：5-8 次访谈中 ≥60% 确认持续使用意愿
- [ ] 作者本人真实投递场景跑通，证明核心闭环有价值
- [ ] 有明确的"愿意付费"信号（访谈中主动询问，非诱导）
- [ ] 采集合规评估通过（至少 2 个数据源可持续采集）

### 3.2 M1 能力增量

| 维度 | M0 | M1 增量 |
|------|----|---------| 
| 鉴权 | 无 | OAuth（GitHub/微信/邮箱）+ 单用户账号 |
| 数据库 | SQLite | PostgreSQL（迁移，复用 M0 抽象层） |
| 多租户 | 无 | tenant_id 列（从 M0 注释激活为真实列） |
| 计费 | 无 | Stripe 订阅（Free/Pro 两档） |
| 采集 | 公开源+低频+人工 | 合规 API 优先 + 官方 RSS + 降级爬虫 |
| 部署 | 本地 | Vercel（前端）+ 云服务器（后端+采集）+ 云 PG |
| AI 解析 | 本地 API Key | 服务端 API Key + 按账户配额 |
| 数据隔离 | 单库共享 | tenant_id 行级隔离（M1 单库多租户） |

### 3.3 M1 不做（留到 M2）
- ❌ 组织/团队概念（M1 还是个人 SaaS）
- ❌ admin 后台（M1 用数据库直连管理）
- ❌ RBAC（M1 只有 owner 单角色）

## 四、M2 · Team 版（演进目标二）

### 4.1 触发条件
- M1 运营 6-12 个月，出现"团队共享"真实需求信号（如求职辅导机构、校招互助社群主动询问）

### 4.2 M2 能力增量
- 组织（Organization）+ 成员角色（owner / admin / member）—— RBAC
- 共享看板（导师看学员投递进度）
- 团队席位计费
- admin 后台（组织管理、用量统计）
- 原生 App（iOS/Android）—— 仅当 M2 验证移动端高频使用后启动

## 五、付费分级策略（Pricing Tiers）

> **定位说明**（v5 修订，2026-06-30）：营销面已从「作品集展示型」转向「真实营销型」。以下分级按真实 SaaS 展示（CTA 用「免费开始」/「开始试用」），不再标注"作品集示意"。Demo 阶段不接支付，但展示语气与真实产品一致。

### 5.1 三档分级

| 档位 | 定价 | 定位 | 包含 | M0 Demo | M1 | M2 |
|------|------|------|------|---------|----|----|
| **Free** | ¥0 | 获客层 | 基础采集 + 投递管理（9 状态）+ DDL 提醒 + 基础看板 | ✅ Demo 即此层 | ✅ | ✅ |
| **Pro** | ¥29/月 | 主力变现 | Free 全部 + AI 解析额度（100 次/月）+ 多源订阅（5 条）+ 数据导出 + DDL 推送（邮件/微信）+ 有效进展趋势 | ⚠️ Demo 可体验（本地 API Key） | ✅ | ✅ |
| **Team** | ¥99/月/3 席位 | 团队场景 | Pro 全部 + 组织共享看板 + 成员管理 + 批量导入 | ❌ | ❌ | ✅ |

### 5.2 定价逻辑（非拍脑袋）

**为什么 Free 是获客层而非限制层**：
- 路径 B 验证的核心是"高频求职者愿意持续用"。Free 必须能跑通核心闭环，否则验证信号失真。
- 参照 Notion/Linear 的个人免费策略：工具型产品靠 Pro 的高阶能力变现，不靠卡核心功能。

**为什么 Pro 定 ¥29 而非更高**：
- 学生/应届群体价格敏感，¥29 是"一杯奶茶/月"的心理锚点
- 对标：Notion 个人 Pro $10/月、滴答清单高级版 ¥179/年——¥29/月处于同类工具合理区间
- M1 真实定价需 A/B 测试验证，此处仅作品集展示

**为什么 AI 解析是 Pro 核心卖点而非 Free**：
- F-C.5（邮件→AI 解析）是本项目最强差异化（移动端英雄功能）
- LLM 有真实边际成本（API 调用），不适合无限免费
- Free 用户用快捷交互层（手动选择）兜底，体验不崩

**Team 档的假设**：
- 求职辅导机构、校招互助社群是潜在 B 端场景
- 但 M0/M1 阶段无验证，Team 档是**远期选项**，定价仅占位

### 5.3 定价页 UI 要求（v5 真实营销型）
- 三档并排卡片，Free 居左，Pro 居中高亮（"最受欢迎"标签）
- 每档功能对比表，Pro 的 AI 解析额度/订阅数等关键差异点加粗
- 顶部标注「14 天免费试用全部 Pro 功能，无需信用卡」（真实营销语气）
- CTA：Free「免费开始」/ Pro「开始试用」/ Team「联系销售」

## 六、移动端策略（跨里程碑）

### 6.1 Demo（M0）：响应式 Web + PWA

| 维度 | 决策 | 理由 |
|------|------|------|
| 桌面（≥1024px） | 完整体验 | 看板/批量操作的主场景 |
| 平板（768-1024px） | 降级可用 | 筛选折叠、看板简化 |
| 手机（<768px） | 核心流程走得通 | **不投入精细打磨**，但投递管理 + F-C.5 AI 解析必须可用 |

**为什么手机优先保 F-C.5**：
- 求职邮件在手机收到，随手粘贴→AI 解析→状态更新，是移动端天然英雄功能
- 这个场景在桌面反而别扭（谁会在电脑上复制邮件再粘贴）

**PWA 配置**：
- 可加桌面（manifest.json）
- 简单离线壳（已访问过的投递列表 Service Worker 缓存）
- 成本极低，演示加分（面试官扫码即看）

### 6.2 原生 App（M2 后评估）
- **Demo 不做**：双代码库成本巨大，PM 作品集收益低，无真实用户验证
- **M2 启动条件**：M1 数据显示移动端 DAU 占比 >40% 且 AI 解析高频使用
- **若启动**：React Native（复用 Web 技能栈）而非原生
