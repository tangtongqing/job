# 阶段 1 评审建议

> 评审范围：`PROJECT.md`、`user-personas.md`、`pain-points-jtbd.md`、`market-analysis.md`，并补充检查 `PRD.md` 中的投递状态机。
>
> 评审结论：阶段 1 可有条件通过。建议先修正画像定位、MVP 优先级和状态机，再进入阶段 2 数据库设计。

## 一、用户画像

### 结论

- **P1 秋招海投型最接近核心用户**：跨平台、高频投递、状态混乱，痛点强且容易感知产品价值。
- **P2 实习定向型可信度最低**：同时存在“仅投 5–8 家”“岗位两小时招满”“收藏数日后再投”“需要转正率”等假设，场景拼接感较强，部分数据也难以可靠获得。
- **P3 春招复盘型的问题真实，但更像 P1 在秋招失败后的生命周期阶段**，不一定需要作为独立核心画像。

### 建议

将首批用户从季节性的“秋招海投型”改为行为分群：

> 近一个月跨 3 个以上渠道、累计投递 20 个以上岗位的高频求职者。

这样即使项目采用路径 B、到春招才形成完整 Demo，核心画像仍然成立。

### 当前遗漏的真实痛点

1. 收到邮件、微信或电话后，如何低成本更新投递状态。
2. 笔试、面试、材料提交等下一步行动、截止时间和日程冲突。
3. 岗位是否仍然有效、最后核验时间及官方来源。
4. 毕业年份、每周实习天数、实习周期、地点等硬条件筛选。
5. 记录投递渠道、简历版本、联系人和准备备注。
6. 长期没有回复时，如何合理结束投递流程。

其中，“用户是否愿意持续维护状态”是产品成立的关键风险。MVP 应增加一个关于低成本维护状态的 Job Story，而不只是把它作为待验证假设。

## 三、路径 B

### 结论

认同“作品集优先，不赶完整 Demo 的秋招时间窗”，但不建议把真实验证推迟到 2027 年春招。

建议将路径 B 调整为：

> 不赶增长窗口，但必须赶验证窗口。

### 2026 秋招期间建议完成

- 5–8 次目标用户访谈。
- 3–5 次原型可用性测试。
- 作者本人持续记录真实投递。
- 根据反馈调整画像、状态和功能优先级。

作品集 Demo 可以不追求用户规模，但不能没有真实用户证据。

## 四、投递状态机

### 当前文档问题

1. 状态表实际包含 8 个状态，部分正文和自检却写成 7 个。
2. Offer 包含 3 个相关状态，但“Offer-待回复”不是终态，只有“已接受”和“已拒绝”是终态。
3. 当前总终态实际为 4 个：Offer 已接受、Offer 已拒绝、公司拒绝、已撤回。
4. “Offer-已拒绝”容易与公司拒绝用户混淆，建议命名为“Offer-已婉拒”或 `offer_declined`。

### 推荐状态

建议采用 9 个状态：

| 类型 | 状态 |
|---|---|
| 进行中 | 已投递 |
| 进行中 | 测评/笔试 |
| 进行中 | 面试中 |
| 进行中 | Offer 待决定 |
| 终态 | 公司拒绝 |
| 终态 | 主动撤回 |
| 终态 | 无回应关闭 |
| 终态 | Offer 已接受 |
| 终态 | Offer 已婉拒 |

### 关键设计修正

#### 1. 新增“无回应关闭”

超时没有回复不等于公司明确拒绝，两者对漏斗和复盘的意义不同。

#### 2. 允许状态纠错

正常业务流转不可逆，但应提供“撤销上一步”或“纠正状态”操作，并保留完整日志。终态永久锁死会导致用户误操作后无法修复。

#### 3. 将阶段与事件分开

状态只表达当前求职阶段。笔试时间、面试轮次、DDL、完成情况等应进入独立的事件或待办表，避免状态数量失控。

#### 4. 消除重复字段

如果 `Application.status` 已经表达 Offer 结果，`offer_result` 应删除或改为派生字段，避免出现状态与结果互相矛盾的数据。

#### 5. 修正用户—岗位关系

`UserJobAction` 如果负责收藏和待投递，就不应同时保存“已投递”。创建 `Application` 后，应结束原关系记录，或让该表只保留收藏、待投递两种动作。
