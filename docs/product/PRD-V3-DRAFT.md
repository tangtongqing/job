## 1. 产品摘要

JobPulse 面向国内校招求职者，把分散在公司招聘官网、招聘公告和可信官方渠道中的招聘变化，整理为可追踪的公司招聘动态；当用户确认某个岗位值得行动时，再通过官方入口完成核验，并将感兴趣的岗位保存到私人工作台中持续管理。

产品由三个边界清晰但相互衔接的部分组成：

1. **公共招聘雷达**：回答“哪些目标公司最近开始招聘或发生了变化”；
2. **官方入口与私人承接**：回答“这条信息是否可信，以及如何把它变成我的下一步行动”；
3. **私人求职工作台**：回答“我现在进行到哪一步，下一步要做什么”。

V3 不以复制所有招聘平台的完整岗位库为目标。公司是持续监控单位，公开层优先保存招聘活动、岗位轻量引用、变化事件、来源与新鲜度；完整岗位信息只在用户明确选择后进入其私人空间。

## 2. 背景与问题

### 2.1 用户问题

- 校招信息分散在公司官网、公告和多个招聘渠道，用户难以持续判断哪些目标公司出现了新机会；
- “有岗位”不足以支持行动，用户还要判断招聘届别、招聘类型、发布时间、来源可信度和信息是否仍有效；
- 用户从公开信息进入投递后，通知、面试、截止时间和下一步行动又分散到邮件、短信、日历和个人表格；
- 现有聚合工具常提供静态岗位列表，但不一定清楚说明来源、覆盖范围、更新时间和失败状态。

### 2.2 项目问题

当前项目已经具备 M0 私人工作台的部分可运行能力，也形成了 M1 公司雷达的产品方案和部分公共数据底座，但两份 PRD 使用不同的入口、角色、数据对象和优先级。文档还混用了“原型已完成”“技术底座已实现”“用户功能已可用”和“用户价值已验证”。

因此，V3 首先要建立一套不会夸大项目成熟度的统一事实体系，再指导架构、原型和工程实施。

## 3. 目标、非目标与成功判断

### 3.1 产品目标

1. 让用户更早、更可靠地发现目标公司的校招变化；
2. 让用户能从公开变化直接进入官方来源完成核验；
3. 让用户只保存真正感兴趣的岗位，减少公共库中的无效完整 JD；
4. 让进入私人空间的机会有清晰状态、下一步和时间线；
5. 让系统在来源失败、信息不完整或数据过期时诚实降级。

### 3.2 当前非目标

- 不承诺覆盖全网所有公司和所有岗位；
- 不承诺实时抓取 BOSS 直聘、猎聘等受限平台的全部信息；
- 不绕过登录、验证码、反自动化措施或平台访问规则；
- 不把自动投递、简历代写、面试辅导或招聘交易作为当前核心；
- 不在缺乏用户证据时确定付费方案、价格或增长目标；
- 不为了“成熟产品”的形式提前引入组织租户、复杂 RBAC 或微服务。

### 3.3 成功判断框架

V3 的成功不以页面数量或抓取条目数量单独判断，而由三组证据共同决定：

| 证据层 | 核心问题 | A4 应挂接的证据 |
|---|---|---|
| 数据可信 | 目标公司是否被稳定监控，变化是否正确，失败是否可见 | 公司池审计、来源健康、快照/差分校验、人工复核记录 |
| 用户有效 | 用户是否理解变化、信任官方来源，并愿意保存或采取行动 | 可用性测试、访谈、行为记录、7 日跟踪 |
| 工程可交付 | 功能是否可重复运行，异常和权限是否有可验证处理 | 代码、接口、迁移、自动化测试、验收报告 |

具体阈值由 [用户验证计划](../research/user-validation-plan.md) 和 A4 的功能验收标准管理。历史测试数量和数据条数只能作为带日期的技术证据，不能代替用户价值证据。

## 4. 目标用户与核心任务

### 4.1 行为分群

| 分群 | 当前角色 | 主要行为 | 产品边界 |
|---|---|---|---|
| S1 目标公司机会监控者 | 首要切入用户 | 关注一组公司，定期判断招聘变化、届别和可信度 | 公共招聘雷达是首要价值 |

## 5. 价值主张与关键假设

### 5.1 价值主张

- 对 S1：把“到处翻招聘页”变成“查看目标公司今天发生了什么变化”；
- 对 S2：把“信息散落在通知和表格里”变成“每个机会都有状态、时间线和下一步”；
- 对所有用户：明确告诉用户信息来自哪里、什么时候检查过、哪里可能不完整，并始终提供官方核验入口。

### 5.2 待验证假设

| 假设 ID | 假设 | 当前证据状态 |
|---|---|---|
| H-R01 | 用户愿意围绕一组目标公司进行持续监控 | `validation_required` |
| H-R02 | 公司招聘变化比静态岗位列表更能触发有效行动 | `validation_required` |
| H-R03 | 来源、更新时间和覆盖说明能改善可信判断 | `validation_required` |
| H-L01 | 用户会从公共动态进入官方来源，并保存少量感兴趣岗位 | `validation_required` |
| H-W01 | 私人工作台比个人表格更能降低持续维护成本 | `validation_required` |
| H-W02 | 通知转下一步行动能产生持续使用价值 | `validation_required` |
| H-B01 | 极简记录方式能覆盖低维护人群而不过度增加复杂度 | `validation_required` |

## 6. 产品边界与核心流程

### 6.1 公共与私人数据边界

| 公共层 | 私人层 |
|---|---|
| 公司、招聘活动、岗位轻量引用、变化事件、来源、检查时间、数据健康 | 用户选择保存的岗位详情、意向、投递记录、通知、事件、待办和复盘 |
| 可用于发现、筛选、比较和官方核验 | 只属于登录用户，并按用户隔离 |
| 不以复制所有完整 JD 为目标 | 仅在用户主动选择后保存必要信息 |

### 6.2 主流程

```text
目标公司池
   ↓ 定时检查官方来源
有效快照 → 差分 → 公司招聘变化
   ↓
公共招聘动态 / 公司详情
   ↓ 查看来源、届别、招聘类型和新鲜度
官方招聘入口
   ↓ 用户主动选择
保存感兴趣岗位到私人空间
   ↓
意向 → 投递 → 通知/面试 → 下一步 → 结束/复盘
```

任何采集失败、来源受限或内容不完整都不得生成虚假的“无变化”；系统必须显示最后成功时间和当前健康状态。

### 6.3 目标信息架构

| 区域 | 目标入口 | 访问边界 | 当前说明 |
|---|---|---|---|
| 招聘动态 | `/updates` | 公共读取 | M1 目标入口，尚不能视为已实现 |
| 公司库/公司详情 | `/companies`、`/companies/:id` | 公共读取 | M1 目标能力 |
| 官方来源承接 | 外部官方 URL + 保存入口 | 公共核验；保存需登录 | 交互方案待验证 |
| 私人工作台 | `/workspace` 及子页面 | 登录后、用户隔离 | M0 已有部分能力，目标 IA 待 A4 统一 |
| 数据运营 | `/ops` | 运营权限 | 目标能力，不是普通用户界面 |

路由只表达目标信息架构，不代表工程现状。A4 必须为每个入口挂接当前路由、目标路由和迁移方式。

## 7. 需求记录规范

### 7.1 为什么拆成四个维度

“已实现”“P0”“用户已验证”“M1”回答的是四个不同问题。V3 禁止把它们压成一个状态字段。

| 维度 | 回答的问题 | 允许值 |
|---|---|---|
| 交付状态 `delivery_status` | 代码和用户链路做到哪里 | `implemented`、`implemented_gap`、`in_progress`、`approved_not_started`、`future_candidate`、`deprecated` |
| 证据状态 `evidence_status` | 用户价值证据做到哪里 | `validation_required`、`expert_only`、`user_validated` |
| 优先级 `priority` | 相对其他需求先做什么 | `User-P0`、`User-P1`、`User-P2`、`Ops-P0`、`Ops-P1` |
| 目标版本 `target_release` | 在哪个发布门槛中交付 | `current`、`M1.x`、`future`、`none` |

### 7.2 交付状态词典

| 状态 | 定义 | 写作规则 |
|---|---|---|
| `implemented` | 用户主链路和关键异常已实现，并有可复核技术证据 | 可写“当前可用”，必须附证据和已知限制 |
| `implemented_gap` | 有可运行部分，但关键状态、权限、异常或用户链路未闭合 | 必须明确“已经有”和“仍缺少” |
| `in_progress` | 已进入当前开发批次，但未满足完成定义 | 不得写成已上线；必须给执行入口 |
| `approved_not_started` | 方向已确认，但尚未开始形成完整用户能力 | 只能写目标和验收条件 |
| `future_candidate` | 值得研究但未承诺版本 | 不进入当前发布范围 |
| `deprecated` | 仅为历史兼容或追溯保留 | 不再作为当前产品卖点 |

### 7.3 证据状态词典

| 状态 | 定义 | 可使用的措辞 |
|---|---|---|
| `validation_required` | 尚无目标用户证据，或证据不足 | “待验证假设”“拟解决” |
| `expert_only` | 已有内部、专家、技术或启发式证据，但没有足够用户证据 | “通过内部检查”，不得写“用户需要” |
| `user_validated` | 已达到预先定义的用户研究门槛 | 必须链接研究记录、样本与结论边界 |

“功能已实现但价值待验证”应记录为 `implemented + validation_required`，两者不冲突。

### 7.4 优先级规则

- `User-P0`：当前核心用户价值链不可缺失；
- `User-P1`：明显改善体验，但不阻断首个闭环；
- `User-P2`：增强或规模化能力；
- `Ops-P0`：没有它就无法可信地提供 User-P0；
- `Ops-P1`：提升运营效率、覆盖和维护性。

优先级不是实现状态。数据采集、来源健康和人工复核可属于 `Ops-P0`，但不能在用户功能列表中伪装成已经实现的用户价值。

### 8.1 成熟产品的最小闭环

V3 的最小成熟闭环不是“把所有功能都做完”，而是同时满足：

1. 至少一批明确边界的国内目标公司可以稳定检查；
2. 公共页面能诚实展示变化、来源、新鲜度和失败状态；
3. 用户能从官方入口选择一个岗位进入自己的私人空间；
4. 私人记录有归属、状态、下一步、导出和删除边界；
5. 每个公开结论可追溯到来源快照，每个关键用户操作有验收证据。

## 9. 全局业务词典

### 9.1 招聘对象

| 术语 | V3 定义 |
|---|---|
| 目标公司池 | 按阶段维护的监控公司集合：10 家技术样本、约 30 家核心、约 100 家扩展；不是少数固定企业，也不是“全网所有公司” |
| 招聘活动 | 某公司面向一类人群和时间窗口开展的一次招聘，如 2027 届秋招、暑期实习、日常实习 |
| 岗位轻量引用 | 用于发现和导航的最小岗位信息，至少包含可识别标题、所属招聘活动、官方来源和检查时间；不等于完整 JD |
| 私人岗位 | 用户主动保存后，进入其私人空间并可补充完整信息、状态和行动的记录 |
| 官方来源 | 公司控制的招聘官网、官方 ATS 页面或可验证的正式招聘公告 |
| 补充来源 | 用于发现线索但需要回到官方来源核验的渠道 |

### 9.2 招聘分类

统一分类至少要表达两个独立维度：

- **招聘类型**：春招、秋招、暑期实习、日常实习、其他/待确认；
- **目标届别**：如 2027 届、2028 届、多个届别、不限、待确认。

不得只根据标题中的单个数字强制推断届别。自动分类必须保留原文证据、置信度和人工修正入口。A4 负责给出字段、枚举和回退规则。

### 9.3 变化与健康状态

| 术语 | 最小定义 |
|---|---|
| 首次有效快照 | 首次成功获取且通过最低校验的数据；只建立基线，不生成虚假“新增” |
| 新增公司 | 公司记录第一次进入可展示公司池；不等于当天开始招聘 |
| 开始招聘 | 公司从无有效招聘活动变为至少有一项有效活动 |
| 公司有更新 | 同一公司出现可解释的活动或岗位变化 |
| 系统新增岗位 | 与上一份有效快照相比新增的岗位轻量引用 |
| 系统关闭岗位 | 与上一份有效快照相比消失或被官方标记关闭的岗位引用；必须考虑采集失败 |
| 当前招聘公司 | 最新有效状态中至少有一项有效招聘活动的公司 |
| 数据过期 | 超过该来源允许的新鲜度阈值，不能把旧状态当作当前事实 |
| 部分覆盖 | 来源可访问但只取得部分页面、字段或地域，必须向用户披露 |

失败抓取不能更新“最后成功时间”，不能覆盖上一份有效快照，也不能直接生成岗位关闭事件。

## 10. 跨功能状态要求

每个用户页面和 API 至少要定义以下状态；未适用时必须解释原因：

| 状态 | 用户界面要求 | 数据/工程要求 |
|---|---|---|
| 加载中 | 显示正在获取什么，避免旧数据伪装成新数据 | 超时和取消可观测 |
| 首次无基线 | 说明仍在建立首次检查结果 | 不生成变化事件 |
| 成功且有变化 | 说明变化内容和比较时间 | 可追溯到两份有效快照 |
| 成功但无变化 | 显示最后成功检查时间 | 只在完整有效检查后成立 |
| 空结果 | 区分“确实没有”和“尚未覆盖” | 给出空结果原因码 |
| 部分数据 | 明确缺失范围，保留官方核验入口 | 不覆盖已知有效字段 |
| 数据过期 | 显示最后成功时间和风险 | 不宣称当前仍有效 |
| 来源失败/受限 | 解释暂时无法确认 | 保留失败原因、重试和人工复核入口 |
| 未登录 | 允许公共浏览，保存时提示登录 | 不创建匿名私人数据 |
| 无权限 | 不泄露记录是否存在 | 统一鉴权和审计 |
| 重复操作 | 告知已保存/已存在及后续入口 | 幂等或明确冲突规则 |

## 11. 单项功能规格模板（A4 使用）

A4 中每一项 CAP 必须包含以下字段，不满足时不能进入架构或开发：

```text
功能 ID / 名称
关联 JTBD 与假设
用户分群与使用边界
delivery_status / evidence_status / priority / target_release
当前事实与证据链接
目标用户结果
范围 / 非目标
前置条件与触发
主流程
业务规则与字段口径
页面、API 和数据状态
公共/私人边界、权限、隐私与合规
埋点与成功/护栏指标
依赖、失败降级与回滚
Given / When / Then 验收标准

开放问题与决策人
```

### 11.1 验收标准最低要求

- 不只验证成功路径；
- 明确首次基线与后续差分；
- 明确来源失败时是否沿用旧数据；
- 明确重复保存、并发更新和状态修正；
- 明确用户数据归属、导出、删除和越权行为；
- 自动分类必须能查看原始证据并允许修正；
- 原型不能作为代码已实现的验收证据。

## 12. 非功能需求框架

### 12.1 数据可信与可追溯

- 每条公共变化都能追溯到公司、来源、抓取时间、有效快照和差分规则；
- 自动分类保留原始文本、规则/模型版本、置信度和人工修正；
- 运营修正不可静默覆盖历史证据；
- 来源健康和覆盖范围能被普通用户理解，不只存在于日志中。

### 12.2 隐私与安全

- 公共数据与私人数据分离；
- 私人数据默认按用户隔离，服务端校验所有权；
- 提供导出、删除和生命周期规则；
- 通知正文、联系人和时间安排按敏感数据处理；
- 日志和分析不得收集不必要的私人内容。

### 12.3 合规与来源边界

- 官方公开来源优先，遵守站点访问规则、频率限制和合理使用边界；
- 对受限来源采用人工确认、官方跳转、合作或用户主动保存，不绕过访问控制；
- BOSS 直聘、猎聘等平台数据只能作为经过合规确认的补充能力，不能成为首个可信闭环的依赖；
- 任何来源均需记录使用目的、允许方式、停用条件和负责人。

### 12.4 可用性、可靠性与可观测

A4 结合实际架构补齐响应时间、可用性、备份恢复、监控告警和容量目标。所有目标必须区分本地作品集演示、受控试点和生产环境，不使用没有测量方式的百分比。

### 12.5 无障碍与移动端

核心发现、官方核验、保存和更新下一步应支持键盘操作、可读焦点、文本替代和基础响应式布局。具体标准和验收设备在设计阶段确定。

## 13. 数据来源与公司池原则

1. 公司池是受管理的产品资产，不是一次性爬虫名单；
2. 先用 10 家技术样本覆盖 3–5 类官方站点结构，再扩展约 30 家核心和约 100 家扩展公司；
3. 企业类型用于保证代表性，实际监控对象是具体公司；
4. 正式招聘官网、官方 ATS 和可验证的正式公告优先；
5. 公众号等难以稳定自动访问的来源可用于线索发现和人工复核，但不得伪装成稳定全量采集；
6. 旧海外 Greenhouse 等来源仅保留为历史适配器或技术样本，不再作为国内校招默认数据源；
7. 每次扩大公司池前，必须先满足覆盖准确性、失败可见性和维护成本门槛。

详细来源策略由 [数据源策略](DATA-SOURCE-STRATEGY.md) 管理；V3 PRD 只规定用户承诺和产品边界。

## 18. A4 完成定义

A4 将本稿提升为主 PRD 前，必须满足：

- [ ] 每个 CAP 的交付状态已对照代码、接口、数据迁移和测试复核；
- [ ] 每个 CAP 至少关联一个 JTBD、一个用户结果和必要的假设；
- [ ] 当前实现、当前缺口、目标能力和未来候选明确分栏；
- [ ] 公共/私人、用户/运营、官方/补充来源边界明确；
- [ ] 招聘类型、届别、变化、基线、新鲜度和失败口径唯一；
- [ ] 关键功能具有成功、空、加载、部分、过期、失败、未登录、无权限和重复状态；
- [ ] 验收标准可用 Given/When/Then 执行，且能映射到测试或人工验收；
- [ ] 所有数字、结论和“已实现”表述有带日期的证据；
- [ ] 所有开放冲突都有决策人、截止点和处理结果；
- [ ] Figma 只引用目标交互，不被用作实施证据；
- [ ] 项目所有者审核通过后，再执行主 PRD 提升和旧稿归档。

## 19. A3 审核问题

请项目所有者重点审核以下四点：

1. 是否认可使用“交付状态 + 证据状态 + 优先级 + 目标版本”四维记录需求；
2. 是否认可 CAP-PUB / BRD / PRI / ACC / NOT / OPS 作为统一功能编号；
3. 是否认可“保存到私人空间”是 P0 用户结果，但浏览器插件只是待验证方案；
4. 是否认可“对纳入公司池的官方来源追求可审计完整性”，取代无法证明的“全网全部收录”表述。
