## 1. 核心任务链

```text
进入招聘窗口
→ 发现目标公司的变化
→ 按届别和招聘类型收敛
→ 判断来源、时间和覆盖是否可信
→ 进入企业官方页面核验具体岗位
→ 决定忽略、关注或保存
→ 管理投递状态与下一步
→ 根据新通知更新行动
→ 结束、重开或复盘
```

这条链路跨越三个业务边界：

| 业务边界 | 回答的问题 | 主要分群 |
|---|---|---|
| 公共招聘雷达 | 哪些目标公司发生了与我相关的招聘变化？ | S1，兼顾 S2 |
| 官方招聘导航 | 这条信息来自哪里、何时核验、是否值得相信？ | S1、S2、S3 |
| 私人求职工作台 | 我决定跟进什么、现在到哪一步、下一步是什么？ | S2，边界上服务 S3 |

## 2. 问题与证据概览

| 问题 ID | 问题 | 当前证据 | 置信度 | 关键反例 |
|---|---|---|---|---|
| P-R01 | 目标公司招聘入口分散，需要重复查看 | 国内公开个案、公开清单行为、专家走查 | 中 | 只关注少量公司时书签已足够 |
| P-R02 | 静态岗位列表难说明“相较上次发生了什么” | 产品逻辑和竞品对比 | 低，待真人验证 | 用户可能只关心当前岗位，不关心变化 |
| P-R03 | 届别、春秋招、暑期/日常实习等分类混杂 | 校招来源结构、专家走查 | 中 | 用户可能直接在官网搜索，不依赖聚合筛选 |
| P-R04 | 来源、更新时间和覆盖状态不透明 | 竞品协议、数据运营风险 | 低至中 | 用户可能不阅读可信度信息 |
| P-L01 | 从外部发现到私人保存存在重复录入 | 公开手工台账、合成反例 | 中 | 用户可能直接官网投递，不保存中间状态 |
| P-W01 | 多个机会并行时状态、通知和下一步容易分散 | 多条第一人称公开记录 | 高 | 邮箱和日历可能已经足够 |
| P-W02 | 收到新通知后需要重新关联岗位并重复更新 | 公开记录、专家走查、合成反例 | 中至高 | 自动解析权限或信任成本可能更高 |
| P-W03 | 长期无反馈使进行中记录失真 | 公开记录 | 中 | 用户可能不需要显式关闭 |
| P-W04 | 用户可能希望复盘，但复杂漏斗价值不足 | 少量公开记录 | 低至中 | 记录不完整会让分析误导 |

## 3. 公共招聘雷达 Job Stories

### JS-R01｜发现目标公司招聘变化

- **分群**：S1；兼顾 S2
- **优先级**：P0（核心价值假设）
- **证据状态**：问题存在性有中等证据；变化流方案价值尚未由真人验证

> 当我关注的公司进入校招或实习窗口时，我想在一个地方看见哪些公司开始招聘、出现更新、新增或关闭了机会，以便决定今天需要核验哪些公司，而不是逐个打开所有招聘入口。

**结果验收信号**：

1. 用户能从整个目标公司池识别当前时间范围内发生变化的公司；
2. 用户能区分“新收录公司”“开始招聘”“有更新”“系统新发现岗位”和“关闭岗位”；
3. 用户知道变化按系统发现时间计算，不被误导为企业一定在当天发布；
4. 同一公司的多个变化被聚合，不用在重复记录中寻找重点；
5. 用户可以按日期、届别、招聘性质、行业或岗位方向收敛结果；
6. 来源失败或覆盖不完整时，系统不把未知状态展示成“没有变化”。

### JS-R02｜判断数据是否可信

- **分群**：S1、S2、S3
- **优先级**：P0（信任基础）
- **证据状态**：产品风险明确；用户是否会主动使用这些信息待验证

> 当我准备根据一条招聘变化采取行动时，我想知道它来自哪个官方来源、最后何时成功核验以及覆盖是否完整，以便判断应当相信、再次核验还是暂时忽略。

**结果验收信号**：

1. 用户能看到来源名称、权威等级、最近成功核验时间和数据截止时间；
2. 用户能区分“完整核验”“仅官方入口”“人工核验”“覆盖不完整”和“来源异常”；
3. 失败快照不会覆盖上一份有效事实，也不会产生虚假关闭；
4. 无法识别具体岗位差额时只显示“页面有更新”，不伪造新增数量；
5. 用户可以追溯变化对应的公司、来源和证据时间；
6. 发生来源冲突或未知时，界面明确说明限制并保留官方核验入口。

### JS-R03｜只查看与自己相关的招聘活动

- **分群**：S1；兼顾 S2
- **优先级**：P0（校招基础能力）
- **证据状态**：来源结构和专家走查支持，真实筛选优先级待验证

> 当公司同时发布不同届别、批次和实习类型的招聘时，我想按自己的毕业年份和求职阶段筛选，以便排除明显不适用的活动，只核验与我相关的机会。

**结果验收信号**：

1. 用户可以按毕业届别筛选，并能处理一个活动对应多个届别的情况；
2. 用户可以区分提前批、秋招、春招、补录、暑期实习和日常实习；
3. 未知届别或类型不会被系统擅自归类，也不会静默消失；
4. 日期、届别、招聘性质、行业和岗位方向组合时采用一致的交集逻辑；
5. 筛选结果保留公司、活动、最近核验和官方入口上下文；
6. 没有结果时能区分“确无匹配”“来源异常”和“字段尚未识别”。

### JS-R04｜进入官方来源核验具体岗位

- **分群**：S1、S2、S3
- **优先级**：P0
- **证据状态**：产品边界和合规要求明确

> 当我发现一项可能相关的招聘活动时，我想快速进入企业官方招聘页面查看完整岗位和申请要求，以便用权威信息做最终判断和投递。

**结果验收信号**：

1. 公司和招聘活动页面始终提供清晰的官方入口；
2. 二级发现来源与企业官方来源明确区分，不能覆盖官方事实；
3. 跳转前用户知道将离开 JobPulse，并能识别目标域名或入口类型；
4. 官方入口失效时显示最后核验和替代官方入口，不跳转到不明第三方页面；
5. JobPulse 的轻量岗位信息不冒充完整 JD，最终要求以企业官方页面为准；
6. 用户可在三次以内的主要交互中从变化或公司列表到达官方入口。

## 4. 公共到私人连接 Job Story

### JS-L01｜保存真正感兴趣的岗位

- **分群**：S1→S2；边界上服务 S3
- **优先级**：P0（两侧连接点）
- **证据状态**：公开手工台账支持保存行为；浏览器插件方案尚未真人验证

> 当我在企业官方招聘页确认一个值得跟进的岗位时，我想用最少操作保存岗位链接和必要上下文，以便回到自己的求职工作台继续判断或投递，而不用重新复制整份 JD。

**结果验收信号**：

1. 用户可以从官方招聘页面主动发起保存，系统不会批量替用户收藏；
2. 最小保存只要求足够识别机会的公司、岗位和原始链接，其余字段可稍后补充；
3. 解析到的标题、地点或 JD 在写入前可由用户检查和修改；
4. 无法解析或受限域名仍允许只保存链接和用户备注，不绕过访问限制；
5. 保存内容进入用户私人空间，不自动变成公共岗位事实；
6. 成功后用户能选择“仅收藏”“待投递”或进入正式投递流程，并能返回原始官方页面。

## 5. 私人求职工作台 Job Stories

### JS-W01｜知道当前状态与下一步

- **分群**：S2
- **优先级**：P0
- **证据状态**：公开第一人称行为证据较强

> 当多个机会同时进入不同阶段时，我想快速看到每个机会现在到哪里、最近发生了什么和下一步什么时候做，以便不漏掉行动，也不需要在表格、邮箱和日历之间来回核对。

**结果验收信号**：

1. 用户能按进行中、已结束和需要行动找到对应机会；
2. 每个机会显示当前状态、最近事件和最近下一步，而不是只有一列静态状态；
3. 状态变化保留时间线，用户可以理解事件先后和修改来源；
4. 测评、笔试、面试和材料截止进入统一近期安排；
5. 同一时间冲突或即将到期的行动可被识别，但不会在未授权时发送虚假提醒；
6. 私人记录可以导出、删除并与其他用户隔离，不因公共岗位关闭而丢失历史。

### JS-W02｜用新通知更新行动

- **分群**：S2；边界上服务 S3
- **优先级**：P0
- **证据状态**：维护摩擦有中等至高证据；解析偏好、权限与信任待真人验证

> 当我收到测评、笔试或面试通知时，我想快速把它关联到正确岗位并形成待确认的状态和时间，以便一次操作同时更新历史与下一步，而不是重复录入。

**结果验收信号**：

1. 用户可以粘贴文本或选择手工方式，不被强制授予邮箱权限；
2. 系统展示识别出的公司、岗位、建议状态、时间和置信信息；
3. 任何业务状态和日程写入前都需要用户确认；
4. 状态事件与带时间的下一步在一次确认中一致写入，失败时不留下半条记录；
5. 无法识别日期、公司或岗位时明确要求补充，不凭空推测；
6. 原始通知或必要证据按用户选择保留，并允许后续纠错和撤销。

### JS-W03｜结束、重开或跟进长期无反馈的机会

- **分群**：S2
- **优先级**：P1
- **证据状态**：公开行为证据中等

> 当一个投递长期没有回复或岗位状态发生变化时，我想明确决定继续跟进、标记无回应关闭或重新打开，以便进行中清单反映我的真实判断，而不是被永久悬置的记录污染。

**结果验收信号**：

1. 系统可以提示长期未更新，但不能自动把机会判定为拒绝或关闭；
2. 用户能区分“无回应关闭”“岗位关闭”“主动放弃”和“明确拒绝”；
3. 关闭前可记录最后跟进时间、原因和备注；
4. 关闭后历史仍保留，且不继续进入进行中和近期行动；
5. 后续收到新通知时可以重开并保留前后时间线；
6. 公共来源异常不会自动修改用户的私人投递状态。

### JS-W04｜在数据足够时复盘真实进展

- **分群**：S2 生命周期延伸
- **优先级**：P1，复杂细分暂缓
- **证据状态**：仅少量公开行为支持

> 当一轮求职进入中后期时，我想回看自己实际到达过哪些阶段和哪些行动仍未完成，以便调整接下来的投入，而不是被投递总量或不完整记录误导。

**结果验收信号**：

1. 基础漏斗按曾经到达的阶段计算，而不是只读取当前状态；
2. 有效进展与单纯投递数量分开，避免鼓励无效海投；
3. 指标可以下钻到对应私人机会和事件；
4. 记录缺失、样本过小或状态不完整时显示限制，不生成确定性策略建议；
5. 用户能看到未完成的下一步和已结束原因，而不仅是一组百分比；
6. 按岗位、渠道或公司类型的复杂分析必须等待真实样本和真人价值验证。

## 6. S3 边界 Job Story

### JS-B01｜只处理真正需要行动的机会

- **分群**：S3
- **优先级**：边界验证，不作为当前核心成功目标
- **证据状态**：公开低维护个案与合成反例支持现象存在

> 当一个机会真正需要我参加测评、面试或提交材料时，我想只保存完成这次行动所需的最少信息，以便及时处理，同时继续使用我熟悉的邮箱和日历。

**结果验收信号**：

1. 用户无需先导入全部历史或建立完整岗位档案；
2. 一次行动只要求公司、岗位、时间和原始通知等必要上下文；
3. 用户可以拒绝邮箱、日历或浏览器权限并继续手工完成；
4. 系统不以补全字段、维护连续签到或查看看板作为完成任务的前提；
5. 行动完成后用户可以导出、删除或离开，不被锁定；
6. 真人测试允许结论是“邮箱/日历更合适”，不强行把 S3 转化为核心用户。

## 7. Job Story 优先级与产品边界

| ID | 结果 | 业务边界 | 当前优先级 | 当前状态判断 |
|---|---|---|---|---|
| JS-R01 | 发现公司招聘变化 | 公共雷达 | P0 | M1 目标，高保真不等于已上线，价值待验证 |
| JS-R02 | 判断数据是否可信 | 公共雷达/导航 | P0 | 数据模型基础部分已有，用户表达待实现与验证 |
| JS-R03 | 按校招语境收敛 | 公共雷达 | P0 | 目标字段已定义，完整覆盖和筛选待实现 |
| JS-R04 | 进入官方来源核验 | 官方导航 | P0 | 首批官方入口已登记，多公司体验待完善 |
| JS-L01 | 保存感兴趣岗位 | 公共→私人 | P0 | 插件为目标方案，尚未真人验证 |
| JS-W01 | 状态与下一步 | 私人工作台 | P0 | M0 主流程已有演示能力，待多用户化与真实提醒 |
| JS-W02 | 通知更新行动 | 私人工作台 | P0 | M0 有粘贴解析与确认演示，权限和持续价值待验证 |
| JS-W03 | 结束与重开 | 私人工作台 | P1 | 基础状态能力可复用，成熟规则待 PRD 裁决 |
| JS-W04 | 复盘真实进展 | 私人工作台 | P1 | 基础漏斗已有，复杂分析暂缓 |
| JS-B01 | 最小关键行动 | 边界 | 验证项 | 不作为当前核心功能覆盖目标 |

优先级表示当前产品判断，不表示用户已经确认需求。A3/A4 编写 PRD 时，每项功能必须说明它支持哪个 Job Story、属于当前实现还是目标能力，以及如何用真实任务验证。

## 9. 关键待验证假设

| 假设 ID | 假设 | 停止或转向条件 | 推荐验证 |
|---|---|---|---|
| H-R01 | S1 会持续监控一组具体公司 | 多数受试者只在偶发节点查看，书签或公众号已经足够 | 问题访谈、两周日记 |
| H-R02 | 公司变化流比静态清单更有行动价值 | 多数受试者只寻找当前岗位，无法解释或不关心变化指标 | 变化流原型任务、现有方式基线对比 |
| H-R03 | 来源、核验时间和覆盖状态能改善判断 | 用户忽略可信度信息，或看完仍无法做出不同判断 | 对照任务、理解访谈 |
| H-L01 | 官方核验后保存能连接公共与私人两侧 | 用户直接投递，不愿保存或安装插件 | 端到端原型与插件意愿测试 |
| H-W01 | 私人工作台比表格降低维护成本 | 表格在耗时、正确率和下一步安排上不差于 JobPulse | 同类任务基线比较 |
| H-W02 | 通知到下一步形成持续使用价值 | 用户不愿授权/粘贴，或仍主要依赖邮箱日历 | 可用性测试、7 天试用 |
| H-B01 | S3 存在可服务的最小行动场景 | 任何额外工具都不如邮箱/日历 | 反例访谈；允许停止开发该方向 |

## 10. A2 评审重点

1. 是否认可 JS-R01～R04 作为公共招聘雷达的核心任务；
2. 是否认可 JS-L01 是公共事实进入私人行动的唯一必要连接点，不要求用户必须完成整条链路；
3. 是否认可 JS-W01/W02 优先于复杂看板、完整简历和自动投递；
4. 是否认可 S3 只作为边界验证，并允许邮箱/日历是更优答案；
5. 是否认可把旧 JS-01 岗位去重降为数据质量规则，而不是产品创新点。
