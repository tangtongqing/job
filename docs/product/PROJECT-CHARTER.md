## 1. 项目背景

**提出人**：用户（求职中的产品经理）
**动机**：
- 个人痛点：校招/实习信息分散在多个平台，难以统一追踪；投递后缺乏系统化的状态管理。
- 职业目标：本项目同时作为**产品经理求职作品集**的核心支撑，需能讲出完整的产品故事（发现痛点 → 调研 → 定义 → 设计 → 落地）。

## 2. 目标用户（v3 更新）

| 画像 | 定位 | 说明 |
|------|------|------|
| P1 林晓 | **核心画像** | 近一个月跨 3 个以上渠道、累计投递 20 个以上岗位的高频求职者 |
| P2 周明 | **次要画像**（能力受限） | 实习定向型，核心需求超出 MVP 能力边界 |
| P3（P1延伸） | P1 生命周期阶段 | 秋招失败后的复盘阶段 |

> 画像不绑定招聘季节，任何时间点只要符合行为特征即为核心用户。

## 3. 项目形态决策（v4 升级）

### 3.1 当前交付形态：作品集 Demo（路径 B，不变）

**Demo 仍是交付主体**，路径 B 的判断不变（成本、周期、PM 作品集优先级）。

| 选项 | 决策 | 理由 |
|------|------|------|
| 作品集 Demo | ✅ 采纳（交付主体） | 成本低、周期短、面试可现场演示；PM 求职看重产品能力而非工程量 |
| 小规模 SaaS | 暂不实现（仅做演进预留） | 成本 ~300/月 + 采集合规负担；但作为演进蓝图写入文档 |
| 生产级 SaaS | 暂不实现（仅做演进预留） | 成本 2000+/月 + 高可用架构，投入产出比低 |

### 3.2 v4 新增：双面产品架构（Demo 阶段即落地）

Demo 不再是"只有应用面"，而是**双面产品**：

| 面 | 寄存器 | 作用 | Demo 阶段交付 | 参考 |
|----|--------|------|--------------|------|
| **营销面** | brand register | 介绍产品 / 展示价值主张 / 定位 | 落地页 `/` + 定价页 `/pricing` | 用户提供的 8 张图（ClarityUI 等） |
| **产品面** | product register | 工具本身 / 交付核心价值 | 5 个核心页面（看板/岗位/投递/订阅/采集） | Linear / Vercel Dashboard / Greenhouse |

**两套寄存器共存且隔离**：
- 营销面允许 hero、大留白、情绪化文案、社会证明占位（参照 Linear/Vercel 官网）
- 产品面保持效率、密度、克制（参照 Linear app、Vercel dashboard）
- 视觉令牌（颜色/字体）共享基础调色板，但**应用层规则不同**（营销面可用更大字号、更宽行距、更多负空间）

**定位语气（v5 已与用户确认）**：**真实营销型**。
- 落地页按真实在售 SaaS 展示，CTA 是「免费开始」「开始试用」
- 定价页用真实营销语气（14 天免费试用/无需信用卡），不标注"作品集示意"
- 视觉标杆对标 Linear / Notion / Apple 落地页
- v5 转向理由：用户迭代中反馈"查看 Live Demo 太怪，不是营销页该有的"。Demo 仍不接支付，仅展示语气转真实营销

### 3.3 v4 新增：范围纪律（IN / OUT 边界）

> 范围纪律是 v4 的核心。新增营销面与演进蓝图容易引发 scope creep，必须用明确边界表锁死。

| Demo 做（IN） | Demo 不做（OUT，仅文档/架构预留） |
|---------------|----------------------------------|
| ✅ 营销面落地页（brand register） | ❌ 真实鉴权 / 多用户 / 多租户实现 |
| ✅ 定价策略 artifact + 定价页 UI | ❌ 支付集成（Stripe 等） |
| ✅ 演进蓝图文档（M0→M1→M2 路线） | ❌ 原生 App（iOS/Android） |
| ✅ 架构演进预留（多租户接缝、API 三层命名空间、迁移注释） | ❌ admin 后台实现（仅留 API 命名空间位置） |
| ✅ 响应式 Web + PWA（桌面优先，移动端核心流程走得通） | ❌ 后端 RBAC 权限模型实现 |
| ✅ 移动端英雄功能：F-C.5 邮件→AI 解析（手机场景天然） | ❌ 真实 LLM 计费/用量配额系统 |

**判断准则**：任何"实现 SaaS"性质的工作，一律走文档/架构预留路径，不进 Demo 代码库。这本身就是 PM 作品集的高价值展示——"我想到了演进路径并做了架构预留"比"我做了个 Demo"高级。

### 3.4 影响小结

- 数据库仍用 SQLite（零配置），不引入账号体系（或仅本地单用户）—— **不变**
- 部署以本地运行为主，演示可通过 Vercel + 云数据库（可选）—— **不变**
- 采集切换为国内校招官方来源优先；海外默认源停用，BOSS/猎聘等未经授权平台不抓取 —— **v7 更新**
- **新增**：营销面 2 个页面纳入 Demo 范围（落地页 + 定价页）
- **新增**：响应式 + PWA 作为前端质量要求（非可选）
- **新增**：演进蓝图作为独立文档产出（`docs/product/ROADMAP.md`）

## 6. 技术栈决策

| 层 | 选型 | 决策依据 |
|----|------|---------|
| 后端 | Python + FastAPI | 采集生态最强（招聘爬虫行业标准）；自动生成 API 文档 |
| 前端 | Next.js + TypeScript + Tailwind + shadcn/ui | 仪表盘 UI 成熟；impeccable 对 React 支持最佳；Vercel 一键部署 |
| 采集 | Playwright + httpx + APScheduler | 兼顾动态渲染（Playwright）与轻量请求（httpx）+ 定时调度 |
| 数据库 | SQLite → PostgreSQL | Demo 零配置起步，生产平滑迁移 |

## 7. 数据源策略

**采集方式：国内企业官方 API / RSS / 招聘官网 / 正式公告为主，政府与高校就业平台做发现和核验，授权平台做补充。**

| 来源类型 | 优先级 | 说明 |
|---------|--------|------|
| 企业官方招聘页、校招专题、公开 ATS / RSS | P0 | 招聘活动和岗位的主要事实源 |
| 企业官网公告、官方公众号公开链接 | P0 | 发现春招、秋招、实习和补录；保留官方原文 |
| 教育部/人社平台、国聘、高校就业网 | P0 发现层 | 发现与交叉核验，尽量回链企业官方申请页 |
| 获书面授权的平台 API / 数据合作 | P2 | 扩大覆盖，不得覆盖官方事实 |
| 用户手工链接/录入 | P2 兜底 | 属于私人数据，不进入公共岗位目录 |

> 详细边界、覆盖率和实施顺序以 [国内校招数据源策略](DATA-SOURCE-STRATEGY.md) 为准。目标公司池内完整收录官方发布的全部校招岗位，采集层不做岗位方向筛选；首批以 100 家公司池衡量覆盖，不宣称无法验证的“全网 100%”。

## 8. 风险与对策

| 风险 | 等级 | 对策 |
|------|------|------|
| 来源访问或模板变化 | 高 | 来源注册表、模板族契约测试、连续 0 条告警与人工复核 |
| 数据合规 | 高 | 逐源审核；fail closed；不登录、不绕过验证码/反爬、不使用代理池规避限制 |
| 作品集 vs 工程深度取舍 | 中 | 明确以"产品故事完整"为优先，工程深度够用即可 |
| 官方公告覆盖不全 | 高 | 版本化公司池、官网/ATS/公告/公众号多信号发现、人工审计发现率 |
