# JobPulse 产品与网站标准验收方案

**制定日期**：2026-07-27

**状态**：已执行（2026-07-27，本地修复完成，线上待部署复验）

**验收对象**：SaaS 官网、产品后台、作品集案例页、FastAPI 后端及线上部署链路

## 一、验收目标

本轮验收不只检查页面能否打开，而是回答四个问题：

1. 用户是否能理解产品解决什么问题，并顺利进入产品后台。
2. 求职管理的核心链路是否真实可操作、数据是否前后一致。
3. 网络异常、空数据、错误输入和共享数据被修改后，产品是否有清晰反馈并可恢复。
4. 官网、后台和案例页是否达到面试展示所需的稳定性、可信度和完成度。

本轮以“**可完整演示、可操作、可恢复**”为验收标准。账号隔离、长期自动采集和多用户权限不属于当前版本，但必须作为已知边界明确展示。

### 2.1 已有质量基础

- 后端已有 109 项自动化测试。
- 前端 ESLint、Next.js 构建和 Sites 构建已有通过记录。
- 线上已完成收藏、创建投递、状态流转、订阅和 Demo 重置等人工验收。

### 2.2 本轮重点补齐

| 风险 | 现状 | 本轮处理 |
|---|---|---|
| 前端回归不足 | 当前没有浏览器 E2E 测试脚本 | 建立 Playwright 核心流程回归 |
| 环境口径不一致 | 本地可达 56 条，线上固定 24 条 | 分开记录本地与线上结果 |
| 共享演示数据 | 访客操作会影响其他访客 | 验证二次确认、重置和恢复结果 |
| 外部链接质量 | 岗位可能失效或跳转异常 | 抽检来源链接和官方投递链接 |
| 前端错误反馈 | 空订阅反馈曾不明确 | 覆盖表单校验、接口错误和网络错误 |
| AI 能力边界 | 线上无付费模型，仅规则降级 | 验证降级标识、置信度和用户确认 |
| 线上可用性 | Railway 免费试用可能暂停 | 验收前检查健康状态和首屏恢复时间 |
| 展示体验 | 视频、动画曾出现重叠和自动播放干扰 | 重测播放、停止、悬停及响应式表现 |

## 四、标准测试流程

### 阶段 0：验收准备

1. 记录当前源码版本、部署版本和 API 地址。
2. 检查线上健康状态，执行一次 Demo 重置并核对标准数据。
3. 建立缺陷台账，字段包含编号、环境、页面、复现步骤、预期、实际、证据、等级和状态。
4. 冻结本轮验收范围，非阻塞新需求进入后续版本，不在测试过程中无限扩项。

### 阶段 1：自动化质量基线

依次执行：

1. 后端 `python -m pytest`。
2. 前端 `npm run lint`。
3. 前端 `npm run build`。
4. Sites `npm run build:sites`。
5. API 健康、CORS、核心只读接口和写接口冒烟测试。

任一构建失败、后端测试失败或核心接口 5xx，停止进入正式产品验收。

### 阶段 2：API 与数据一致性

验证：

- 列表与详情字段一致。
- 收藏、待投递、投递记录和岗位之间的关联正确。
- 状态流转符合 9 状态规则，非法流转被阻止。
- 每次状态变化生成事件，当前状态、时间线、看板和待办同步。
- 重复收藏、重复待投递和重复创建投递不会产生脏数据。
- 订阅创建、编辑、删除及空条件校验正确。
- Demo 重置后各表数量、状态和关联恢复到标准值。
- AI 解析在无 Key 时走规则降级，确认前不修改数据。

### 阶段 3：浏览器端核心流程

按照真实用户任务执行，不以“页面返回 200”代替功能验收。

| ID | 用户任务 | 操作主线 | 核心预期 |
|---|---|---|---|
| P0-01 | 理解产品 | 官网首屏 → 功能说明 → CTA | 价值主张清楚，CTA 正确进入后台 |
| P0-02 | 查找岗位 | 岗位页 → 搜索/筛选 → 分页 → 清空筛选 | 结果、数量、分页与条件一致 |
| P0-03 | 判断岗位 | 岗位详情 → 阅读 JD/要求 → 打开来源/投递链接 | 信息完整，外链指向对应官方岗位 |
| P0-04 | 收藏比较 | 收藏岗位 → 查看收藏页 → 取消收藏 | 跨页面状态同步，无重复记录 |
| P0-05 | 准备投递 | 加入待投递 → 查看待投递 → 移除 | 清单与按钮状态一致 |
| P0-06 | 创建投递 | 待投递 → 创建投递 → 投递列表 | 创建成功并从待投递移除 |
| P0-07 | 推进状态 | 已投递 → 测评 → 面试 → Offer | 状态、事件、看板和待办同步 |
| P0-08 | AI 辅助更新 | 粘贴通知 → 查看建议 → 用户确认 | 建议可解释，确认后才流转 |
| P0-09 | 管理订阅 | 新建 → 编辑 → 删除 → 空表单提交 | CRUD 正确，错误输入有明确提示 |
| P0-10 | 恢复演示 | 修改数据 → 点击重置 → 二次确认 | 恢复标准数据且页面重新同步 |
| P0-11 | 理解采集边界 | 进入采集页 → 查看来源 → 尝试线上触发 | 清楚说明公开版限制，403 被友好呈现 |
| P0-12 | 查看作品集 | 官网/后台 → 案例页 → Demo CTA | 项目逻辑完整，链接无断点 |

每个场景必须记录起始条件、逐步操作、每步可观察结果和最终数据状态。

### 阶段 4：异常、边界与体验测试

#### 功能异常

- 搜索无结果、空收藏、空投递、空待办和空订阅。
- 不存在的岗位或投递 ID。
- 重复点击、连续提交和页面刷新。
- 非法状态流转、终态纠错和面试状态自循环。
- 超长关键词、特殊字符、空格和中英文混合输入。
- API 400、403、404、409、422、500 及网络断开。

#### 产品体验

- Loading、Empty、Error、Success 四类状态均有明确反馈。
- 操作后反馈及时，按钮不会在请求中被重复点击。
- 返回路径和下一步动作明确，不出现页面死胡同。
- 状态名称、数量、时间和筛选条件在不同页面口径一致。
- 公开演示限制、AI 降级及演示岗位标识不会误导用户。

#### 网站展示

- 主视频可播放、暂停、停止并回到静态展示。
- 次级视频只在悬停时播放，离开后停止。
- 视频、动画、导航、按钮和正文不重叠。
- 桌面和移动端无横向溢出、文字截断或操作区遮挡。
- 亮暗主题颜色、状态色、图表和对比度可读。
- 官网、后台和案例页的品牌、术语、数字及链接一致。

#### 非功能检查

- 首屏及核心页面在正常网络下可接受地加载。
- 页面无明显布局抖动、大资源阻塞和持续报错。
- 键盘可访问主要按钮和表单，焦点可见。
- 图片有替代文本，表单有标签，颜色不是唯一状态表达。
- CORS 仅允许规定来源；公开环境不暴露密钥或敏感日志。

### 阶段 5：产品走查与探索性测试

以四种视角各走一遍产品：

1. **首次访客**：能否在 30 秒内理解产品、知道下一步。
2. **求职用户**：能否完成从找岗位到管理面试的完整任务。
3. **面试官**：能否快速看懂产品思路、功能深度和项目真实性。
4. **异常用户**：快速点击、错误输入、刷新和返回时是否破坏数据。

重点检查“功能存在但用户不知道如何使用”“数据正确但表达难理解”“演示效果好但操作不能闭环”三类产品问题。

### 阶段 6：缺陷修复与回归

1. 每个缺陷先确认复现步骤和影响范围。
2. 按 P0—P3 排序，P0/P1 修复后才能进入最终验收。
3. 修复后执行单点回归、关联链路回归和自动化基线回归。
4. 同一问题连续两次回归通过后关闭。
5. 对重复出现的核心问题补充自动化用例。

### 阶段 7：最终展示彩排

1. 重置标准数据。
2. 从官网进入后台。
3. 完成搜索、岗位详情、收藏、待投递、创建投递、状态流转、AI 建议、待办和看板联动。
4. 打开案例页说明产品决策与技术边界。
5. 再次重置数据，确认展示环境恢复。
6. 录制一次完整操作视频并保存最终验收截图。

## 五、缺陷等级

| 等级 | 定义 | 示例 | 发布要求 |
|---|---|---|---|
| P0 阻断 | 产品无法访问、数据严重损坏、核心链路完全不可用 | 后端宕机、Demo 无法重置 | 必须修复 |
| P1 严重 | 核心任务失败或数据前后不一致 | 无法创建投递、状态与看板不同步 | 必须修复 |
| P2 一般 | 有替代路径，但明显影响理解或操作 | 空订阅无提示、移动端按钮遮挡 | 原则上修复 |
| P3 优化 | 不影响任务完成的体验或技术债 | 个别间距、弃用警告 | 可列入后续 |

## 六、通过标准

只有同时满足以下条件，才能认定“产品可用于正式展示”：

- 后端测试、前端 lint、两类生产构建全部通过。
- 12 个 P0 核心场景全部通过。
- 无未关闭 P0、P1 缺陷。
- P2 缺陷有明确处理结论，不得影响核心演示路线。
- 线上标准数据可重置，关键数量和页面状态一致。
- JD、来源链接和官方投递链接抽检通过。
- 桌面与移动端、亮色与暗色均无阻断问题。
- 官网视频和动效可控，不遮挡内容、不抢占操作。
- 公开演示、共享数据、采集关闭和 AI 降级边界表达清楚。
- 完成一轮无中断的最终展示彩排。

## 七、建议新增的自动化

当前最值得增加的是 Playwright 浏览器回归，而不是继续堆叠后端单元测试。

第一批自动化覆盖：

1. 官网 CTA 到后台。
2. 岗位筛选与详情。
3. 收藏与待投递。
4. 创建投递与状态流转。
5. 看板、待办和时间线联动。
6. 订阅 CRUD 与空表单校验。
7. Demo 重置。
8. 桌面/移动端基本视觉与溢出检查。

自动化写操作应在测试开始前和结束后执行 Demo 重置，避免污染共享环境；正式 CI 优先使用隔离的本地测试数据库。

## 八、交付物

执行完成后产出：

- `TEST-CASES-PRODUCT-WEBSITE.md`：详细测试用例与预期结果。
- `DEFECT-REGISTER.md`：缺陷、证据、等级、负责人和状态。
- `ACCEPTANCE-YYYY-MM-DD.md`：最终验收报告。
- Playwright 核心回归脚本与执行结果。
- 桌面/移动、亮/暗主题关键页面截图。
- 一段完整无中断的产品展示录像。

## 九、建议执行顺序

第一轮先跑自动化基线和 12 个 P0 场景，快速判断是否存在阻断问题；第二轮覆盖异常、移动端、主题、视频与数据口径；第三轮修复并回归；最后进行完整展示彩排。这样既符合标准测试流程，也能优先保障面试展示最关键的产品链路。
