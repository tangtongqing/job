# TASK-004 · PRD 初稿（产品需求文档）

阶段 1 的收官任务。TASK-001/002/003 已完成（竞品/痛点/市场分析），本任务把所有结论收口为一份**可执行的产品需求文档**，作为阶段 2（架构设计）和阶段 4（实现）的直接输入。

**目标**：产出作品集级的 PRD 初稿，覆盖功能需求、非功能需求、验收标准、范围边界。能直接用于：
1. 工程实现的依据（阶段 2/4）
2. 面试时"我如何写 PRD"的展示物

## 实现要求

### 一、PRD 标准结构（八个部分）

#### 1. 文档信息
- 版本号、作者、日期、状态、修订记录
- 关联文档清单（指向前面 4 个输入文档）

#### 2. 产品概述
- 一句话定位（引用 TASK-001/003 的差异化定位）
- 目标用户（引用画像，点明 P1 为首批）
- 核心价值主张（信息统一 / 投递闭环 / 数据驱动）
- 项目形态：作品集 Demo（路径 B，引用 TASK-003）

#### 3. 业务流程与状态机（**重点**）
**这部分是本 PRD 的硬核内容，必须画清楚**：

3.1 **采集流程**：源 → 调度 → 抓取 → 清洗 → 去重 → 入库 → 失效标记
3.2 **岗位生命周期**：新入库 → 展示中 → 已收藏 → 已投递 → 已关闭（失效）
3.3 **投递状态机**（核心）：
   - 明确定义所有状态：待投递 / 已投递 / 笔试 / 面试中 / Offer / 拒绝 / 已撤回
   - 画出状态流转图（文字或 Mermaid 描述）
   - 明确每个状态的触发条件、允许的下一状态、禁止的流转
   - 这是后续数据库设计与前端交互的依据
3.4 **订阅-推送流程**：用户订阅 → 匹配新岗位 → 推送通知

#### 4. 功能需求（**核心**）
按四大 MVP 模块组织，每个功能点用标准格式：

```
### 功能 F-X.X：<功能名>

**优先级**：P0/P1/P2（引用 TASK-002 映射表）
**对应 Job Story**：JS-XX
**用户故事**：作为 <画像>，我希望 <行为>，以便 <价值>

**功能描述**：<2-3 句话说清做什么>

**输入/输出**：
- 输入：...
- 输出：...

**验收标准（AC）**：
1. <可测试的具体条件>
2. ...

**异常与边界**：
- <空状态/错误/极端情况的处理>
```

**四大模块清单**（优先级已由前面任务锁定）：

- **模块 A：数据采集与展示（P0）**
  - F-A.1 多源采集器（公司官网 + 主流平台）
  - F-A.2 数据清洗与去重
  - F-A.3 岗位列表与筛选（关键词/地点/公司/薪资/应届标签）
  - F-A.4 岗位详情页（含 JD、要求、投递链接、来源）
  - F-A.5 定时调度与失效清理

- **模块 B：看板统计（P0）**
  - F-B.1 今日新增 / 收录总数 / 投递总数（核心 KPI 卡片）
  - F-B.2 投递转化漏斗（投递→笔试→面试→Offer）
  - F-B.3 近 7 天趋势图
  - F-B.4 分布维度（按公司/地点/岗位方向）

- **模块 C：投递管理（P0）**
  - F-C.1 投递状态机（状态流转，引用 3.3）
  - F-C.2 投递时间线
  - F-C.3 DDL 提醒（P1 增强，MVP 必做）
  - F-C.4 收藏与待投递区分

- **模块 D：个性化订阅（P0）**
  - F-D.1 订阅规则（关键词/公司/地点）
  - F-D.2 新岗位推送（站内通知 / Demo 阶段方式）

#### 5. 非功能需求
- 性能：列表加载 ≤ 1s；采集不阻塞用户操作
- 可用性：Demo 阶段不要求高可用，但要标注
- 兼容性：现代浏览器（Chrome/Edge/Safari 最新版）；移动端响应式（标注是否 MVP 必须）
- 安全：本地 SQLite，无账号体系（路径 B）；输入校验防注入；采集频率限制
- 合规：引用 TASK-003 风险对策（低频采集、公开数据、不存隐私）

#### 6. 数据模型预览（**为阶段 2 铺路**）
列出核心实体与关键字段（不要求完整建表语句，但要列出）：
- 岗位 Job：id、公司、岗位名、地点、薪资、JD、投递链接、来源平台、采集时间、发布时间、deadline、应届标签、状态
- 投递记录 Application：id、job_id、状态、时间戳链、备注
- 订阅 Subscription：id、用户、关键词、公司、地点、创建时间
- 公司 Company（可选）：id、名称、行业、官网

#### 7. 范围边界（**做/不做，引用 TASK-003**）
明确列出 Demo 阶段**不做**的功能（简历/面经/公司点评/社交/账号体系等），避免范围蔓延。

#### 8. 依赖与风险
- 依赖：采集源稳定性、反爬对抗
- 风险：引用 TASK-003 的风险表，标注在 PRD 层面的影响

### 二、质量要求

- **状态机必须完整且自洽**——这是 PRD 最容易出错的地方，也是面试最容易被追问的
- **验收标准必须可测试**——"用户体验好"不是 AC，"列表加载 ≤1s"才是
- **每个功能可追溯到 Job Story**——展示需求不是凭空来的
- **非功能需求要诚实**——Demo 阶段不要求高可用，但要标注清楚边界
- **范围边界要明确**——"不做"比"做"更重要
- Markdown 格式，中文撰写，篇幅 4000-6000 字

### 三、交付物自检

PRD 完成后，自查以下问题（这是面试官会问的）：
- [ ] 投递状态机的每个状态都有明确的进入/退出条件吗？
- [ ] 有没有死循环或不可达状态？
- [ ] 每个功能的验收标准是否真的可测试？
- [ ] 哪些功能是"看起来简单但实际有坑"的？（在风险里标注）
